## 0. 修订摘要：三条结论级修正

| # | 上一版的说法 | 修订后 | 依据 |
|---|---|---|---|
| ① | 「重打包成 IQ2_S（Vulkan 有内核）」 | **错**。OpenCL 的 `MUL_MAT_ID` 通用支持只有 **Q4_0 / Q8_0 / MXFP4**，整个 IQ 家族缺席 ⇒ IQ2_S 在 GPU 上无路 | vendored `ggml-opencl.cpp:9152-9180` |

## 1. 第一性约束：后端能力塌缩（FIG 1）

步骤一、二的所有结论都建立在「后端可靠」这个前提上。手机上这个前提不成立。

| 维度 | CUDA | OpenCL (Adreno) | Vulkan 原厂 | Turnip |
|---|---|---|---|---|
| 量化类型 | 全 | 白名单 ~11 种，**无 IQ 家族** | 全（生成式） | 全（生成式） |
| **MoE `MUL_MAT_ID`** | 全 | **仅 Q4_0 / Q8_0 / MXFP4**（+ Adreno 形状受限的一组 K-quant） | 全 | 全 |
| 编译器正确性 | 成熟 | 有坑（`__constant` 变址错编） | **三类 bug 并存** | 需三药 |
| 真机结论 | 改代码即生效 | 可用（PTQ1_0 内核 174/174） | **从未跑通** | 5–11 t/s |

> **原则**：量化格式不能「先选后找内核」，必须**从内核白名单反推**。

OpenCL 内核白名单（Adreno，源自 `kernels/` 目录枚举）：
`q1_0 · q4_0 · q4_1 · q4_K · q5_0 · q5_1 · q5_K · q6_K · q8_0 · iq4_nl · mxfp4`（+ 本地自研 PTQ1_0）。
MoE 专属内核 `gemv_moe_*` / `gemm_moe_*` 覆盖 q4_0/q4_1/q4_K/q5_0/q5_1/q5_K/q6_K/q8_0/mxfp4。

## 2. 架构差异：35B 不是「小一号的 Flash」（FIG 2）

| 维度 | Qwen3.8-Flash-Next | Qwen3.6-35B-A3B | 影响 |
|---|---|---|---|
| 专家表 | 48×512 = **24,576** | 40×256 = 10,240 实例 | **决定性** |
| 单专家 | 2.31 MiB | **0.844 MiB** | 预取粒度小 2.7× |
| 每 token 专家字节 | **1.11 GiB** | **270 MiB** | 小 4.1× |
| 注意力 | QSA(top_k 2048)+压缩比 | 30 DeltaNet + 10 全注意力，2 KV-head | 35B 引入 SSM/DeltaNet 算子 |
| KV/token | 需 indexer 打分 | **10.9 KB** | 64K 仅 0.65 GiB |
| PLE | **有，28.8 GB** | **无** | 手机上少一个必走 SSD 的子系统 |
| MTP | 有（blk.48） | **无** | 与「不做投机」一致 |
| 量化 | IQ3_S / IQ4_XS | **T42 自研 2.25 bpw** | 跨平台格式负债 |
| **每 token 比重** | MoE **69%** / KV 26% / attn 4% | dense **85%** / MoE 12% | **优化优先级反转** |
| 词表 | 248,320 | 248,320 | 一致，手术可复用 |

### 热集覆盖率算术（为什么分层在手机端第一次有意义）

| | 3 GiB 热集预算能覆盖多少 |
|---|---|
| Flash | 3 GiB ÷ 2.31 MiB = 1,330 个 ÷ 48 层 = **27.7/层 ÷ 512 = 5.4%** |
| 35B | 3 GiB ÷ 0.844 MiB = 3,640 个 ÷ 40 层 = **91/层 ÷ 256 = 35.5%** |

⇒ **覆盖率差 6.6×**。DGX 上「统一内存下分层没有作用对象」依然成立，但它对 35B 在 16G 手机上不成立。
⚠️ 这是**容量覆盖率**，实际收益取决于路由热度集中度——必须用真实对话样本统计 STRY 式热度表验证。

## 3. 格式决策（FIG 3）

| 目标后端 | MoE 可用格式 | 最小 bpw | 专家体积 | 全模型 |
|---|---|---|---|---|
| OpenCL 通用 | Q4_0 / Q8_0 / MXFP4 | 4.25 | 15.9 GiB | ≈19.8 GiB |
| OpenCL Adreno 专用 | + Q4_1/Q5_0/Q5_1/Q4_K/Q5_K/Q6_K | 4.5 | 16.9 GiB | ≈20.5 GiB |
| **CPU** | **全部（含 T42 原样）** | **2.25** | **8.44 GiB** | **11.37 GiB** |
| Vulkan | 全 | 2.25 | 8.44 GiB | 驱动不可用 |

**结论：双轨** —— 骨干（attn/SSM/lm_head，1.90 GiB，占每 token 85%）上 GPU；专家留 T42 走 CPU。
这样「格式负债」只落在**一个 CPU vec_dot 内核**上，而不是四个 GPU 后端。

## 4. 分层与调度：把 UFS 当虚拟内存用（FIG 4）

> 手机没有可用的 swap：ZRAM 是「压缩 RAM」，对已量化权重压缩比≈1；写回式 swap 还会成倍消耗 NAND 寿命。
> 唯一可用的是 **UFS 上的 file-backed mmap**，靠「干净页可被内核直接丢弃、不需写回」的语义。

| 层 | 介质 | 容量 | 内容 | 回收语义 | 对应 Strata |
|---|---|---|---|---|---|
| **L0** | Adreno / 匿名内存 | 1.5–2.5 GiB | per-layer pin 热专家 + KV | 匿名，不可丢 | expert-cache + `--expert-cache-per-layer` |
| **L1** | CPU Oryon 常驻 | 3–5 GiB | dense 骨干 + 中热专家 + 在算的冷专家 | 匿名，不可丢 | `cpu/expert.cpp` 冷路 |
| **L2** | UFS 4.1 / file-backed mmap | 5.06 GiB (T42) | 冷专家 | **干净页可直接丢弃** | SSD 层（Strata 那里只放 PLE 表） |

**硬件事实**：UFS 4.1 顺序读 4.3 GB/s、4K 随机 590K IOPS、**QD1 随机读 ≈100 µs**；
CPU = 2×Oryon Prime 4.6GHz + 6×Performance 3.62GHz，**无小核**，24MB 缓存，与 GPU 共享同一 LPDDR5X 单池。

**调度四件套**：
1. **热度表（离线）** —— 统计「每层 × 每专家」被选频率 → pin 优先级（对应 Strata expert-profile）
2. **per-layer 填充** —— 预算 ÷ 40 层 = 每层配额；3 GiB ⇒ 91 个/层 = 35.5%（Strata 实测该条把命中率 54%→99%）
3. **超集异步预读（最关键）** —— 绝不用 4KB 页故障；批量 `pread` / `MADV_WILLNEED`，**读 top-32 只用 top-8**
4. **预算切分** —— KV(0.65 GiB@64K) ↔ 专家热集（对应 strata-plan）

**核心风险**：216 页 × 100 µs = 21.6 ms。若按页故障触发，**一层命中一个冷专家就吃掉一整步**。

**关键洞察**：「dense 占 85%」在这里第一次变成**优势**——每层 GPU 算 attention 的时间足够长，
可以完整盖住下一层专家的 UFS 预读延迟。**方案成立的关键不是把专家塞进内存，而是让「必然要读的 dense」成为「冷专家的预读窗口」。**

## 5. 更低量化怎么做（FIG 6）—— 本版新增的核心答案

### 5.1 先找对目标：每 token 2304 MiB 的构成

| 组成块 | 精度 | MiB/token | 占比 | 能否再降 |
|---|---|---|---|---|
| attn / SSM 投影 | Q8_0 · 8.5 bpw | **1222** | 53% | ✅ 大幅 |
| lm_head | Q8_0 · 8.5 bpw | **600** | 26% | ✅ 大幅 |
| routed 专家 ×8 | T42 · 2.25 bpw | 274 | 12% | ❌ 已到底 |
| shared expert | Q8_0 | 128 | 6% | ✅ 可降 |
| norms | F32 | 80 | 4% | ❌ 不动 |

### 5.2 三条路径

**路径 A · dense 降比特 Q8_0 → Q4_0（配 imatrix）** — 省 **635 MiB**
- attn/SSM 1222→647、shared 128→68
- 风险**低**：Q4_0 上游标准，OpenCL 的 `MUL_MAT` 与 `MUL_MAT_ID` 都有内核；用 `llama-quantize --imatrix`
- ⚠️ **禁忌**：30 层 DeltaNet 的 `ssm_a` / `ssm_d` / `ssm_dt` 是**递推参数**，误差会逐 token 累积 ⇒ 用 `--tensor-type` 单独保留高精度

**路径 B · 词表子集 lm_head 248,320 → 64,000 行** — 省 **445 MiB**（再降 Q4_0 再省 73）
- 风险**中**：要裁剪工具 + 采样器映射；coupled sampling 的 Gumbel 键必须映射回全词表 id
- DGX 上已定为头号杠杆，可直接复用

**路径 C · 专家 2.25 → 1.75 bpw（三元）** — 只省 **61 MiB（总量 2.6%）**
- 代价：新格式 + 新内核 + 重做质量验证 + 工具链 ⇒ **明确不做**

**白捡 · token_embd BF16 → Q8_0** — 省 **0.5 GiB 内存**，**不省任何每 token 带宽**（每 token 只查 1 行 ≈4KB）
⇒ 省下的内存直接加进专家热集，覆盖率 35.5% → ~40%。**内存换带宽，纯赚。**

### 5.3 累计效果（45 GB/s 有效带宽）

| 阶段 | dense | 专家 | 合计/token | 单步 | 稳态吐字 |
|---|---|---|---|---|---|
| 现状 | 1950 | 274 | 2304 MiB | 53.7 ms | **18.6 t/s** |
| + 词表子集 64K | 1505 | 274 | 1859 MiB | 43.3 ms | **23.1 t/s** |
| + attn/SSM & shared → Q4_0 | 870 | 274 | 1224 MiB | 28.5 ms | **35.1 t/s** |
| + lm_head → Q4_0 | 797 | 274 | 1151 MiB | 26.8 ms | **37.3 t/s** |

**只做「dense 降 Q4_0」一步就 +52% 吐字**，零新内核、零额外存储压力。

### 5.4 专家要不要动？
- **默认不动**：2.25 bpw 同时满足「接近 2-bit 极限 / CPU 原生支持 / 无需自研 GPU 内核」
- 若一定要上 GPU：① 重打包 MXFP4（体积反涨到 15.9 GiB）② 为 T42 写 OpenCL `MUL_MAT_ID` 内核
  （可复用 PTQ1_0 经验，已知坑 `__constant` 变址错编；约 1–2 周）—— 只在「CPU 跑专家确实成瓶颈」时才做

## 6. 修订评级与路线（FIG 5）

**评级：中等**（上一版「中等偏高」下调）

| 等级 | 机制 |
|---|---|
| 低 | CPU 跑 MoE 专家 · 保持 T42 · **词表子集（升为头号）** |
| 中 | OpenCL 跑 dense 骨干 · UFS mmap 放冷专家 |
| 高 | 专家热集 pin + 层间异步预读（llama.cpp **无现成机制**） · GPU+CPU 双路真实收益 |
| 放弃 | Vulkan 路径 · GPU 直接跑 T42 专家 |

**落地顺序**：
- **P0 能力探测** —— 目标机跑 `test-backend-ops`，产出 OpenCL/Vulkan 的「类型 × 算子」白名单 + 实测有效带宽。**所有决策的输入。**
- **P1 双路骨架** —— 选 Q4_0/Q8_0 小 MoE 模型验「GPU dense + CPU MoE」；判据：CPU 侧耗时占比 < 55%
- **P2 专家分层** —— 热度表 + per-layer pin + 超集异步预读；判据：冷专家命中不产生可见 stall
- **P3 T42 CPU 内核** —— dequant + vec_dot（NEON/i8mm）
- **P4 上 35B** —— 扫热集预算 × 预读深度 × 线程数

**稳态预期**：乐观 **17–20 t/s**（热集覆盖 >35%、预读完全重叠）；悲观 **6–9 t/s**（UFS 随机读藏不住）。

## 7. 一句话总纲

> **手机的「更低量化」的正解是把 8.5 压到 4.5，而不是把 2.25 压到 1.75。
> 手机上「分层调度」的意义不是把模型塞进内存，而是让必然要读的 dense 成为冷专家的预读窗口。**
