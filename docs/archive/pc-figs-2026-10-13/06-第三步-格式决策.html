从内核白名单反推量化格式：GPU 上最小只能到 4.25 bpw

只要专家要在 GPU 上算（MUL_MAT_ID），可选格式就被 OpenCL 白名单锁死在 Q4_0 / Q8_0 / MXFP4（+ 一组 Adreno 形状受限的 K-quant）。 T42 的 2.25 bpw 在 GPU 上没有任何内核。这一张图决定「专家到底放哪算」。

重打包到 GPU 格式的代价：比想象小，但不在「吞吐」上

每 token 固定必读字节
T42 原样
2.25 GiB
重打包 Q4_0
2.52 GiB
紫 = dense（attn/SSM + lm_head + shared，1.90 GiB，不随格式变） ·  红 = routed 专家（0.27 → 0.54 GiB） ·  灰 = norms
代价其实很小
每 token 字节只从 2.25 → 2.52 GiB（+12%）
因为 dense 占 85%，专家翻倍被稀释掉了
→ 换算速度：18.6 → 17.5 t/s，几乎不影响
真正的代价在存储与调度
冷专家落 UFS 的体积：5.06 → 10.1 GiB
同容量热集能装的专家数腰斩：每层覆盖率 35.5% → 17.8%
而且要新写 T42 → MXFP4/Q4_0 的量化器（自研格式，无现成工具）
结论：双轨。 ① 骨干上 GPU——attention / SSM / lm_head 保持 Q8_0 原样（在 OpenCL 白名单内，体积不变，且这 1.90 GiB 占每 token 的 85%）。 这是「先能跑起来」的起点；下一步骤要做的「更低量化」见 FIG 6——把这一块从 Q8_0 压到 Q4_0； ② 专家留 T42 走 CPU——CPU 支持全部类型，体积不变，且不需要自研任何 GPU 内核。 这条路把「格式负债」限制在 一个 CPU vec_dot 内核上，而不是四个 GPU 后端内核。
保留的升级选项：若后续实测发现 CPU 跑专家是瓶颈，再把专家重打包成 MXFP4 交回 GPU—— 代价是体积翻倍 + 覆盖率腰斩，所以在被数据逼到之前不做。
