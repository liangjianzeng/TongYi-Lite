评级下调为 中等：风险从「硬件」搬到了「软件机制」

上一版给的是「中等偏高」，隐含假设是「手机 GPU 后端像 CUDA 一样听话」。 核实后端能力与架构差异后，这个假设不成立。但也要说清楚：下调的不是「能不能跑」，而是「跑多快、要多少工程量」。
1

风险分级（每条机制归位）

等级机制依据动作
低 CPU 跑 MoE 专家 llama.cpp 原生 split graph 就支持；只需补 T42 的 CPU dequant + vec_dot 直接做
低 保持 T42 格式不变 CPU 后端支持全部 GGML 类型，体积不翻倍 直接做
低 词表子集手术（lm_head 248K → 64K） 省 445 MiB，占每 token 约 15%；35B 的 dense 占比比 Flash 更极端 优先级升为头号
中 OpenCL 跑 dense 骨干（Q8_0） Q8_0 在白名单内；但 SSM / DeltaNet / flash-attn 的 OpenCL 覆盖需逐算子验证 P0 探测后定
中 UFS file-backed mmap 放冷专家 llama.cpp 原生 mmap 就有；缺的是 pin 与预读增强 P2
高 专家热集 pin + 层间异步预读 llama.cpp 没有任何现成机制（现有 -ot / --n-cpu-moe 粒度是「张量」和「整层」，拆不到单个专家）；手机端零先例 P2，最大不确定项
高 GPU + CPU 双路并行的真实收益 共享单池带宽，CPU 侧计算可能把 GPU 侧的带宽抢走，净收益可能远小于预期 P1 先量化
放弃 Vulkan 路径（原厂 / Turnip） 原厂端到端 0/6 通过；Turnip 三药后也只有 5–11 t/s 仅留作驱动更新后的复测项
放弃 GPU 直接跑 T42 专家 无内核；自研 GPU 内核 + Adreno 编译器已知错编风险 保留 CPU 路作为替代
2

落地顺序（每步都有证伪判据）

P0 · 能力探测

目标机跑 test-backend-ops，产出 OpenCL / Vulkan 的「类型 × 算子」白名单 + 实测有效带宽。

这是所有决策的输入，先做

P1 · 双路骨架

选一个 Q4_0/Q8_0 的小 MoE 模型，验「GPU dense + CPU MoE」的 split graph 真实行为，测两路耗时占比与带宽争抢。

判据：CPU 侧耗时占比 <55%

P2 · 专家分层

热度表 + per-layer pin + 超集异步预读。工程量最大的一步。

判据：冷专家命中不产生可见 stall

P3 · T42 CPU 内核

dequant + vec_dot（NEON / i8mm）。可直接复用 PTQ1_0 OpenCL 内核踩过的坑与验证方法。

P4 · 上 35B

扫热集预算 × 预读深度 × 线程数，找稳态最优。

REVISED VERDICT

可行性 中等——门控不在算力、不在带宽，而在 「冷专家不 stall」

乐观稳态 17–20 t/s（热集覆盖 >35%，且 UFS 预读与 dense 计算完全重叠）； 悲观 6–9 t/s（UFS 随机读藏不住，每次冷专家命中都 stall 一整步）。 两者之间没有中间态好猜——这正是 P0/P1 要先用很低成本量出来的东西。
