要压的不是专家，是 dense 的 Q8_0

直觉上「更低量化」＝把专家的 2.25 bpw 再往下压。但把每 token 的字节账摆开就会发现这条路是死的： 专家只占 12%，而占 85% 的 dense 权重用的却是 8.5 bpw 的 Q8_0。 唯一有 40% 以上下降空间的地方在那里——而且它全部落在 OpenCL 的内核白名单内，不需要写一行新内核。
降 dense · 省 635 MiB · 零新内核 词表子集 · 省 445 MiB · 需采样映射 专家再降 · 省 61 MiB · 投入产出最差

两条真正有效的路径，外加一个白捡

路径 A · dense 降比特：Q8_0 → Q4_0（必须配 imatrix 校准）
attn / SSM 投影 1222 → 647 MiB
shared expert 128 → 68 MiB
合计省 635 MiB，每 token 总量 −27%
风险 低：Q4_0 是上游标准格式，OpenCL 的 MUL_MAT 与 MUL_MAT_ID 都有内核
工具：llama-quantize + --imatrix（llama.cpp 原生，无需自研）
禁忌：30 层 DeltaNet 的 ssm_a / ssm_d / ssm_dt 是递推参数， 误差会逐 token 累积 ⇒ 必须用 --tensor-type 把这一组单独留在高精度
路径 B · 词表子集：lm_head 248,320 → 64,000 行
保持 Q8_0：600 → 155 MiB（省 445）
再降到 Q4_0：155 → 82 MiB（再省 73）
风险 中：需要裁剪工具 + 采样器映射表
注意：coupled sampling 的 Gumbel 键必须用映射回全词表的 id，否则接受率统计语义会变
DGX 上已定为头号杠杆，手机上是同一件事，可直接复用结论
白捡 · token_embd 从 BF16 降到 Q8_0
省 0.5 GiB 内存
不省任何每 token 带宽——每 token 只查 1 行（2048 × 2B ≈ 4 KB）
这正是「内存换带宽」的免费午餐：
省下的 0.5 GiB 直接加进专家热集，把每层覆盖率从 35.5% 推到 ~40%
在内存比带宽更紧的手机上，这笔兑换是纯赚

那专家到底还要不要动？

默认答案：不动，2.25 bpw 就是最优解

它同时满足三件事：① 体积已接近 2-bit 的实际极限；② CPU 后端原生支持该格式；③ 不需要任何自研 GPU 内核。 把它压到 1.75 bpw 省下的 61 MiB 换不来速度，只会带来质量风险与全套内核工作。

如果一定要让专家上 GPU（两条路，都不推荐先做）

路线 ①：重打包成 MXFP4 —— 体积反而从 8.44 涨到 15.9 GiB，热集覆盖率腰斩。

路线 ②：为 T42 写 OpenCL 的 MUL_MAT_ID 内核 —— 可复用本项目 PTQ1_0 内核的成功经验 （test-backend-ops 174/174 通过），已知坑是 Adreno 对 __constant 数组变址会错编，用三元表达式绕过。 工程量约 1–2 周，但只在「CPU 跑专家确实成为瓶颈」时才值得做。

ANSWER

把 8.5 压到 4.5，而不是把 2.25 压到 1.75

手机端的「更低量化」不是继续折磨那 12% 的专家，而是去动那 85% 的 dense 权重—— 它们是 Q8_0（8.5 bpw），是所有块里唯一还留着一半以上冗余的地方，而且目标格式 Q4_0 本来就在 OpenCL 白名单里。三步组合（词表子集 → attn/SSM 降 Q4_0 → lm_head 降 Q4_0） 把每 token 从 2304 MiB 压到 1151 MiB，吐字从 18.6 提到 37.3 t/s（2 倍）， 全程只用到 llama-quantize 与一个采样映射补丁。

dense Q8_0 → Q4_0 + imatrix（省 635 MiB）
第二优先
lm_head 词表子集 248K → 64K（省 445 MiB）
明确不做
