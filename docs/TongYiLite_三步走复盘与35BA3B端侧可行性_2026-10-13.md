# 三步走复盘 + Qwen3.6-35B-A3B 端侧可行性推演

**日期**：2026-10-13
**范围**：5060Ti 同构 fork（步骤一）→ DGX GB10 异构 ARM 统一内存（步骤二）→ TongYi-Lite 手机端（步骤三）
**第三步目标模型**：`D:\MyLLM\models\Qwen3.6-35B-A3B-GSQ\Qwen3.6-35B-A3B-GSQ-hybrid.gguf`（实读，非推测）

---

## 0. 一句话结论

**可行，但成立的形态不是"把 35B 装进 16GB"，而是"常驻小核 + 专家走闪存分层"。**

- 这个 GSQ-hybrid 实测 **11.368 GiB / 2.25 bpw**，权重本身就顶满 16GB 机的可用内存 ⇒ **全量常驻方案直接判死**。
- 但它的结构对手机**极度友好**：每 token 只激活 8/256 专家（0.856 MiB/专家）、30/40 层是 DeltaNet（KV 不随 ctx 增长）、只有 10 层全注意力且仅 2 个 KV head。
- ⇒ 常驻部分只需 **约 3.0 GiB**，routed expert 的 **8.56 GiB 里放 3~3.5 GiB 做热集、其余 5.06 GiB 落 UFS**，总内存账 **7.1–8.5 GiB**，16GB 机放得下。
- 稳态吐字预期 **12–20 t/s（保守，且此数已按"无投机"计）**，把词表手术 + attention 降比特做到位可上 **20–33 t/s**。
- **设计前提：原生推理，不做投机解码。** 端侧 MTP 是负收益（草稿税 > 接受率收益），该模型本身也没有草稿层——两者一致，视作前提而非缺憾。见 §4①。
- 两个真实拦路虎：**GSQ(T42) 在 Adreno 上没有反量化内核**、**手机端 llama.cpp 目前没有"专家分层 + 异步预取"这套机制**。

## 1. 三步走的实质：同一套机制，在三种内存环境里反复验真

| | 步骤一 同构 | 步骤二 异构 | 步骤三 端侧（计划） |
|---|---|---|---|
| 硬件 | RTX 5060 Ti 16G / 48G RAM / Windows | DGX Spark GB10 128G UMA / ARM64 | 8 Elite Gen 5 / 16G LPDDR5X / Adreno |
| 对象 | Qwen3.8-Flash-Next 125B（GSQ IQ3_XXS） | 同左 + Strata 引擎 ARM64 移植 | **Qwen3.6-35B-A3B GSQ-hybrid** |
| 手段 | llama.cpp fork `strata-like` 复刻 Strata 机制 | llama.cpp fork + Strata 移植 + nsys/ncu profile | llama.cpp 手机端 + 端侧内核 |
| 得到的原理 | **prefill 瓶颈是"窗口内专家重拷贝次数"（ub 512→2048 得 3.15×）；MTP 深草稿 n_max=4 被硬截是白送的提速（0.87 接受率可撑到 8 步）；16G 小卡上"专家热缓存"无效（3G 缓存 vs 40G 专家）** | **统一内存下"内存分层/换入换出/DMA 流水/pinned 池"整类机制失去作用对象（专家全常驻）；真正杠杆只剩"每 token 少读字节"；零拷贝直读是对的（host 映射读 ≈225 GB/s ≈ 设备的 90%），真正的窄口是拷贝引擎（H2D 50 / D2H 30 GB/s）；瓶颈是 kernel 粒度与并行度，不是带宽** | **待验：在"内存真的不够"的设备上，分层机制第一次有了作用对象——步骤二被证伪的那批机制，在这里集体复活** |
| 留下的资产 | fork 分支、ub/n_max 定案、GGUF 字节手术规则、单实例测试器 | ARM64 移植补丁五件套、Strata rt 转换链、nsys/ncu 权限解法、membw 探针 | 复用步骤一/二：**架构同族 ⇒ 内核与调度经验可直接搬运** |

**这三步不是三条平行的线，是一条螺旋**：
- 步骤一证明了"机制缺位 = 性能差距"（同机同模型，Strata 引擎 pp 1311 / tg 61-68 vs 本 fork pp ~250 / tg ~38，"硬件墙"假说破产）。
- 步骤二反过来证明了"机制用错场景 = 白干"（把 5060Ti 的 PCIe 分层机制搬到 UMA 上，一个字节都省不下来）。
- 步骤三正好落在两者之间：**手机的内存比 5060Ti 还紧，所以分层机制第一次真正有用；但手机的"搬运"代价（UFS 随机读）比 PCIe 更贵，所以分层必须配异步预取，而不能靠内核页故障兜底。**

## 3. 可行性定量推演

### 3.1 带宽账：每 token 必读多少字节

decode 单 token，权重只读一遍（理想）：

| 项 | MiB | 说明 |
|---|---|---|
| attn / SSM（dense, Q8_0） | **1222** | 每 token 全读，最大单块 |
| lm_head `output.weight`（Q8_0） | **600** | 全词表 248,320，每 token 必读 |
| routed expert 8/256（T42 2.25bpw） | **274** | 8 × 0.856 × 40 层 |
| shared expert（Q8_0） | **128** | 每 token 全读 |
| norms / router（F32） | 80 | |
| token_embd（BF16） | ~0 | 只读 1 行（4 KB） |
| **合计** | **≈ 2304 MiB = 2.25 GiB = 2.42 GB** | |

手机侧带宽（8 Elite Gen 5：LPDDR5X-5300、4×16-bit、**峰值 84.8 GB/s**）：

| 有效带宽 | ms/token | t/s |
|---|---|---|
| 30 GB/s（悲观 35%） | 80.6 | **12.4** |
| 45 GB/s（53%） | 53.8 | **18.6** |
| 60 GB/s（71%） | 40.3 | **24.8** |

**注意这个账的形态**：dense 权重（attn 1222 + lm_head 600 + shared 128 = 1950 MiB）占了 **85%**，而全部 routed expert 只占 274 MiB（12%）。
⇒ 与 DGX 上 Flash 的构成（decode 单步必读 ≈1.6 GiB：**MoE 69% / KV 26% / attn 4%**）完全不同；**手机上第一瓶颈是 dense 权重，尤其是 lm_head**。

> ⚠️ **本文档已被修订**：见 `35BA3B端侧方案_修订版_2026-10-13.md`（+ `docs/figs/` 三步走合订 9 张图）。
> 三处结论级修正：① 「T42 → 重打包 IQ2_S」**错**（OpenCL 的 MUL_MAT_ID 通用只支持 Q4_0/Q8_0/MXFP4，IQ 家族缺席）；
> ② 手机可用 GPU 路径实际**只有 OpenCL**（原厂 Vulkan e2e 0/6、Turnip 三药后 5–11 t/s）；
> ③ 可行性由「中等偏高」**下调为「中等」**。新增核心答案：**更低量化应压 dense 的 8.5 bpw，而不是专家的 2.25 bpw**。

### 3.2 优化后的账

| 杠杆 | 省 | 依据 |
|---|---|---|
| lm_head 词表子集（248K → 64K + 采样映射） | −445 MiB | DGX 上已定为头号杠杆；手机上占比更极端 |
| attn/SSM Q8_0 → Q4_0 重打包 | −582 MiB | 纯 dense，精度敏感度低 |
| （可选）shared expert 也降比特 | −60 MiB | |
| **合计** | **≈ 1280 MiB = 1.34 GB** | |

⇒ 45 GB/s 下 **29.8 ms/token ≈ 33.6 t/s**（理论上界）。
**保守定档：稳态 12–20 t/s；优化到位 20–30 t/s。**

### 3.3 内存账（16GB 机）

| 项 | GiB |
|---|---|
| attn/SSM Q8_0 常驻 | 1.19 |
| token_embd BF16（mmap 页缓存） | 0.95 |
| lm_head Q8_0（子集化后 0.15） | 0.59 / 0.15 |
| shared expert | 0.13 |
| norms / other | 0.08 |
| **routed expert 热集常驻** | **3.0 – 3.5（可调）** |
| KV @64K（10 层 × 2 KV-head × 256 × 2 × 1.0625 B） | **0.65** |
| 计算缓冲 + graph + 碎片 | 0.5 – 0.8 |
| **合计** | **7.1 – 8.5 GiB** |
| 剩余 routed expert 落 UFS mmap | **5.06 GiB** |

16GB 机 Android 系统占 ~2.5–3.5 GB ⇒ 应用可用 ~10–11 GiB ⇒ **放得下，余量 2–4 GiB**。

**KV 这一项是本模型最大的隐藏红利**：40 层里只有 10 层需要 KV，且仅 2 个 KV-head ⇒ **10.9 KB/token**，64K ctx 只要 0.65 GiB（262K 也才 2.79 GiB）。30 层 DeltaNet 的状态是固定大小、不随 ctx 增长。**"长上下文在手机上不可行"这条老结论，被混合架构直接推翻了。**

### 3.4 prefill 账（真正的风险点）

prefill 每 ubatch 要把该批激活到的专家全部读一遍，unique 专家数随 batch 亚线性增长：

| ubatch | unique 专家估算 | 需读专家字节 | UFS 冷部分（约 60%） | 若 2 GB/s |
|---|---|---|---|---|
| 32 | ~0.9 × 256 | 7.7 GiB / 32 tok = 246 MiB/tok | — | **极差** |
| 512 | ~200 / 256 | 6.6 GiB / 512 tok = 13.2 MiB/tok | ~4.0 GiB | 2.0 s ⇒ 256 t/s |
| 2048 | ~240 / 256 | 7.9 GiB / 2048 tok = 3.9 MiB/tok | ~4.7 GiB | 2.4 s ⇒ 850 t/s |

⇒ **prefill 必须走大 ubatch**（与步骤一在 5060Ti 上"ub 512→2048 得 3.15×"是同一条原理，只是原因从"重拷贝"换成"重读闪存"）。
⇒ 1K prompt TTFT 约 **1.3–3 秒**；10K prompt 约 12–30 秒。**能接受，但不惊艳，且强依赖预取质量。**

## 4. 设计前提 + 两个真实拦路虎

### 前提 · 原生推理，不做投机解码

**端侧 MTP/dspark 是负收益，已被实践否掉，不再列为候选。** 理由与 DGX 侧的经验正好相反，要分清：

| | DGX GB10（步骤二） | 手机 16G（步骤三） |
|---|---|---|
| 草稿权重常驻成本 | +2.2 GB（MTP Q4_0）/ 128G 无所谓 | +0.5–1.5 GB **/ 10–11 GB 可用，占 5–15%** |
| 每轮草稿税 | 9.7–12.0 ms（实测） | 按草稿自身字节读 + Adreno GEMV 效率外推，**25–40 ms** |
| 接受率（temp>0） | mean acc len 2.43–2.60，coupled 后 +7% | 显著更低（更小更弱的草稿） |
| 结论 | **1.6–2.2×，必须开** | **草稿税 > 收益，关掉** |

⇒ 两者不矛盾：DGX 上"草稿读取几乎免费、验证批还能摊薄权重"，手机上没有一样成立。**这是同一个机制在不同字节成本下的符号翻转。**

**"无投机"反而是手机的三个红利，应该主动利用：**

1. **形状固定**：decode 恒为 M=1、单序列。Vulkan 上可预编译固定 shape 的 pipeline（specialization constants），命令缓冲可复用——**这正是 DGX 上 MMVQ `switch(ncols_dst) case 1..8` + `MMVQ_MAX_BATCH_SIZE=8` 那套模板地狱的完全回避**。
2. **无草稿权重常驻**：省下的 0.5–1.5 GB 直接加进专家热集，命中率上升，平均延迟下降。
3. **唯一杠杆收敛到"每 token 少读字节"** —— 与步骤二在 DGX 上得到的结论**完全一致**（"UMA 下真正的杠杆是每 token 少读字节，不是更聪明的缓存调度"）。两端的优化方向第一次指向同一个点。

⇒ 因此 §3.1 的 **2.42 GB/token 就是真基线**，不需要再乘任何投机系数；§3.2 的字节削减就是**唯一**的性能路线。

### 拦路虎 A · GSQ(T42) 在手机上没有任何内核
2.250 bpw 的 T42 是自研类型，Adreno 的 Vulkan/OpenCL 后端不认识。两条路：
- **A（自研内核）**：照我们写 PTQ1_0 OpenCL 内核的老路，给 T42 写 dequant-GEMV + 对应 mul_mm。工程量中等（有先例，但 Adreno 825/840 的编译器坑要重新趟）。
- **B（改回上游类型）**：重打包成上游已有的 **IQ2_S / IQ2_XXS**（Vulkan 有内核）。代价：体积涨 ~0.3–0.6 GiB，2.25 → 2.06/2.5 bpw 之间有质量取舍。**推荐 B 作为第一版，A 作为后续优化。**

（附带说明：免训练投机路径 ngram / lookup / suffix-draft 在手机上同样不必指望——DGX 实测 `ngram-mod` 命中率仅 1.3%，只能算"免费但不中"；手机上草稿开销更贵，更不划算。）

### 拦路虎 B · 手机端 llama.cpp 目前没有"专家分层 + 异步预取"
现有 `assets/models_catalog.json` 最大的条目是 5.95 GB（Ternary-Bonsai-2-27B PTQ1_0，minRAM 16GB），**全是全量常驻**。而 35B-A3B 要求：
- 专家级 **pin 住热集**（mlock / 常驻缓冲池）
- **知道下一层要哪些专家 → 提前 `posix_fadvise`/异步读**（这一步是关键，纯靠内核 4KB 页故障会被随机读延迟打死）
- KV 与热集之间的**预算切换**（对应 Strata 的 per-layer 填充策略）

**这三点就是第三步的主体工程量，也正是步骤一/二把机制摸透之后才具备的移植能力。**

## 5. 与 DGX 经验的反转表（最重要的一张表）

| 机制 | 5060Ti 16G（步骤一） | DGX 128G UMA（步骤二） | 手机 16G（步骤三） |
|---|---|---|---|
| 专家热缓存 / 分层 | ❌ 无效（3G vs 40G 专家，命中≈0） | ❌ **无对象**（专家全常驻） | ✅ **主杠杆**（5.06 GiB 必须落闪存） |
| 按字节定额的预取环 | 判死（慢 8 倍） | ❌ 无对象 | ✅ **必需**（否则随机读延迟吃掉一切） |
| 零拷贝 / mmap 直读 | PCIe 上慢 | ✅ 反转后成立（≈225 GB/s） | ✅ 成立且**额外好处**：file-backed 干净页可被 LMKD 回收，不易被杀 |
| prefill 大分块 | ✅ ub 2048（3.15×） | ✅ 8192 | ⚠️ 受限但仍是正解（受 UFS 带宽约束） |
| 投机解码 | ✅ MTP n_max 8 | ✅ MTP 1.6–2.2× | ❌ **主动关闭**（前提；草稿税 > 收益，且模型无草稿层）|
| 词表子集手术 | 未做 | ✅ 头号杠杆（+6%） | ✅✅ **第一优先**（每 token 600 MiB） |
| KV 量化 | 必要 | 次要（KV 本来就读得少） | ✅ 极大红利（混合架构 ⇒ 10.9 KB/token） |
| 编译档位 / 调参 | 中性 | 中性（±0.4%） | 待测（Adreno 上不算中性） |

**一句话**：步骤二花大力气证伪的那批"分层调度机制"，在步骤三的设备上**全部复活**——因为只有在"内存真的不够"的地方，它们才有作用对象。

## 6. 判定与分级目标

| 目标 | 判定 | 依据 |
|---|---|---|
| 能加载并跑起来 | ✅ **可行** | 内存账 7.1–8.5 GiB < 可用 10–11 GiB |
| 能稳态吐字 | ✅ **可行**，12–20 t/s（保守） | 带宽账 2.42 GB/token ÷ 45 GB/s |
| 体验舒适（>20 t/s） | ⚠️ **条件达成** | 需 词表手术 + attn 降比特 + 高命中率热集 |
| 长上下文（64K+） | ✅ **意外地可行** | 混合架构 KV 只 0.65 GiB |
| 智能体 / 工具调用质量 | ⚠️ **有风险** | 2.25 bpw + 我们既有结论"工具调用对量化格式高度敏感"（UD-IQ3_XXS 行、froggeric IQ3_M 不行）|
| 首 token 延迟 | ⚠️ **是短板** | 1K≈1.3–3 s，10K≈12–30 s，全靠预取质量 |

## 7. 建议的落地顺序（最小验证 → 放大）

**不要一上来就上 35B。** 先用同族的"缩小版 MoE"把机制验通：

| 阶段 | 做什么 | 成功判据 |
|---|---|---|
| **P0 测基线带宽** | 在 8 Elite Gen 5 真机跑现有模型（Qwen3.5-9B / Bonsai-2），用 Vulkan 与 OpenCL 两条后端测 **有效带宽占峰值比** | 拿到"有效 GB/s"这个除数，整个可行性模型才能定量 |
| **P1 代理实验** | 用 catalog 里已有的 **`lfm2.5-8b-a1b-ud-iq3_xxs`（3.05 GB，MoE A1B）** 做"专家 mmap 流式 + 热集 pin + 层间预取" | **A1B 是 A3B 的天然缩比代理**；能跑到 20+ t/s 则 35B-A3B 可外推 |
| **P2 内核** | T42/GSQ → IQ2_S 重打包（或写 Adreno 反量化内核） | 加载成功 + 数值一致 + GEMV 达到带宽账预期 |
| **P3 上 35B** | 热集预算扫描（3.0/3.5/4.0 GiB）× ubatch 扫描 × 预取深度 | 稳态 t/s + TTFT + 内存余量三指标达标 |

**P1 是被严重低估的一步**：`lfm2.5-8b-a1b` 与 35B-A3B 是同一族（MoE + 小激活参数），但只有 3.05 GB——它能在 16GB 机上**同时验证"常驻"与"流式"两种模式**，用很小的代价把第三步的全部机制风险前置暴露。

---

## 8. 结论

**可预期可行性：中等偏高，但要把目标从"跑 35B"改成"跑 35B 的常驻核 + 闪存专家"。**

- t/s 不是主要矛盾（2.42 GB/token 在 45 GB/s 上就是 18.6 t/s，中文约 12 字/秒，可读）。**这个数字已经是在"完全不投机"的前提下算的**，不需要再打折。
- **内存容量才是**，而容量问题恰好由这个模型的三个结构特征（top-8/256、30 层线性注意力、10.9 KB/token 的 KV）大幅缓解。
- **"不做投机"不是退让，是把问题空间砍到只剩一个变量**：每 token 读多少字节 + 这些字节里有多少必须从闪存来。所有优化手段都归到这两项上，可测、可归因、无耦合——比 DGX 上"投机收益与草稿税纠缠不清"的状态干净得多。
- 真正的未知数只有三个：**Adreno 的有效带宽**、**UFS 冷读的延迟隐藏能力**、**T42 内核**。这三个都能用 P0/P1 在很低的成本上先量出来。
- 而那套"分层 + 预取 + 热集"的机制原理，**我们已经在两个截然不同的硬件上各验证过一次它该用在哪、不该用在哪**——这正是第三步最大的底气。
