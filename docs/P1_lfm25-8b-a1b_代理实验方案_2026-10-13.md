# P1 代理实验方案：LFM2.5-8B-A1B 作为 35B-A3B 缩比代理

> ⚠️ **2026-10-13 晚调整（联网查证后定案）**：P1 代理主对象为 **Ling3.0-tiny**（官方规格：7.9B 总参 / **1.3B 激活 MoE**，128 路由专家 top-8 + 1 共享，3:1 KDA+MLA 混合线性注意力；官方 BF16/FP8/INT4）。量化路线为 **Q4_K_M 先通**（OpenCL 白名单内 + dense loop MoE，零自研）→ 再调 IQ2/Q2 自研内核。本文档降级为**备选对照方案**保留，其中「热集 pin ~34% 模拟 35B 失真」「页故障代价推演」等机制设计原则对 Ling3.0-tiny 同样适用。

> 2026-10-13 · 承接《35BA3B端侧方案_修订版_2026-10-13.md》的 P1 阶段
> 对象：catalog 条目 `lfm2.5-8b-a1b-ud-iq3_xxs`（unsloth GGUF 3120.7 MB）
> 结论先行：**能当代理，但 UD-IQ3_XXS 这个量化包只够验"CPU 流式"一半，OpenCL 一半要靠同仓现成的 MXFP4_MOE pack；且热集覆盖率天然 100%，分层机制必须人为预算模拟才有作用对象。**

## 1. 模型解剖（公开配置，GGUF 实读待 P1.0 核对）

| 项 | 值 | 备注 |
|---|---|---|
| 架构 | `lfm2moe`（vendored b11267 已支持，`src/models/lfm2moe.cpp` 实证） | |
| 规模 | 8.3B total / 1.5B active | 文件实测参数 8.47B |
| 层数 | 24 = 18 double-gated conv-L（内部 cache=3）+ 6 GQA | 另一来源写 19+5，以实读为准 |
| MoE | 前 2 层 dense，其余 22 层 MoE：**32 专家 / top-4** | expert FFN 1792，hidden 2048 |
| 注意力 | 32 Q / 8 KV head，RoPE 5M | |
| 词表 | 128,000（**tied embedding**） | |
| ctx | 128K（native） | |
| 草稿 | 官方 DSpark 328M，~2.5× | **端侧规则：不用** |
| llama.cpp 生态 | day-one 支持；M5 Max 253 t/s、Ryzen AI Max+ 395 CPU 146 t/s、内存 <6 GB | |

**推导账目**（等 P1.0 实读核对）：
- 单专家参数 = gate_up(2×1792×2048) + down(1792×2048) = 3×1792×2048 ≈ **11.0 M ≈ 4.55 MiB @IQ3_XXS(≈3.3bpw)**
- 专家参数总量 ≈ 22 层 × 32 × 11.0M ≈ **7.74B ⇒ 91% 的参数在专家里**（比 35B 的 75% 更极端）
- 每 token 专家读 = 22 层 × top-4 × 4.55 MiB ≈ **400 MiB**（35B 只有 274 MiB ⇒ **代理对流式路径的压力反而更大 1.5×，是好性质**）
- 每 token 总读（IQ3_XXS）≈ dense ~0.7 GB + 专家 400 MiB ≈ **1.1 GB/token** ⇒ 45 GB/s 有效带宽下上限 ~25 t/s；换 Q4_0 专家 ≈ 545 MiB ⇒ ~1.3 GB/token ⇒ ~36 t/s 上限

## 2. 代理适配度评估（核心表）

| 指标 | LFM2.5-A1B | 35B-A3B | 判定 |
|---|---|---|---|
| 每 token 专家读 | ~400 MiB | 274 MiB | ✅ 更狠，流式压力足够 |
| 单专家体积 | ~4.5 MiB（~1100 个 4K 页） | 0.856 MiB（216 页） | ✅ 页故障代价更极端（110µs×页数更高），逼出"必须预读"的结论 |
| 每层专家数 / 激活比 | 32 / top-4（12.5%） | 256 / top-8（3.1%） | ⚠️ 稀疏度差 4×，路由热度分布形态不同 |
| **热集覆盖率（3 GiB 预算）** | **全模型才 3.05 GB ⇒ ~100%** | **35.5%** | ❌ **最大失真：常驻跑 = 分层机制无对象（DGX 悲剧重演）** |
| 每 token 构成 | dense:MoE ≈ 65:35 | 85:12 | ⚠️ 不同但同量级，结论方向可迁移 |
| KV/token | ~24.6 KB（f16，6 层×8KV×128） | 10.9 KB | ✅ 都是混合架构红利，长 ctx 都可行 |
| 词表 | 128K tied | 248K untied | ⚠️ 词表手术只能缩比验证 |
| 算子族 | conv-L + GQA | **DeltaNet** + GQA | ❌ GDN/SSM scan 算子验不了（要靠 Qwen3.5 系列） |

**结论：三条能验、两条验不了、一条要人为造条件。**
- ✅ 直接验：① decode 有效带宽（兼 P0 探针）② GPU dense + CPU/GPU MoE 分图 ③ 低 bpw 工具调用质量（LFM2.5 原生 JSON tool-call，app 已有 prompt_json_protocol 支持，顺带测 35B §6 的"工具调用对量化敏感"风险）
- ❌ 验不了：DeltaNet 算子、248K 词表手术全量效果
- ⚠️ 须造条件：**专家分层**——必须人为把热集预算压到 ~34%（22 层 × pin 11/32 专家 ≈ 1.1 GB），其余强制逐出 UFS，才能复现 35B 的 35.5% 覆盖率场景。否则模型全常驻，测出来的"分层收益"是假的。

## 3. 量化格式决策（本方案第一修正）

**UD-IQ3_XXS 是 IQ 家族 ⇒ OpenCL 的 MUL_MAT 与 MUL_MAT_ID 双双无内核（白名单只有 iq4_nl 一个 IQ 成员）⇒ 这个包在手机上只能全程 CPU。**

| 包 | 体积 | 专家格式 | 手机用途 |
|---|---|---|---|
| UD-IQ3_XXS（catalog 现有） | 3.05 GB | IQ3_XXS（CPU-only） | ✅ CPU 流式/分层模拟实验底座 |
| **MXFP4_MOE（unsloth 现成，新发现）** | 5.1 GB | **MXFP4 = OpenCL MUL_MAT_ID 白名单内** | ✅ **零重打包直接验「OpenCL dense + MoE」分图** |
| （可选）自建对齐包 | ~3.5 GB | dense Q4_0 + 专家 Q4_0 | 完全复刻 35B 目标形态；等前两个包跑通再说 |

⇒ **建议双包并行**：先用现成的两个包把两条路都验通，自建包降为可选项。这比原计划"先重打包"省一整步工程。

## 4. 实验矩阵

| 步骤 | 内容 | 成功判据 |
|---|---|---|
| **P1.0 实读核对** | 下载 UD-IQ3_XXS + MXFP4_MOE；用 `_probe/gguf_inspect_35b.py` 改版实读两张量谱（层数/专家数/单专家字节/量化构成），校准 §1 推导账 | 账目对上 ±10%，否则改判据 |
| **P1.1 CPU 基线** | 手机 CPU-only 解码 IQ3_XXS 包，变长 prompt，记录 t/s / 内存 | 实测 t/s ÷ 已知每 token 字节 = **Adreno 有效带宽**（一份账当 P0 的除数用） |
| **P1.2 OpenCL 分图** | MXFP4_MOE 包，GPU dense + MoE 路径，跑 `test-backend-ops` 先验白名单 | 加载成功 + 数值一致；**CPU 侧耗时占比 < 55%**（修订版 P1 判据） |
| **P1.3 分层模拟** | IQ3_XXS 包，人为 pin ~34% 专家/层，其余 MADV_DONTNEED 走 UFS；A/B：纯页故障 vs `pread` 超集异步预读（读 top-16 用 top-4） | **冷专家命中无可感知 stall**（单步增量 < 10 ms）；预读版显著优于页故障版 |
| **P1.4 热度表** | 真实对话样本统计每层×每专家路由频率 → 验证"热度集中度"假设（修订版 §2 遗留问题） | 拿到 top-11/32 覆盖率曲线，直接外推 35B 的 91/256 |
| **P1.5 质量抽测** | IQ3_XXS vs MXFP4_MOE vs Q8_0，工具调用/中文生成各 20 例 | 为 35B 的"专家留在 2.25bpw CPU"决策提供同型证据 |

## 5. 代理本身的优化清单（按杠杆排序）

1. **有效带宽是第一产出**——P1.1 的除数直接决定 35B 全部推算的可信度，变长 prompt（512/4K/32K）各测。
2. **预读窗口利用**：LFM2.5 的 conv 层计算量小、attention 只有 6 层 ⇒ "attention 时间盖预读"的洞察在此模型上**更难成立**；若 P1.3 仍能藏住延迟，35B 只会更稳（保守侧外推）。
3. 词表子集 128K→64K（tied，embd+lm_head 同省，约 −80~120 MB/token 相关字节）：小杠杆，但可把手术工具链先跑一遍。
4. KV f16→q8_0：6 层 GQA 收益小，顺手做。
5. n_threads 沿用 hc/2、n_ubatch 沿用 512 起步；**不要**在代理上花时间调编译档位（DGX 已证中性）。
6. ❌ 明确不做：DSpark 草稿（端侧投机规则）、专家降到 1.75bpw、为 IQ3_XXS 写 OpenCL 内核（IQ 家族被判死，工程投给 T42 才有意义）。

## 6. 外推规则（P1 → P4）

| 从代理测得 | 外推到 35B |
|---|---|
| Adreno 有效带宽 GB/s | 直接代入 2.25 GiB/token（优化后 1.22 GiB）账 |
| 冷专家 stall（有/无预读） | 单专家页数比 1100:216，按比例放大；预读窗口按 35B 的 dense 85% 重算（更宽松） |
| 热度集中度曲线 | per-layer pin 配额从 91/256 修正 |
| CPU MoE 耗时占比 | 决定 35B 专家留 CPU（T42）还是必须上 GPU 内核 |

---

## 7. 一句话总纲

> **lfm2.5-8b-a1b 是合格的"机制压力测试件"（专家读压力比 35B 还大 1.5×），但不是"天然缩比件"——覆盖率 100% vs 35.5% 的失真必须靠人为预算模拟抹平；量化包选型要从 IQ3_XXS 单包改为 IQ3_XXS（CPU 流式）+ MXFP4_MOE（OpenCL 分图）双包。**
