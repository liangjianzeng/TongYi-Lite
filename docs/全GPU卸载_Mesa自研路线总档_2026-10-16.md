## 1. 背景与问题定义

### 1.1 目标

TongYi-Lite（Flutter Android 离线 AI 助手，JNI 直调 llama.cpp）在骁龙旗舰机（Adreno 830 / SM8735 后继代）上跑 MoE 大模型（MiniCPM-V4.7-35B-A3B 拆分版，dense 权重常驻 + 专家流式供给）。当前生产配置为 **CPU bank + LES 前瞻专家调度**，本档回答一个问题：

> **decode 全 GPU 卸载并做到极致，能不能赢 CPU？需要自研什么、已有什么、还差什么、怎么干、风险在哪。**

### 1.2 为什么 CPU 混合现在守擂

decode 的计算形态 = 每 token ~4000 个小算子串行执行（40 层 × ~100 ops，几乎全是 GEMV）。llama.cpp 规则是**一个 ggml 算子 = 一次 kernel 提交**，decode 时单个算子工作量仅几微秒。这是通用图形态，不是 MiniCPM 特意切小的——任何模型在任何后端跑 llama.cpp decode 都长这样。

各家后端面对这 4000 次串行提交的代价完全不同：

| 后端 | 提交代价（单 op） | 应对 | 结果 |
|---|---|---|---|
| CPU | ≈0.34µs（函数调用进 SIMD） | 无需应对 | **我们 CPU 混合赢** |
| CUDA（DGX 8086） | 几十 µs | CUDA Graph 整图一次提交 | 理论地板 7-9ms vs 实测 52.9ms（我们在 GB10 上实测过同一堵墙） |
| Metal（Apple） | ~10-30µs + 单 command buffer 整图收编 | M 系列天然优势 | MiniCPM 官方 iPhone 13+ t/s |
| Adreno OpenCL | **9.04µs（probe9 实测）** | llama.cpp 无 graph 机制，驱动不暴露 command buffer | 全行业 Android LLM 方案纯 CPU |

MiniCPM-V 4.7 官方 Android App（OpenBMB/MiniCPM-V-Apps）**就是纯 CPU，零 GPU 代码路径**（实读过其 CMakeLists，一行 OpenCL/Vulkan 都没有）。Qualcomm 生态下没人付得起 decode 小 kernel 串行税，这是行业现状，不是我们做得差。

### 1.3 两条被否决的路（记录在案，不再回头）

| 路线 | 实测 | 否决原因 |
|---|---|---|
| 反编译高通闭源驱动解锁 command buffer | — | 扩展是**功能缺失**不是开关隐藏；command buffer 编译器根本没写，需在闭源代码里凭空造子系统；法律风险（仅豁免互操作必需研究，分发违法）；**且天花板仍只有持平 CPU** |
| Turnip Vulkan（Mesa 合法逆向成品，天然单提交） | 825 上 5-11 t/s，已弃用 | 提交税在 Turnip 上已解决，输在内核质量：llama.cpp Vulkan shader 未经 Adreno 调优 + vendor Vulkan 驱动 e2e 0/6 全错 |

**推论**：单提交模式本身不是银弹，内核质量才是同权重的胜负手。这决定了 Mesa 路线必须带着自研内核一起走。

## 2. 双机真机现状（全部实测）

统一协议：minicpm_e2e，48 token decode，冷启动含 prefill，交错 A/B，90s 冷却。

### 2.1 830（100.75.247.55:5555 无线，Adreno 830）— 主战场

| 配置 | decode t/s | prefill | SCHED_STATS（每 token） |
|---|---|---|---|
| **CPU bank（生产基线）** | **7.05 / 7.70（新库）→ 8.07（新高）** | 5.9-7.7s | 全 CPU，无 split |
| GPU bank route0（LLAMA_MOE_UPLOAD=0） | 3.97 / 5.46 / 4.12 | ~11s | 161 splits + 200 copies（OC 1240 / CPU 2743） |
| ngl=99 dense 全 GPU（830 首测） | 5.27 / 5.29 / 5.32 | ~10.8s | 203 splits + **378 copies**（OC 3391 / CPU 592） |
| GPU bank + ngl=99 全合体（830 首测） | 3.58 / 4.66 / 3.55 | 14.5s ← 最差 | 仍 203 splits + 338 copies（OC 3551 / CPU 432） |
| **x7 全图收编修复后** | 4.23 / 4.30 | — | **83 splits + 128 copies（OC 3941 / CPU 42）** |

12 腿全部 EXIT=0（race fix 后新库稳定）。

### 2.2 740（98fc9410，Adreno 740）— 对照机

| 配置 | decode t/s | prefill |
|---|---|---|
| CPU bank（生产基线，新库无回归） | **2.57 / 2.50** | 15.4 / 18.3s |
| GPU bank route0（最优） | 1.68 / 1.40 | 29.7 / 32.0s |
| GPU bank route1（staging+async drain） | 1.26 / 1.08 | ~38s |
| ngl=99 | 1.60-1.71 | —（基线 3.82） |

740 结论：GPU 路径结构性出局（161 splits + 200 copies 税 200-300ms 主导），生产 = CPU bank + LES，热稳态 3.0-3.4 t/s。**a8x 收窄后 740 仅作回归对照，不再投入。**

### 2.3 关键定性

- **830 CPU 是真快**：dotprod/i8mm 的 dense GEMV 本来就强，8.07 t/s 已是 740 的 3 倍，接近"够用"线。
- GPU 三条路（GPU bank / ngl=99 / 全合体）在两台机器上全输，且"全合体"最差——证明问题不在某个 kernel，在**图被劈开**（split/copy 税）+ **小算子内核速度**，双重结构病。

## 3. 先天短腿五条（机制 + 证据）

### 短腿① 无 command buffer → 提交税 36ms/token

- **证据**：probe9 在 830 上 dlopen libOpenCL 枚举设备扩展：`cl_khr_command_buffer = NO`、`cl_arm_command_buffer = NO`（Mali 阵营有 ARM 版，Adreno 不给）。
- **机制**：OpenCL 每 op 走完整提交链 `clEnqueue → 驱动校验 → 打包命令流 → 敲门铃`，实测斜率 **9.04µs/op**（K=1 单图固定开销另加 65.6µs）；CPU 同图仅 0.34µs/op。3941 ops × 9.04µs ≈ **36ms/token 纯提交税**。
- **历史勘误**：早期记录的"150-220µs 提交税"是误记——那实际是跨后端 split+copy 的混合成本，per-op 提交本身只有 9µs。
- **注**：probe9 的扩展 dump 只见到 `cl_khr_icd` + `cl_qcom_subgroup_shuffle`，疑似被 opencl_stub 截断，M0 阶段应复核完整扩展串（重点找 `cl_qcom_*` 私有 command buffer 类扩展，概率低但查一次便宜）。

### 短腿② 小算子 GPU 内核慢

- **证据**：x7 全图收编后（splits 203→83、copies 338→128、CPU ops 432→42），税已砍到只剩 launch 税，t/s 仍只有 4.30 vs CPU 8.07。
- **机制**：RMS_NORM / SSM_CONV / 微 GEMV 等 3µs 级算子，GPU 上单跑不过 CPU 的 SIMD 循环；3941 ops 的 GPU 执行时间本身 ~150ms，比 CPU 全图 ~124ms 还慢。
- **对策归属**：M3 链融合（只有把几十个小算子熔成大 kernel 才翻盘）。

### 短腿③ 混合图结构税（splits + 跨后端拷贝）

- **证据**：ngl=99 时 203 splits + 378 copies/token（拷贝税 ~60ms，正好对上 7.4→5.3 的差距）；GPU bank 161 splits + 200 copies；全合体最差（残留 432 CPU ops 继续制造全量 split + FGSVM 反噬）。
- **机制**：图一旦劈成两个后端，每个 split 边界都要跨后端拷贝 input tensor，Adreno 提交税放大拷贝成本。
- **已部分收编**（见 §4 资产五）：CPU ops 432→42 后 splits 203→83、copies 338→128。

### 短腿④ 黑盒编译器不可靠（E031）

- **实锤案例（batched MUL_MAT_ID q4_K，MoE 自研内核）**：Adreno 830 驱动 E031.47 在线编译器损坏 `get_scale_min_k4` + 三平面 mask 解码的代码形状——7 种形状改写 NMSE 位级不变、同地址四子群读互异字节、regA 读回激活位型、重编结果漂移；SPIR-V 绕行不可行（IL_VERSION 为空）。
- **解法**：host 预计算 seff/meff（set_tensor 一次性算好每 32-block 的 d·sc / dm·mn，内核 scale 读取退化成 q4_0 同构 half2 加载），把复杂代码形状整个移出内核。v0.3.1 上线，11/11 形状 NMSE=0~1e-6。
- **重要澄清**：**dense q4_K GEMV 从来没坏**——10-14 的 TBO ERR 1.7-1.9 是 sgb shim 的 bug（假案），当晚修 SGB_BC 宏时被静默治好，重编后 TBO 5 连跑 54/54 全绿。坏的是 MoE batched 路径，且坏因是编译器不是代码。
- **教训**：vendor 黑盒编译器会**静默**损坏特定代码形状，你摸不着改不了，只能发明 dodge 绕行。这是 Mesa 路线（ir3 源码可读可改）的核心动机之一。

### 短腿⑤ FGSVM 流式写反噬 pread

- **证据**：GPU bank 模式下专家流式读带宽 io 2.9→1.7GB/s，pmgmt 21→44ms。
- **机制**：FGSVM（fine-grained SVM）直写路径与 pread 读流争抢内存子系统；740 上更严重。
- **对策归属**：M2 换 UMA gpuobj mmap 直写（freedreno 天然 UMA，等价且更干净）。

### 4.1 明确不追的遗留

- GPU-bank 残留 42 CPU ops 中 MAP_CUSTOM2:39 = `ffn_moe_slots` 同步 op（CPU by design，便宜）。
- GPU bank 下 pread 变慢（短腿⑤）——等 M2 UMA 一起治，不单独修。
- x 腿 432→42 后的收益被小算子内核慢吃掉——不修内核速度，只走 M3。

## 5. 本轮战役完整记录

### 5.1 bank23-26（740，GPU bank 收口）

| 轮次 | 内容 | 结果 |
|---|---|---|
| bank23 | async vs blocking drain A/B | **全灭**（随机步 #11/#36 SIGSEGV 于 stage_pack 读垃圾 soa）→ llvm-symbolizer 定位 → `uploads` 并发 push_back 无锁 UB |
| race fix | per-thread 本地 vector + join 后合并 | bank24 四腿全 EXIT=0 |
| bank24 | io4 vs io1 | 1.15/1.13 vs 0.98/1.24（噪声级，io4 prefill 略优 35/37 vs 41/43s）→ 维持 IO_THREADS=4 |
| bank25 | **route0**（直写 SVM + IO 线程入队 pack）vs route1（staging+async drain） | **route0 全面胜出**：1.68/1.40 vs 1.26/1.08 t/s，prefill 29.7/32.0 vs ~38s；drain 130ms→0，pmgmt 269→135ms |
| bank26 | CPU bank 基线（新库回归）+ SCHED_STATS | CPU 2.57/2.50 无回归；GPU-bank 161 splits + 200 copies 税实锤 → **740 GPU 路径结构性出局** |

运维插曲：adb push "坏了"其实是 Git Bash MSYS 路径转换（`MSYS_NO_PATHCONV=1` 平反，124MB/s）；740 一次自行重启 + PIN adb 注入解锁恢复存储（224/82 + text + 66）；830 无线掉线 = 息屏杀 adb，重连 `adb connect 100.75.247.55:5555`。

### 5.2 bank30-32（830，GPU 三连测）

见 §2.1 表格。关键发现：**g 腿（GPU bank）MoE 上 GPU 但 dense 留 CPU；f 腿（ngl=99）dense 上 GPU 但 MoE 留 CPU——两半各自上过 GPU，从没合体过**；bank32 合体后反而最差（残留 432 CPU ops + FGSVM 反噬）。

### 5.3 probe9（830，提交税解剖）

| 测项 | OpenCL | CPU |
|---|---|---|
| tiny-op 斜率 | **9.04µs/op** | 0.34µs/op |
| K=1 单图固定开销 | 65.6µs | — |
| 40×q4_K GEMV 串链 | 128.3µs/GEMV | 109.1µs/GEMV（打平） |
| lm_head（248144×2048） | 7.3ms（39GB/s）**赢 2.5ms** | 9.8ms（29GB/s） |
| cl_khr_command_buffer | **NO** | — |
| cl_arm_command_buffer | **NO** | — |

结论：per-op 税 9µs 不是 150-220µs（勘误）；GEMV 本体打平；lm_head GPU 有小赢；**单提交机制驱动不暴露**。

### 5.4 x7 / x8（830，全图收编 + 数值验证）

- CPU 岛根因三连：①`use_adreno_kernels` 要求 ne≥512×512 → gdn 的 ssm_alpha/ssm_beta 小权重无 GEMM 内核 + load-time dummy m=512 检查 → 拒收 → CPU buffer；②SSM_CONV 被 10-14 的 A8X 保守门控关死；③MAP_CUSTOM2:39 = `ffn_moe_slots` 同步 op（CPU by design）。
- 修复后 x7：splits 83 / copies 128 / CPU ops 42，**但 4.30 t/s vs CPU 8.07**——省下的税被小算子内核慢吃回。
- 数值：三路通顺无坏 token；x7 vs x8 隔离证明分叉 = fp16 精度差。
- **定性**：Metal 两招，"整图一次提交"被驱动锁死，"全图收编"做到了但小算子内核速度不赚反亏 → 830 全 GPU（vendor OpenCL 栈）数学天花板 ≈ 持平 CPU 且实测差距大 → **vendor OpenCL 栈封存，转 Mesa**。

## 6. Mesa 栈可行性侦察结果

### 6.1 三个钉死的事实

1. **Mesa 26.0 官方支持 Adreno 8xx（830/840）**：Turnip（tu_kgsl）+ Freedreno，A830 base entries 已 upstream；社区 fork（whitebelyash/mesa-unified gen8、The412Banner/Banners-Turnip）实测可跑。已知坑：A830 GMEM write page fault（`TU_DEBUG=sysmem` 绕过）。
2. **Rusticl + Freedreno 默认启用**：Mesa 24.3 起 Freedreno Gallium3D 支持 Rusticl OpenCL compute；2026 XDC 报告 Freedreno 默认 enable Rusticl，**OpenCL 3.1**，支持 cl_ext_float_atomics、cl_khr_subgroup* 等。
3. **830 设备条件齐备**：`/dev/kgsl-3d0` 权限 0666（shell 用户可直开）；**`/dev/dri/card0` + `renderD128` 存在** → freedreno msm_drm winsys 直连可用（不需要 kgsl winsys）；内核 6.6.118-android15（kgsl GPL 源码可查）。

### 6.2 这改变了什么

- **不用自己从零逆向**：a8x 的 ISA、IB 命令流、ir3 编译器全部在 Mesa 源码里合法可读。"反编译驱动"这个动作 Mesa 社区替全行业做完了。
- **不用自己写 OpenCL 前端**：rusticl 已搭好 CL C → SPIR-V → NIR → ir3 完整管线，我们的标准 OpenCL C 内核（batched MUL_MAT_ID、q4_K pack）理论上直接编译。
- **天然整图单提交**：Gallium pipe_context 模型 = 用户态录制命令流 + 批量 flush，kernel 间无 host per-op 提交——vendor OpenCL 缺的那个机制，Mesa 栈结构上就有。
- **编译器可读可改**：ir3 编译器是 Mesa 自己的，坏代码形状能修编译器本体而不是发明 dodge（对比 E031 教训的结构性反超）。

### 6.3 仍不确定的（M0 要回答）

- ir3 编译器产出的内核代码质量 vs 高通 compiler（决定性）；
- rusticl 通用层 per-op 录制开销（NIR 转换 + 命令打包）实际多少 µs；
- a8x GMEM fault 在 compute 路径是否也会踩（sysmem 绕过掉多少性能）；
- Android bionic 交叉编 rusticl 的工具链工作量（rust aarch64-linux-android target + NDK r29 补丁）。

## 7. 四步走路线 M0→M4

### M0 判据探针（1-2 天，一票否决点）

**目标**：回答"ir3 编译器行不行"。

- **方法**：mesa 交叉编（NDK + rust aarch64-linux-android，`-Dgallium-drivers=freedreno -Dgallium-rusticl=true`；可先借 mesa-for-android-container 预编译包在 proot 里快跑）→ 830 上 clinfo 确认 → 跑 **dense q4_K GEMV**（干净标尺，§4 资产 7）对比 ir3 vs 高通 compiler 速度 + NMSE；同时测 rusticl per-op 录制成本（probe9 同款 tiny-op 斜率法）；顺带复核完整扩展串。
- **判据（两条同时满足才继续）**：ir3 内核速度 ≥ 高通 compiler 的 **70%**；rusticl 录制 < **3µs/op**。
- **失败处置**：当场枪毙整条路线，止损 2 天，CPU bank 8.07 封顶也够用。

### M1 内核迁移（~1 周）

**目标**：自研内核在 Mesa 栈上全部跑通。

- batched MUL_MAT_ID（q4_0/q4_K）+ q4_K pack 内核直接以 CL C 源编译；
- 全形状 NMSE 门禁照搬（moe_probe 工作流）；
- 若 ir3 编译坏代码形状（E031 同类问题）：**修 ir3 编译器本体**（Mesa 源码可改），或沿用 seff/meff dodge；
- seff/meff 预计算管线搬迁（set_tensor 对应物在 rusticl 里重新接线）。

### M2 整图单提交（1-2 周）

**目标**：36ms host 提交税 → ~0。

- Gallium pipe_context 批量 flush：decode 图录制一次、多 token 重放（或每 token 一次 flush，量级已够）；
- UMA gpuobj mmap 直写替代 FGSVM：freedreno 天然 UMA，CPU preadv 直写 + GPU 直读（短腿⑤同治）；
- 预期：x7 的 233ms/token → ~170ms ≈ **5.9 t/s**（仍输 CPU 8.07，见 §8）。

### M3 小算子融合（数周，质变点）

**目标**：3941 ops → 几百个，GPU 执行时间 150ms → <90ms。

- norm+rope+GEMV 链融合、SSM_CONV+SCAN 融合、逐层 megakernel 化；
- **ir3 可读可改是核心优势**：融合内核编坏 → 修编译器（对比 E031 只能 dodge）；
- 每个融合 kernel 照旧过 NMSE 门禁（moe_probe 纪律）；
- 预期：**8-10 t/s，反超 CPU 8.07**。

### M4 集成（数天）

- moe_probe / minicpm_e2e 工具链整体搬迁到 Mesa 栈；
- 双机回归（740 只验不投入）；
- 830 生产配置切换 + 文档。

## 8. 天花板数学推演

以 830 x7 实测 4.30 t/s（233ms/token）为基准分解：

| 成分 | 现值 | M2 后 | M3 后 |
|---|---|---|---|
| host 提交税（3941 × 9µs） | ~36ms | **~0**（批量 flush） | ~0（ops 已少 10×） |
| 跨后端拷贝 | ~20ms | ~0（全图单后端） | 0 |
| GPU 执行（小算子为主） | ~150ms | ~150ms | **<90ms**（融合） |
| FGSVM pread 反噬 | ~15ms | ~5ms（UMA mmap） | ~5ms |
| 其余（调度/LES/同步） | ~12ms | ~12ms | ~12ms |
| **合计** | **233ms = 4.3 t/s** | **~170ms = 5.9 t/s** | **~110ms = 9 t/s** |

- M2 全成仍输 CPU（8.07 = 124ms/token）——因为 vendor OpenCL 栈上小算子执行慢是主项；
- **赢 CPU 完全押在 M3**：融合后 GPU 执行 <90ms 是全部 GPU 路线里 dense GEMV 优势（lm_head 赢 2.5ms、GEMV 打平）+ 大 kernel 化之后的自然结果；
- 上限估 **8-10 t/s（+20-30%）**——不是质变级的赢，但这是 decode 侧唯一还没关死的门。

## 12. FD740 rusticl 正确性战役（2026-10-17）

> M1 第一阶段：把 MiniCPM-les 全 GPU 推理搬到 740 真机 rusticl/freedreno+kgsl 栈上跑对。本节记录 subgroup 语义勘误、内核修复、编译链坑、op 全绿结果，以及 e2e 全 0 的根因追踪（两根因实锤 + 第三根因收窄）。

### 12.1 FD740 subgroup 三大铁律（probe2/3/4 实锤，翻案两次）

1. **查询撒谎**：内核内 `get_max_sub_group_size()`/`get_sub_group_size()`/`get_enqueued_num_sub_groups()` 恒返回静态设备最大值 128，不随 dispatch 变；但 `sub_group_shuffle_xor`/`sub_group_reduce_add` 实际作用于真实活跃 lane（local=64 → 64 lane）。⇒ 一切 `i += get_max_sub_group_size()` 步长循环只算一半 K。
2. **真实 subgroup = min(128, WG 总元素数)**（flatten x-fastest）：WG=64 → 64；WG={64,2}=128 或 {64,4}=256 → **一个 128/128 跨行子群**，破坏所有"多子群 per WG"假设（`get_sub_group_id()` 恒 0、lane id 0..127 越界）。
3. **`reqd_sub_group_size(N)` 被 rusticl 无视**（probe4）；且 `reqd_work_group_size(64,1,1)` + shuffle 组合会输出全 0（probe1，ir3 SHFL 相关，机理未深查，ggml 内核不含该属性）。vendor Adreno 无此问题（qcom attr 钉 subgroup 64 == local）。

**跨布局正确的 64-lane 归约** = xor 32..1 蝶形：vendor（sg=64）= 全子群归约；rusticl（sg=128、lane 线性化 x-fastest）= 恰好归约一个 64 对齐 y 行。可移植 lane/id 语义：`get_sub_group_local_id()`→`get_local_id(0)`、`get_sub_group_id()`→`get_local_id(1)`。

### 12.2 内核修复清单（全部走 `GGML_OPENCL_FAKE_QCOM_REQD=1` rusticl 路径，vendor 零影响）

| 文件 | 修复 |
|---|---|
| l2_norm / rms_norm / mul_mv_f16_f16 / mul_mv_f16_f32 / mul_mv_f16_f32_1row / mul_mv_f16_f32_l4 / mul_mv_f32_f32 | stride 全换 `GGML_EFF_SGS`（eff = min(max_sgs, local_size(0))） |
| mul_mv_q4_k_f32_flat / mul_mv_q6_k_f32_flat（dense decode GEMV 主路径，WG={64,2}=128） | `GGML_REDUCE64` shmem 树归约（`__local float[128]`，按 `local_id(1)*64+local_id(0)` 行分组，barrier 双同步）+ slid/sgid→local_id 替换 |
| gemv_moe_{q4_0,q4_1,q4_k,q5_0,q5_1,q5_k,q6_k,mxfp4}_f32_ns + gemm_moe_mxfp4_f32 + gemv/gemm_moe_mxfp4（10 文件） | `uint slid = get_sub_group_local_id()` → `get_local_id(0)`（slid 仅作 reduceLM 索引、无子群内建） |
| ggml-opencl.cpp | F16_MROW 默认值在 FAKE_QCOM 下改 false（mrow WG={64,16}=1024 → 128-lane 跨行 reduce 混两行 + ne00>2048 尾段永不填充 → NaN）；`GGML_OPENCL_DISABLE_GDN=1` 新增（GDN 强制回 CPU 二分用） |

### 12.3 编译链四坑（rusticl 内核注入协议，M1+ 照抄避坑）

1. **`-D CLK_SUB_GROUP_SHUFFLE_WIDTH_WAVE_SIZE_QCOM=64` 撞头文件枚举**（err=-11 "expected '}'"）——clang 21 注入的 kernel header 已声明该枚举常量，宏展开进 typedef enum 直接语法错误。**绝不要 -D 注入任何 CLK_*/CL_* 标识符**。
2. **手写 builtin 原型（`float sub_group_shuffle_xor(float, uint);`）编译过但 err=-6（CL_OUT_OF_HOST_MEMORY）无法落地**——自声明模块 rusticl lowered 不了。**绝不手写 OpenCL builtin 原型**。
3. **qcom→core shim 宏自递归**——rusticl **预定义 `cl_qcom_subgroup_shuffle`**（header 带 qcom builtin 声明 + width 枚举），kernels 的 `#elif defined(cl_qcom_subgroup_shuffle)` 分支天然激活；注入 `-D qcom_sub_group_shuffle_xor(v,m,w,a)=sub_group_shuffle_xor((v),(m))` 会递归成 implicit declaration。
4. **结论：FAKE_QCOM 注入只保留 `-D cl_qcom_reqd_sub_group_size=1 -D GGML_GENERIC_SUBGROUP_SHUFFLE=1`，其余全撤**——rusticl 原生实现 qcom shuffle builtin 且校验 width 枚举合法性（传裸整数 64 会报 invalid value），真枚举让头文件给。

### 12.7 根因 B 追踪续：批量模式 GET_ROWS 读零（2026-10-17 深夜–10-18，收窄）

#### 12.7.1 方法学三连坑（前轮「window state bug」结论作废）

1. **`E2E_CBD_PREFILL=0` 真值 bug**：e2e 用 `!= nullptr` 判空 → `export E2E_CBD_PREFILL=0` 反而**激活** prefill 审计 → `g_cbd.done=true` 杀死后续 decode 审计。昨夜 window=0 A/B 实际比较的是 prefill 节点，全部作废。已修 `e[0] != '0'`（同坑：`E2E_CBD` 也无法用 `=0` 关闭）。
2. **wdump 时机伪影**：`seen_w` 去重使 W_cache_*.bin 落在**首个匹配节点**（多为 prefill 早期零态），不是 decode 时状态。
3. **VIEW 节点审计先于其 cpy**：`conv_state_update-N`（VIEW）审计验证的是**上一次**写回；最后一次写回（真正留给 gen-1 的）从未被审计。

#### 12.7.2 CPY 写回直接审计（新插桩，bring-up 通用）

`e2e_cb_eval` 中对 `op==GGML_OP_CPY && src1 名含 "cache_"` 的节点：ask=true 返回 true 让该节点**单独成 batch + sync**，ask=false 时读 dst view 落地值 + src0 同刻值（rms/zero/nan + occ 序号，`E2E_CBDDIR` dump 原始字节）。`E2E_CPY_ONLY=1` 只审计写回（22 call prefill 可承受）。occ 每 call 2 个：奇数 = `n_rs==n_seqs` 时零尺寸 extra-states cpy no-op（无害悬案告破），偶数 = 真写回。

#### 12.7.3 决定性数据：dst 忠实于 src0，cpy 无罪；病灶在 gather

| 配置 | conv_state_last-38（写回源 src0） | 落入 cache |
|---|---|---|
| CPU 腿 | call1=2/3 零 → call2=1/3 → call3=0 → call4+ 全满（读-移位-追加窗口正常填充，逐字节吻合） | 全满 rms 2.5，文本正确 |
| **GPU 腿批量（生产等价）** | **每次 call 恒 2/3 零 rms~0.5，22 次 prefill + 48 次 decode 全程不累积** | 2/3 零 |

- 写回链：`build_rs` 用 **I32 input 索引 gather（GET_ROWS，op=40）** 读 RS cache 旧行 → 与新 token concat → `conv_state_last` view 取列 1-3 → cpy 写回。dst 忠实于 src0 ⇒ **gather 每次读回 [0,0,0]**，历史永不累积 → cache=[0,0,x22] → gen-1 读入垃圾 state → logits 崩溃（max 9.29 vs CPU 32.42）。
- **逐节点同步模式健康**（nwg 旧日志：call2 gather 已读到 [0,0,x1] rms 2.12）——**批量 vs 逐节点是唯一判别维度**，decode 期批量同样坏。
- **三连证伪**：① 跨 call 异步排队（`E2E_PREFILL_SYNC=1` 每 call 后 llama_synchronize，无效）；② OpenCL 融合吞节点（`GGML_OPENCL_DISABLE_FUSION=1`，无效）；③ layer 0 批量下健康（decode-1 src0 全满）——**layer 0 与 38+ 的差异是当前最强线索**。
- RS_CACHE_CPU=1（ddrc）换 CPU 存放 cache 仍坏且模式不同（全满但 ~0.41× 系统性缩放）⇒ 排除内存踩踏，指向值流本身。

#### 12.7.4 未解：rsidx 探针管线之谜（下轮第一优先）

### 12.8 探针管线告破 + GET_ROWS 输出审计（2026-10-18 凌晨，根因收窄到最后一层）

#### 12.8.1 探针管线之谜告破 = adb 引号劫持（方法学重大勘误）

- rsidx3/4/5 三连 0 行的根因：`adb shell sh cpy.sh tag "A=0 B=0 C=1"` 中**本地 MSYS shell 吃掉双引号**，adb 转发后设备 sh 重切 → `$3` 只拿到第一个词，**LLAMA_RS_IDX_DEBUG 等后续 env 从未进环境**。
- 连锁翻案：nofuse 首跑（融合证伪当时无效）、pysg（Run Y）、rsidx4/5 全部作废；cpysg（单变量 $3）仍有效。

- 另修：ninja 曾静默没重编（推旧 so）——此后「本机 grep 探针串 → push → 设备 grep」三验为固定流程。

#### 12.8.2 rsidx 探针战果：索引侧全线无罪

GPU 逐节点同步 / CPU / GPU 纯批量三模式 `idx: 0, head=0, rs_z=-1` 全程恒定（单序列正确值），70 次 set_input 齐整。**「索引垃圾」分支正式出局**。

#### 12.8.3 ★ GET_ROWS 输出审计（rows1/2/3 三跑确定性复现）

新插桩：ask=true 单独同步 gather 节点，ask=false 读**输出**+**源视图**+row0diff。核心事实：

- **忠实层（out==src 逐字节、状态正常累积）：静态 = {l0, l4, l5, l6}**（l4 零列 16384→8192→0 完美填充）。
- **损坏层（输出恒纯零、src 有数据）：l1（call-3 起）、l2（call-3 起）、l8 起全部线性层（call-2/3 起）**。row0diff = src 非零元数 ⇒ 输出 = 纯零页。
- 层组结构：线性层 [0-2][4-6][8-10]…（attn 层 3,7,11… 分隔）。忠实 = 第一组部分 + **第二个 attn(3) 后的整组 [4,5,6]**；第三个 attn(7) 之后全灭。非前缀、非 offset 单调。
- idx/源数据/内核三要素在忠实层已验证健康 ⇒ 损坏 = 内核**没执行或读/写到零页**，按 (layer, call) 确定性。
- sched 分配映射（GGML_SCHED_DEBUG=2，schedmap 日志）：全部 gather 各自独占一个 OpenCL split、src 同 buffer 无跨后端拷贝、结构完全同质 ⇒ **sched 层排除**。out_ptr 指针：l4/5/6（健康）与 l8+（损坏）共用 0x18300 scratch ⇒ **scratch 别名排除**。
- 融合二分：关 MoE combine 系（COMBINE/BIAS_COMBINE/BIAS_GLU=0）纹丝不动 ⇒ combine 系排除；nofuse2（全禁）gather 忠实但 L38 状态 NaN、纯批量+禁融合（prodnf2）logits 全零 ⇒ 禁融合暴露 standalone 内核另有问题，非干净对照。剩余嫌疑：rms_add/mm_glu/norm 系融合、OpenCL GET_ROWS 内核在特定 split 前缀下的执行（下一轮逐个 opt-out 二分 + 内核级 probe）。

#### 12.8.4 现状与下一步

- 纯批量生产（无审计）= logits 全零流（§12.5 原始病灶）；ddg 的 9.29 垃圾 logits = prefill 逐节点 + decode 批量混合态。
- 下一步：① rms_add / mm_glu / norm 系融合逐个 opt-out 二分（rows 配置，6.5min/跑）；② GET_ROWS 内核最小复现 probe（复刻 l8+ split 前缀）；③ 修真根因 → 强制 token GPU 文本对齐 CPU → 真实 t/s。

### 13.1 一句话结论

**天玑 = 同构地基换驱动栈**：内核源码 / 数值门禁 / 调度 / 工程链约 70% 资产直接复用，**驱动层 100% 重做**。与 Adreno 的三个实质差别：

1. **vendor 驱动给 command buffer**（`cl_khr_command_buffer_mutable_dispatch` + `cl_khr_create_command_queue`，Arm 官方扩展清单在列）——Adreno vendor 恰恰没有（§3 短腿①，probe9 实锤 `cl_khr_command_buffer = NO`）。§3 短腿①的提交税在 Mali vendor 路径上有**现成官方抓手**，M2 整图单提交在 vendor 路线就可能先做到——这是 Adreno 线不曾有过的选项。
2. **内核侧形态不同**：Adreno retail 有 kgsl userspace winsys（rusticl 直连，§11.1）；Mali stock 设备只有 `/dev/mali0`（kbase），**rusticl 的 Gallium 路线没有 kbase winsys**——但社区已有 **PanVK-on-kbase/CSF β**（2026-08 起，Mali-G720 MC8 实测 compute 管线通过），与 Turnip-on-KGSL 完全同构。
3. **开源生态位刚翻转**：Mesa 26.2 起 **rusticl + Panfrost 默认启用，且 Panfrost 已过 OpenCL 一致性认证**（XDC 2026）；Arm 员工直接参与上游；新编译器 KRAID 2026-06 合入覆盖 Valhall v9+。天玑线的长期开源势能反而**好于** Turnip 起家时。

### 13.5 推荐与节奏

**A/B 并行先出 M0' 数据（1-2 天/台）→ 中期押 C（与 Adreno 同构）→ D 作 dev 底座保底 → NPU 另册。**

- A 的价值在于最快拿到 vendor 真实底数，且 **command buffer 结论直接决定 M2 走 vendor 还是 Mesa**。
- B 是 A 的备份，且比 C 稳（不依赖 β）。
- C 与 Adreno 线同构、长期收益最大，等 β 成熟 + KRAID 出早期后跟进。
- D 保「不被 vendor blob 绑架」的底线，也为将来 MTK GKI 主线开 panfrost 留口子（低概率，可关注）。

**时序铁律：830 线 M2/M3 定型后才启动天玑线**（内核层人力冲突，双线同时改内核必烂）。M0' 探针可在 830 M1 期间并行——设备到位即跑，1-2 天成本，不碰内核。

**测试机建议**：一台 G720 级（8400/8550/9300；**G720 MC8 优先——与社区 PanVK β 的 MC8 同型**，社区已有 D8400 跑 llama.cpp 的存量环境）+ 一台 G925 级（9400）验 v13 档位；先单台 G720 可接受。

### 13.6 M0' 判据探针（对齐 §11 M0，一票否决置顶）

前置：一台天玑（G720/G925 级）+ DGX trixie chroot 自编 mesa 26.2+（同 §11.2 环境链，目标驱动 Panfrost 替 freedreno）。

| # | 判据 | 方法 | 否决线 |
|---|---|---|---|
| 1 | **`/dev/mali0` SELinux 权限** | 小 app dlopen vendor blob 跑 `clGetPlatformIDs`（shell 域先探）；类比 Adreno 侧 kgsl-3d0=gpu_device | app 域打不开 → 路线 C 死（A/B 同样死；但游戏/Vulkan 在用 → 大概率通，**实测为准**） |
| 2 | vendor blob 存在性与扩展全串 | clinfo：CL 版本、subgroups、fp16、command buffer 家族、int8 dot、il_program、AHB import；多 ICD 并存顺序 | 无 CL 平台 → A 死，转 B/C |
| 3 | 提交税 | 同 probe9 方法（K=1000 tiny-op 斜录）：vendor CL enqueue/op vs clvk vs PanVK-kbase；**专测 command buffer 录制+重放路径** | 录制+重放 < 3µs/op 才配谈 M2 单提交 |
| 4 | 数值 smoke | moe_probe 直接跑 batched MUL_MAT_ID q4_0 + q4_K 全形状；subgroups 三铁律（§12.1）在 Mali 编译器的复现 | NMSE ≠ 0 → 按 E031 纪律定位（编译器 or 代码） |
| 5 | e2e 48 token | vendor CL vs clvk vs PanVK-kbase vs **CPU 基线**（天玑基线先建） | — |
| 6 | 热曲线 | 10 分钟持续 decode，t/s 衰减斜率 | 衰减 > 30% → 需频率/预算策略，否则长会话不可用 |
| 7 | 机型分裂测绘 | G615/G715/G720/G925 四档指纹（CL 版本/subgroups/白名单） | 不在指纹表的机型 → CPU 兜底 |

判据口径同 M0：① 自研内核 ≥ vendor 70%；② 提交税 < 3µs/op；③ NMSE 与 CPU 参考位级一致；④ e2e decode 超 CPU 基线。

### 13.7 风险清单（MTK 特有）

### 13.8 与 Adreno 线的关键不对称（备忘）

- 提交税：Mali vendor **有** command buffer（probe9 当年就注意到「Mali 阵营有 ARM 版」，本节查证坐实为 `cl_khr_command_buffer_mutable_dispatch` + `cl_khr_create_command_queue`）/ Adreno vendor **无** → 两条线 M2 起点形态不同；
- 内核栈：Adreno retail 有 kgsl userspace winsys（rusticl 直连）/ Mali stock **无** Gallium-kbase winsys（只有 PanVK-kbase，OpenCL 需 clvk 中转）；
- 开源生态位：Turnip 起于社区高风险逆向（kgsl winsys 还是自研补丁 0011/0012/0026）/ Panfrost+rusticl 已有 Arm 员工上游参与且过认证 → 天玑长期势能更好；
- INT8：Mali Valhall+（G77 起）有 native int8 dot-product-accumulate 扩展 → 量化 GEMV 在 fp16-dequant 之外有第三条路，M1' 评估；
- SELinux：Adreno 侧实测 renderD128 拒 / kgsl-3d0 可开（§11.1）；Mali 侧 mali0 权限**未测**，是 M0' 第一否决项。

## 结语

三条路都试过了：vendor OpenCL 全 GPU（四配置全输，x7 收编到极限仍 4.30）、Turnip Vulkan（5-11，内核裸奔）、反编译闭源驱动（法律 + 工程 + 天花板三杀）。**M0 探针已完成并裁决 GO（§11）**：ir3 编译质量不输高通（大形状反超 21%）、rusticl 录制税在 proot 污染内仍达标、kgsl 全链路真机跑通。全 GPU 路线的最后一张牌继续打——下一步 M1 内核迁移：batched MUL_MAT_ID + q4_K pack 以 CL C 源上 rusticl/ir3，全形状 NMSE 门禁照搬 moe_probe 纪律，坏形状修 ir3 编译器本体。
