### 1. `:583` — E4「`known_bad_kernels` 表 🟥 不可达 / **无数据表**」＝**过期**

原文（E4 行）：`🟥（不可达，只跟踪）… 无数据表 ⇒ 无法判"这个 ke…"`

**实况**：坏内核数据表已经在场并且**有机检**：

- `wt/vk-line/tools/known_bad_kernels.tsv` — 12 行，`vk_table_check.py` PASS（schema + evidence 首 token 可解析）；
  `vk_table_audit.py` 在 turnip 归档 1224 判定行上判：`failed but not in the table: none`、
  `in the table but seen only passing: none`（无漏抓、无白排除）。
- `ggml-vulkan.cpp` 内 **5 张 C++ 驱动表**：ssm_scan 宽度表、subgroup 归约可用性表、matmul/matmul_id 坏类型表、
  host-buffer 类型拒绝表等；全部走 `ggml_vk_driver_is()`（driver_id **或** deviceName 小写子串）+ 代际门。
- 判据 3 的机检在场：`vk_no_device_if_check: PASS - 3 个文件无按设备名分支（设备特例只在数据表里）`。

**该改的口径**：E4 由 🟥 改 🟩（有表 + 有校验器 + 有负对照）；但**同时**记一条新欠账：
a6xx 的负对照 config 是表落地**之前**的语义，目前空转（见第三节）。

### 2. `:652-654` 与决策面板 `:744` — 「`test-backend-ops … 27 分钟未退出 ⇒ 疑似挂死；使 K40 无法进入安静态」＝**认错人**

**实况**：那是 **Vulkan 线本人的 stock 扫描**，且**不是挂死**：

- 表打完全部判定之后**在进程退出时** SIGSEGV（`rc=139`），归档里有相位标记
  `# crash_phase=teardown verdicts_before_crash=93`，现场在 `base_a.crash.txt`；
- 判定点已经收录进矩阵（`0 OK / 843 FAIL / 90 NS, maxERR=1407`），崩溃单独定案；
- **进程现在早就不在了**（此刻 `ps` 只剩门禁自己的子进程）。

**面板 #7「要我 kill 还是你看」的答复：是我的，别 kill。** kill 掉只会把判据 1 唯一在跑的
stock 证据丢掉。正确处置是**已实现的** `crash_phase` 机制：判定收录、崩溃另立一章。

### 3. `:1685`「**定案：不是内存压力，是 vendor 驱动的硬上限**（单块 ~996 MiB）」＝**证据是单点，结论下重了**

三条独立反证 + 一个更省事的假设：

1. **数字本身可疑**：他们那次失败的是 `1044893696 B ≈ 996.5 MiB`，离 **1 GiB 只差 3.4 MiB**。
   "996 MiB 硬上限"和"某个 2^30 边界（探针/loader 侧）"两种解释，靠**一个尺寸点分不开**。
   最小判别实验：同一探针跑 **512 / 768 / 960 / 1023 / 1024 / 1025 MiB** 六档。
   若 1023 通过而 1024 失败 ⇒ 是**边界**，不是"996 MiB 这个上限"。
2. **跨驱动不同数**：Vulkan 侧 stock 报的是 `alloc 723448992 B failed`（≈690 MiB），
   而 turnip 实测可用墙 ≈ **4.29 GB**。同一台 K40、同一块 GPU，三个数 ⇒ **更像是两处独立的门**
   （vendor ICD/OpenCL 路径一处、Vulkan 一处），不是一个统一的"vendor 硬上限"。
3. **探针所在位置**：他们说探针跑在 **vendor ICD loader** 上，且 `kgsl-3d0` 对 shell 是
   `Permission denied`（无权威读数）。那么"驱动硬上限"与"loader/探针自身上限"目前**不可分**。

**建议口径**：把"定案"降为「**观察：OpenCL 路径上单块 ~996 MiB 被拒，候选有二（驱动上限 / 2^30 边界）**」，
等六档扫描出结果再定案。**这条影响所有大模型全载，值得花 5 分钟把六档跑完。**

## 二、归属更正（他们的"邻居"就是我）

| 地图原述 | 实况 |
|---|---|
| `:1639` / `:1672`「邻居那条 **CPU 腿**（~8 GB RSS）使 K40 无法安静」 | 那是 **Vulkan 线的 CPU 参照腿**（`-dev none -ngl 0`，`llama-cli` RSS 8.6 GB）。它**不能关**——§8.1 基线表要求同 session 三后端对照，缺它整个判据 4 就废 |
| `:654`「它使 K40 无法进入安静态（G-803）」 | 同上。**不是滥用**，是判据要求的对照腿；且我每条测量前都跑 `vk_contend_sample.sh`，`foreign_over_1g` 只数**别人** |

**提议立一条跨线规矩（不点名、按时间戳互斥）**：K40 上开一个文件锁
（`/data/local/tmp/vkl/.device_lock`，内容 = `哪条线 + 起始时间 + 预计时长`），
谁在测量谁持锁，另一方**排队而不是并行**；两边各自的争用采样器都改成：
**发现对端持锁 ⇒ 本轮数据自动作废并等待**，而不是"看见大进程就报警"。
现状是双方互相当对方是"外来 1GB 进程"，两边都在丢数据。
