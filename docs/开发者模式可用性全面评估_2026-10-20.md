## 一、结论摘要

开发者模式**当前不具备面向用户的可用性**，属于「功能骨架完整、闭环全是洞」的状态。它的分层设计（工作区四后端 / L0-L3 执行环境 / 统一 ToolExecutor / TOFU / secure storage）方向是对的，但**用户真正走通的每一条路都在中途静默失败或说谎**，且**唯一该解除阻塞的开关（危险命令策略、审批通道）是死的**。

一句话诊断：**这个功能不会告诉用户"为什么不行"，也不会告诉模型"其实没成功"——它甚至会在失败时报告成功。**

三条最要命的实测结论（都不是推测，是跑出来的）：

1. **远端命令根本没有退出码**：`SSHClient.run()` 返回 `Future<Uint8List>`（`third_party/dartssh2/lib/src/ssh_client.dart:409`），
   结构上拿不到 exitStatus → `pytest`/`npm test` 全红，AI 也会回「测试已通过，现在提交」。**假验收是 AI 编程功能的死刑。**
2. **安全护栏两头都输**：13 条正则真跑实测，**45-65% 的正常开发命令被误杀**（`dart format lib/`、`npm run sync`、
   `git commit -m "fix mount bug"`、`git push --force-with-lease`、Termux 下清 `build/` 全废），
   而 `\rm -rf /`、`/bin/rm -rf /`、`bash -c "rm -rf /"`、`git push -f` **全部放行**。拦不住真要命的，专拦天天用的。
3. **审批体系是假的**：「每次审批」设置零消费方（`allowAsk` 函数体未用）；工具级审批框因 `preListeners` 生产从不传而**永不触发**；
   沙箱升级审批被 `main.dart:52` 的前置开关掐死、**连弹框都不弹**，却回填「用户拒绝了」——模型和用户互相都觉得对方在耍自己。

同时，**测试基线是健康的（`flutter test test/agent` = 465 通过 / 2 skip / 18s 全绿）**：
问题从来不是"测试挂了"，而是**P0 全部落在零覆盖的层**（SSH 连接层、SFTP、向导、审批弹框、黑名单真实误杀率）。

历史证据同向：`lib/agent/dev` 自 2026-10-06（`8a2da7fd` / `a002b3a0`）后再无实质改动；AGENTS.md 2026-10-04 自列的「遗留（真机验收点）：Termux RUN_COMMAND 全链路 / SFTP+git 闭环」**至今无验收记录**。同期主线全部投入推理引擎。2026-10-06 一天内连吃 4 轮真机「还是不行」（/plan 只读被 dev_shell 绕过、dev_shell 描述误导模型放弃 git、git_clone 目标路径恒失败、git 工具看不到子仓库），说明该功能**没有自动化验收，靠用户当测试机**。

## 二、P0 阻断级（16 条，逐条带证据）

### P0-1 「每次审批」是纯装饰，被误杀的命令**没有任何解除路径**

- 证据：`lib/agent/dev/safety.dart:30`
  `String? checkDangerousCommand(String command, {bool allowAsk = false})` —— **函数体从不使用 `allowAsk`**，命中即返回拒绝原因。
- 4 个调用点**全部不传策略、也不读设置**：`ssh_tools.dart:211`、`ssh_tools.dart:283`、`verify_tool.dart:51`、`embedded_tools.dart:164`。
- `dangerousCommandPolicy` 只在 `settings_service.dart:413/538/850/956/1114` + `settings_provider.dart:325` + `settings_screen.dart:6077-6083`（拒绝 / 每次审批 两个 ChoiceChip）之间往返，**没有任何执行链路消费它**（全项目 grep 无第三处使用）。
- 唯一合法的绕行是 `dev_shell` 的满权限批准（`embedded_tools.dart:162-170`），而它被 P0-2 堵死。
- **用户看到**：AI 说「危险命令被拒绝：删除系统目录」，去设置里把策略改成「每次审批」——毫无变化，永远弹不出审批框。
- **复现**：Termux 工作区里让 AI「删掉 `/data/data/com.termux/files/home/projects/demo/build` 重新构建」→ 命中 `safety.dart:24` 的 `rm\s+-rf\s+(/usr|/system|/data|/vendor)` → 判「删除系统目录」→ 切「每次审批」→ 再试 → 依然直接拒绝。
- **修复**：① `checkDangerousCommand` 增 `policy` 入参并真正分流（deny→拒绝 / ask→返回"需审批"标记）；② 4 个调用点从 `ToolDefinition` 执行闭包透传设置快照（对齐 `devSshConfigs` 回合级快照做法）；③ 审批落 `toolPreApproverProvider` 复用现成 ApprovalDialog（`main.dart:84`）；④ 黑名单改「shell-words 解析 + 首 token + 路径 jail」，见 §四-1。

### P0-2 沙箱升级审批默认**谎称「用户拒绝了」**，模型被系统性误导

- 证据链：
  1. `lib/main.dart:49-52`：审批实现第一行 `if (!settings.agentFullFileAccess) return false;` —— **在 `showDialog` 之前就返回拒绝**。
  2. `settings_service.dart:512` `this.agentFullFileAccess = false` —— 默认关；开关藏在 设置→智能体→「🧪 高级 / 开发者」（`settings_screen.dart:3730`）。
  3. `lib/agent/tools/tool_executor.dart:73-76`：拿到 false 后回填模型 `'用户拒绝了沙箱升级到 "..."'`。
  4. `ssh_tools.dart:252` / `embedded_tools.dart:145` 的工具描述**主动教模型**「需要完整文件系统访问时带 sandbox_permissions 请求用户批准」。
- **用户看到**：AI 说「我请求访问权限时你拒绝了，所以我改用别的办法 / 做不了」。用户：我什么时候拒绝过？
- **复现**：开发模式开、不动任何高级设置 → 对话里说「把工作区外的 /sdcard/x.txt 拷进来」→ 模型带 `sandbox_permissions` 调用 → 无任何弹框 → 模型收到"用户拒绝"。
- **为什么是 P0**：这不是功能缺失，是**信任崩塌**。模型据此改变行为，用户据此怀疑 AI 在编瞎话。
- **修复**：区分三态返回（`granted / rejected-by-user / not-configurable`）；未开启授权时回填给模型的文案必须是「用户未开启『完整文件访问』，请在 设置→智能体→高级 打开后重试」，**不得伪装成用户决策**。

### P0-3 `git_push` 没有强制审批，但 prompt 与工具描述都承诺有

- 证据：`git_tools.dart:258-299` git_push 执行体**无任何 approver 调用**，直接 `LocalGit.push(...)` 或远端 `git push`。审批完全依赖模型**自愿**带 `sandbox_permissions`（`git_tools.dart:263-264` 描述："会改动远端代码，**需要用户批准**：请带 sandbox_permissions + justification 请求批准后执行"）。
- 同 `dev_context.dart:147`（注入给模型的 `kDevInstruction`）：「6. 提交：git_commit（本地），需要推送时 **git_push 并请求用户批准**」。
- 后果：端侧 2B-4B 模型漏带该参数是常态（本项目 AGENTS.md 大量记录小模型工具调用格式退化）→ **无人确认即推送到远端仓库**。叠加 P0-2，即使模型带了参数被拒，它得到的还是"用户拒绝了"的假信号。
- **修复**：git_push（以及 workspace_sync 的覆盖方向）在**执行体内**硬性要求审批，缺 `sandbox_permissions` 直接返回 `requires_approval`，不接受模型自觉。

### P0-4 `ssh_write_file` 声称"目录自动创建"，SFTP 实现根本不建父目录

- 证据：工具描述 `ssh_tools.dart:376`「写入文本到…（覆盖，**目录自动创建**）」；
  实现 `ssh_environment.dart:234-237` 只有 `SftpFileOpenMode.write | create | truncate`，**无任何 mkdir/父目录创建**。
  （对比：Termux intent 分支**建了**目录 —— `termux_intent.dart:147-152` 有 `mkdir -p '$dir'`。）
- **用户看到**：远程电脑/未开免 SSH 通道的 Termux 工作区里，让 AI「新建 `src/utils/helper.py`」→ AI 回「已创建」，实际文件不存在，或报 `No such file`；同一个操作在另一条通道下又能成 —— 表现为"时好时坏的玄学 bug"。
- **复现**：远程电脑工作区（走 SSH，不走 intent）→ 让 AI 写一个位于新子目录的文件。
- **修复**：`writeFileBytes` 前逐级 `sftp.stat` + `mkdir`，或统一走 `execute('mkdir -p …')`；描述与实现对齐（两条通道行为必须一致）。

### P0-5 工作区/任务**重启即丢**，且存在"持久化了但没人读"的双真相源

- 证据：
  - `dev_controller.dart` 的 `_activeWorkspaceId` / `_activeTaskId` **只在内存**；`init()` 只 `loadWorkspaces()`，**从不恢复激活工作区**；`setActiveTask`（`dev_controller.dart:105-109`）不落盘。
  - `workspace_store.dart` 全文（1-134）**没有任何 active id 的读写 API**，只有 workspaces/tasks 两类文件。
  - 而 `settings_service.dart:406/536/848/954/1111` 有 `devWorkspaceId`，UI 在 `settings_screen.dart:5622` 写入它 —— **全项目零读取方**（grep 确认）。
- **用户看到**：今天切到「我的博客项目」，杀掉 App 明天再进来 → 切回「默认工作区」，AI 把文件写进默认沙盒，用户找不到文件；设置页的选中态也丢了。
- **修复**：删掉 `settings.devWorkspaceId` 这条死路，激活态由 `DevStore` 落一份 `dev/active.json`，`init()` 恢复；或反过来让 DevSessionController 以 settings 为唯一真相源（二选一，不能并存）。

### P0-6 工作区**只能新增，不能改名也不能删除**

- 证据：`DevSessionController.deleteWorkspace`（`dev_controller.dart:88-102`）**全项目零调用方**；
  `_showWorkspaceDialog` 支持 `existing:` 参数（`settings_screen.dart:5642`），但唯一调用点是「新增」（`settings_screen.dart:5629`）。
- 附带：工作区芯片 `settings_screen.dart:5612` `Text(ws.isDefault ? ws.name : ws.name)` —— 三元两分支相同，后端类型/默认标记就此丢失。
- **用户看到**：试错建出一堆「未命名工作区」，删不掉、改不了名、看不出哪个是 Termux 哪个是远程电脑，只能弃用整个功能。
- **修复**：芯片长按弹菜单（改名/编辑/删除/查看绑定连接）；芯片加后端徽标；删除时联动清理 `projects/<id>` 镜像与归属任务（现 `taskBelongsToWorkspace` 会把无主任务收进默认工作区，删除后要确认语义）。

### P0-7 Termux 向导：连接失败即**关掉整个对话框**，无回退、原地重试、诊断分叉

- 证据：`settings_screen.dart:5038-5062` `finishConnect` → 无论成败都 `Navigator.pop(ctx)`，失败只给一条红色 SnackBar；`step` 只能 0→1→2 前进，无「上一步」。
- 连带代价：向导内的密钥是**对话框局部状态**（`generated` / `privateKeyPem`，`settings_screen.dart:5010-5014`），关掉即弃 → 重开向导 = 重新生成密钥 = **用户必须回 Termux 重新粘贴执行那条万能命令**。
- **复现**：用户名填错一个字符 → 点「✅ 连接」→ 对话框消失 → 重来（含重新粘贴命令）。
- **修复**：失败保留对话框 + 内嵌诊断区（复用 `_classifySshError`）+ 「改用户名重连」原地按钮 + 「上一步」；密钥改为按配置 id 持久化（已有 secure storage）。

### P0-8 `run_tests` 带 `cwd` 时本地路径拼错，验证环节直接坏

- 证据：`verify_tool.dart:44` `final full = cwd.isEmpty ? command : '$cwd && $command';` —— **缺 `cd `**。
  该 `full` 在本地分支 `verify_tool.dart:56` 直接交给 `executeDevShell` 执行 → shell 把 `subdir` 当命令执行 → `command not found`。
  （远端分支 `verify_tool.dart:60` 是 `'cd $root/$cwd && $command'`，正确 —— 于是又是"本地坏、远端好"的不一致。）
- 影响面：`run_tests` 是 `kDevInstruction` 第 5 步「验证」的唯一入口（`dev_context.dart:146`），坏了等于**AI 编程闭环断在验证上** → 模型只能"写完就说好了"。
- 另一处：`cwd` 未禁 `..`/绝对路径（远端分支直接字符串拼接），与 `git_tools.dart:70-73` 已做的 path jail 不一致。
- **修复**：`full = cwd.isEmpty ? command : 'cd ${shellQuote(cwd)} && $command'`；补 path jail；补一条单测（现有 `dev_embedded_test.dart` 未覆盖带 cwd 分支）。

### P0-9 远端命令**根本没有退出码**：测试失败会被当成功（最危险的一条）

- 证据：`ssh_environment.dart:184-197` 用 `client.run(command)`，而 vendored dartssh2 的
  `SSHClient.run` 签名是 **`Future<Uint8List> run(...)`**（`third_party/dartssh2/lib/src/ssh_client.dart:409`）
  —— 合并 stdout+stderr 返回，**结构上拿不到 exitStatus**（要 exitStatus 必须用 `execute()` 自管 `session.exitStatus`）。
- 后果链：`ssh_tools.dart:226-231` 只要不抛异常就 `ToolResult(content: …)`（`isError` 缺省 false）
  → 模型看到"有输出、无 error" → 判定命令成功。
- **用户看到**：`run_tests` 跑 `pytest`/`npm test` 全红，AI 回「测试已通过，现在提交」→ **假成功 + 假验收**。
  这是"AI 编程"最不可接受的一类错误：它不是失败，是**把失败演成成功**。
- 对照：Termux intent 通道**有**退出码（`termux_intent.dart:55-67` 解析 `__TYL_EXIT__=`），
  但一旦回落到 SSH（Termux 未开 allow-external-apps、或远程电脑后端）就失明；且 P1-9 那条"缺 EXIT 行判成功"雪上加霜。
- **修复**：`ssh_environment` 增 `executeFull()` 走 `client.execute()`，返回 `(stdout, stderr, exitCode)`；
  `ssh_tools` 输出统一为 `exit=N` + `[stdout]/[stderr]` 分段，`exit!=0 → isError=true`。

### P0-10 大文件死角：读不动、写不了、逃生口是假的

- 证据链（四处互相咬死）：
  1. `file_tools.dart:94-96`：`if (len > kReadFileLimit * 2) return ToolResult.error('文件过大…仅支持读取前 …KB')` —— **超 ~16KB 直接拒读**；
  2. `read_file` 参数只有 `path`，**无 offset/limit**（`file_tools.dart:80-84`）；
  3. `ssh_read_file` 从头截断 8192 字符、同样无 offset（`ssh_tools.dart:24/359-361`）；
  4. 唯一的写是 `write_file`/`ssh_write_file` **整文件覆盖**（≤64KB，`ssh_tools.dart:27/392`），无 append、无按 old_string 局部替换；
  5. 上下文溢写给模型的逃生提示写著「可用 read_file 指定 offset 回读」（`lib/agent/context_eng/spill.dart:28`）——**该参数不存在**；
     且溢写文件落在 `ApplicationSupport/agent_spill/`（`chat_provider.dart:2174-2176`），越出 `read_file` 的 workspace 白名单，回读也会被拦。
- **用户看到**：让 AI 改一个 800 行的文件 → 先"文件过大读不了"，或读到前 8KB 断章取义；
  改的时候只能整文件重写，端侧 4B 模型重写大文件**必然丢内容**，用户第二天发现文件被写坏。
- **这是"AI 连上环境也干不成活"的直接原因**（比连不上更致命，因为连接成功后才暴露）。
- **修复**：① `read_file`/`ssh_read_file` 加 `offset/limit`（并让 spill 提示真正可用、spill 目录纳入白名单）；
  ② 新增 `edit_file` 远端版 `ssh_edit_file(old_string,new_string)`（照本地 `createEditFileTool` 语义）；
  ③ 新增 `fs_append` / `fs_delete` / `fs_move` / `fs_mkdir`。

### P0-11 本地 git 闭环断裂：不能 init、不能 pull，还把人指向不存在的工具

- 证据：`embedded_git.dart` 的 `LocalGit` 对外只有
  `isRepo / status / diff / log / commit / push / clone`（`:55-99`）—— **无 init、无 pull、无 branch/checkout/stash/remote-add**。
- 又：`dev_shell` 描述明说"没有 git"（`embedded_tools.dart:141`）→ 本地后端**没有任何途径**补齐这些操作。
- 更糟：`git_clone` 的报错文案是「目标目录已是一个 git 仓库…更新代码请用 **git_pull**」（`git_tools.dart:375-376`），
  而 `git_pull` **不存在于注册表**（`kDevToolNames` 17 个里无它，`builtin_tools.dart:111-129`）
  → 模型照提示去调不存在的工具，得到「未知工具」，然后原地打转。
- 另：JGit commit 未见设置作者身份（`DevGitPlugin.kt` 无 user.name/email 配置）→ 全新目录首次 commit 大概率 `Author not set`（需实测确认）。
- **用户看到**：「帮我把这个项目变成 git 仓库并首次提交」→ 做不到；克隆下来的仓库想更新 → 走不通。
- **修复**：JGit 桥补 `init`（自动写占位身份）/`pull`/`branch`/`checkout`/`remoteAdd`；或注册 `git_pull`；
  并在**注册表与文案之间加一道一致性检查**（所有工具描述/错误文案里提到的工具名必须在册，可用单测保证）。

### P0-12 对话界面对「在哪个环境干活」零可见，导致假成功无法自证

- 证据：`lib/screens/home_screen.dart` 与 `lib/widgets/*.dart` grep「工作区 / Dev / workspace」**零命中**。
  对话里看不到：当前工作区名、后端类型（本地沙盒 / 内嵌 / Termux / 远程电脑）、SSH 是否已连、当前任务。
- 与 AGENTS.md 记录的历史投诉吻合：Phase E 时期用户报「**123.py 创建报成功是假的**」——用户根本没有地方核对 AI 到底连上了什么环境。
- **修复**：对话顶部一条环境胶囊（工作区名 + 后端徽标 + 连接状态，点击直达 Dev Tab）；工具卡标注执行通道（SSH / RUN_COMMAND intent / 内嵌沙箱 / JGit），这一条同时解决 P1「用户看不出走的哪层」。

### P0-13 工具级审批（pre-execute `ask`）**整条链是死代码**，生产环境永不触发

- 证据（独立复核）：
  - `lib/agent/tools/pipeline.dart:65-70`：只有 `preListeners` 返回 `ask` 才会调用 `preApprover`（即 ApprovalDialog）。
  - 全仓 `preListeners` 只有 3 处出现：`pipeline.dart:44/54`（字段声明）、`loop/agent.dart:150`（构造参数）、`:243`（原样透传）；
    **生产唯一构造点 `chat_provider.dart:1709` 从不传 `preListeners`** —— 全仓唯一传它的地方是 `test/agent/pipeline_test.dart:102`。
  - `lib/agent/hooks/hooks.dart:53-54` 的 `AgentHooks` 只有 `preStep` / `result` 两个注册口，**没有 pre-execute 注册口** → 想从 hooks 侧注入也无门。
- **后果**：`main.dart:84` 那个"允许调用工具「X」？"确认框**一次都不会出现**。项目里写得最完整的审批 UI 是死代码，
  真正在跑的只有沙箱升级审批（还被 P0-2 掐死）。**等于开发者模式没有任何工具级人工闸门。**
- **修复（唯一正确接点）**：`chat_provider.dart:1709` 补传 `preListeners`，给 `AgentHooks` 加 `onToolPreExecute`；
  写一个 `DevSafetyPreExecuteListener` 按 `dangerousCommandPolicy` + jail 判定返回 allow/ask/deny —— 这一步同时让 P0-1 的策略设置活过来。

### P0-14 三条审批链互不连通：用户批准了升级，ssh 侧照样被黑名单硬拒

- 证据：4 个黑名单调用点里**只有 `embedded_tools.dart:162-163` 检查 `effectiveModeOf(args) != dangerFullAccess`**；
  `ssh_tools.dart:211/283`、`verify_tool.dart:51`、`git_tools.dart` **完全不看 mode**。
- **用户看到**：模型请求升级 → 用户批准 → ssh_exec 仍回「危险命令被拒绝」→ 模型以为没批准，再请求一次 → 死循环烧 round。
- **修复**：所有 Dev 工具统一从一个 `DevSafetyGate` 读 `effectiveModeOf` + settings 策略；批准后同类命令会话内放行。

### P0-15 审批等待**无超时、不可取消**，切后台即整回合永久卡死

- 证据：`tool_executor.dart:72` `await approver(...)` 在第 3 段，而 `.timeout()` 在 `:121` **只包 `tool.execute()`** → 审批不受超时保护；
  `main.dart:57/99` 两个 `showDialog` 均 `barrierDismissible: false`，全文件无 `Timer`/`timeout`；
  `agent.dart` 的 `cancel()` 只 `_cancelCompleter.complete()` + `adapter.cancel()`，**不 dismiss 挂起的审批框**。
- 叠加：无「本次会话全部允许」批量授权（全仓 grep `全部允许/alwaysAllow/sessionGrant` 零命中）、无审批留痕（不写 session log）。
- **用户看到**：AI 跑到一半弹确认框，用户接个电话回来 → App 卡在"执行中…"，停止按钮无效，只能杀 App。
- **修复**：审批 `await` 包 `Future.timeout(90s → 自动拒绝并回填"用户未响应")`；`cancel()` 里 dismiss 挂起对话框；加会话级 grant + 留痕。

### P0-16 `ssh_exec` 一次可串联任意多条命令，审批粒度形同虚设

- 证据：`ssh_tools.dart:275` `fullCommand = 'cd ${remote.root} && $command'`，`command` 直接来自模型；
  全仓对 `;` / `&&` / `|` **无任何校验**（grep 零命中）；审批粒度是"一次工具调用"，而链 B 又是死的（P0-13）。
- 反讽：`&&` 前缀反而给 `(^|[;&|]\s*)` 提供锚点 —— 实测 `cd /tmp && su` 命中「提权」，
  即**前缀拼接只增加误杀、不增加防护**。
- **修复**：分词后按"每条子命令"分别判定与审批，把分段列表展示给用户逐条勾选。

`\rm -rf /`、`/bin/rm -rf /`、`env rm -rf /`、`command rm -rf /`、`rm -fr /`、`rm -r -f /`、

**根因是设计而非正则写歪**：扫的是**未分词的整条 shell 串**，无法区分「命令位」与「参数位/字符串位」，
于是分不清 `dart format`（格式化代码）与 `mkfs`（格式化磁盘）、`npm run sync`（脚本名）与 `sync`（刷盘）。

### 该重写的 7 条（按性价比）

1. **`清空内存 \bsync\b`** —— 建议整条删（真 `sync` 无破坏性，Android 非 root 根本写不了 `/proc/sys`），只留 `>\s*/proc/sys`。**一行消除最大误杀源。**
2. **`格式化 \bformat\b`** —— 删掉，只留 `mkfs|mke2fs`。零成本。
3. **`挂载`** —— 锚定命令位并排除 `--grep=`/`-name` 取值位（Termux 非 root 本就 mount 不了，收益极低）。
4. **`rm -rf 根目录` + `删除系统目录` 合并重写并引入 jail** —— 路径规范化后落在工作区根之下即放行；直接解决 Termux `/data/data/...` 与 `/data` 字面撞车。
5. **`git 强推`** —— `--force(?!-with-lease)` + 补 `\s-f(\s|$)` 与 `+ref`（当前是反的）。
6. **`提权`** —— `sudo` 补命令位锚定（`su` 有、`sudo` 没有，不一致）。
7. **`重启/关机`** —— 命令位锚定 + 补 `telinit`。

**止血价值**：仅第 1、2、5 三条正则改动，即可当天发版消除约一半误杀，且不引入任何新风险。

## 五、结构性根因（为什么会有这么多洞）

1. **策略/审批"接口存在、实现缺席"**：`allowAsk`、`dangerousCommandPolicy`、`git_push` 审批、`probe()`、token 预算截断 —— 五处"写了签名没写实现"。这类缺陷对用户表现为「设置项是假的」，比崩溃更难发现，因为**它不报错**。
2. **描述与实现各写各的**：`ssh_write_file` 说建目录、`git_push` 说会审批、`dev_shell` 说"没有 git"、`_showSshConfigDialog` 说有个不存在的按钮。缺一道"工具描述 ↔ 实现"的一致性检查。
3. **多真相源**：工作区激活态（内存 vs settings）、镜像路径（两个 sanitize）、执行通道（intent 建目录 vs SFTP 不建）。
4. **没有端到端验收**：Dev 模式测试全在纯函数层（`dev_*_test.dart` 6 个文件），**0 个真机 e2e**（Termux 全链路 / SFTP / JGit / RUN_COMMAND），AGENTS.md 的验收点长期挂空。
5. **为端侧小模型设计时用了"大模型假设"**：36 工具、长 schema、靠模型自觉走审批 —— AGENTS.md 里全是 4B 模型思考中途 EOS、工具协议退化的记录，Dev 层却按理想模型写。

### 优先级判断（如果只能做一件事）

1. **先做第 0 批**（半天）：误杀率从 45-65% 直降一半以上，零风险，当天可发版。
