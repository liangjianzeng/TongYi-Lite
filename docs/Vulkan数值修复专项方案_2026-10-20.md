## 0. 一页结论

**症状**：Ling 3.0 Tiny（GGUF arch `bailingmoe3`，KDA 线性注意力 + MLA + 128 专家 MoE）在 App 里选 Vulkan → 输出乱码。

**实测定位（2026-10-20，全部本机自测，命令见 §5）**：不是偏见、不是慢、不是配置没调对，是**数值算错**，且这台机器上 **Vulkan 没有任何一条可用路径**：

| 驱动 | 结果 |
|---|---|
| stock 高通 Vulkan（V@0800.71） | 建 compute pipeline 即 `vk::Device::createComputePipeline: ErrorUnknown` → abort(EXIT=134)。**JNI 那 4 个 workaround flag 开与不开都崩** |
| APK 内置 turnip（JNI 无条件强开） | 能跑，但 op 级数值大面积错 → 端到端确定性乱码 |

**op 级（test-backend-ops 对比 CPU，同工装同版本）**：

| op | 结果 |
|---|---|
| `SSM_SCAN` | **12/12 FAIL**，ERR 0.147 / 0.411 / 0.681 / 0.745 / 0.866 / 0.869 / 0.914 / 0.924 / 0.945 / 0.991 / 1.048 / 1.145（阈值 **2e-7**）→ 全废。含 `n_seq_tokens=1`（decode）与 32/300（prefill） |
| `MUL_MAT` | **247 FAIL / 1132**，且**不限量化**：f32 76、bf16 66、f16 32、q4_K 10、q5_K 10、q4_0 3、iq* 各 2、mxfp4/nvfp4 3、q1_0/q2_0 3 |
| `MUL_MAT_ID` | **8 FAIL**：`q4_0` ×4、`iq3_s` ×4，全部落在 **n=64 / n=300**（多 token 批次）；`n=1` 与 f16/bf16/q4_K/iq2_xs 全 OK |
| `SSM_CONV` `ADD_ID` `ROPE` `RMS_NORM` `SOFT_MAX` `GET_ROWS` | 全 OK |

**端到端（同一二进制 / 同一 gguf / 同 prompt / `--temp 0 -s 42`）**：

| 配置 | 输出 | prompt / gen tok/s |
|---|---|---|
| Vulkan 默认 | `Per?...olateutanCOPE distraction-distacity?!-dist…` 乱码 | 9.2 / 19.1 |
| Vulkan + App 的 4 flag | `The user is asking about "cargo cult" … Karl Popper's book` ← **英文流利但答非所问**（分布已被算坏） | 8.8 / 16.9 |
| Vulkan + `DISABLE_F16=1` | `>C worst>C支点+C审 razachaoE[v commission/ap?…` | 8.3 / 17.9 |
| Vulkan + `DISABLE_MMVQ=1 NO_SUBGROUP=1` | `无前yss（图去的调料，(路人哈哈，拜登打我。】🤥🤞🤕🤬…` | 8.6 / 17.2 |
| **OpenCL** | 正常中文 | 19.4 / 6.4 |
| **CPU** | 正常中文 | 1.8 / 2.4 |

> **四种 Vulkan 配置错法各不相同 → 不是单个量化内核的点 bug**，而是 `matmul` / `matmul_id` / `ssm_scan` 这一族着色器在这颗 turnip 上整体不可靠。
> **奖金（2026-10-20 用户纠正后重写，撤回原"3 倍"说法）**：Vulkan 算对约 **17-19 tok/s**，
> 但**这不构成"3 倍于 OpenCL"的论证**。自研 batched MoE 落地提交 `ae8ba172`（2026-10-14，
> **同一块 Adreno 830 真机**）记录 **prefill 149 t/s / decode 14-22 t/s，probe NMSE=0**。
> 今天 OpenCL 只有 6.4（工装）/3.7（App）-> 那是**相对自己历史值的 2-3 倍回退**，不是 OpenCL 的天花板。
> 所以 Vulkan 这条线的价值要重述为：① 今天它是**完全不可用**（0 可用后端），修好才有第二条腿；
> ② 它给"OpenCL 回退为什么"提供**同机同形状的对照面**（同一 op 集在两后端各测一次，
> 坏在哪一侧一目了然）；③ 性能上它与 OpenCL 的历史最好值只是**持平**，不是代差。
> **推论**：OpenCL 从 14-22 掉到 3.7/6.4 的回归，是与本专项**同级**的目标，且已有可 bisect 的锚点 commit。

## 1. 已确证的代码落点

| # | 位置 | 事实 | 后果 |
|---|---|---|---|
| C1 | `ggml-vulkan.cpp:1616-1632` `gpu_pipeline_configs` | 只有 `AMD_RDNA1` / `AMD_RDNA2` 两条 | Adreno 上 `get_subgroup_size()` 返回 **0** → `required_subgroup_size=0`（:1964、:5133）→ **完全照抄驱动自报 subgroup 宽度** |
| C2 | 设备自报（实测） | turnip：`Adreno 830v1 … warp size:128 shared:65536 int dot:0`；stock：`Adreno 830 … warp size:64 shared:32768 int dot:0` | 同一块 GPU 两个驱动自报 **subgroup 宽度相差一倍、shared memory 相差一倍** → C1 使这个差异直接进着色器 |
| C3 | `ggml-vulkan.cpp:2896-2965` | `use_subgroups` 仅作用于 `dequant_mul_mat_vec`（dmmv）；出错的是 `matmul`/`matmul_id`/`ssm_scan` 家族（`ggml_vk_get_mul_mat_mat_pipeline_map(..., mul_mat_id=true)`，:6107/7539） | **`GGML_VK_NO_SUBGROUP` 管不到坏的那条路**；我们现在连绕的开关都没有 |
| C4 | `tongyilite_jni.cpp:2895-2946` | 4 个 flag + `GGML_VK_TURNIP` **无条件强设**，注释自陈是在 **Adreno 825 + stock 驱动 + 稠密模型** 上导出的 | 把 825 的结论当全设备真理；830 上"关 turnip 用系统驱动"反而是 abort |
| C5 | `ggml-vulkan.cpp` 设备能力（实测） | `int dot: 0`、**`matrix cores: none`** | 无 coopmat、无 int8 dp4a → 只能走 dequant/mmv 家族，正是坏的那一族 |
| C6 | 设备 `/data/local/tmp/test-backend-ops`（10-20 03:25） | 只注册 `GPUOpenCL` + `CPU`，**没有 Vulkan** | "内核门"从未覆盖 Vulkan；8-04 基线的 `Vulkan 8.60 tok/s` **从未验过输出正确性** |

**C1+C2 合成 H1**：我们从不校验驱动自报的 subgroup 宽度，而 turnip 在 a8xx 上报的 128 与真机/stock 的 64 冲突。若 a8xx 真实 subgroup 是 64，则所有按 128 做归约/分块的着色器必然算错 —— 与"多 token 批次才错、单 token OK"的实测形状完全吻合。

## 2. 候选根因与判决实验

| ID | 假设 | 判决实验 | 判据 | 成本 |
|---|---|---|---|---|
| **H1** | **subgroup 宽度**：turnip 自报 128 与实际不符，我们照抄（C1/C2） | 在 `ggml-vulkan.cpp` 设 `device->subgroup_size` 处加 env 覆盖 `GGML_VK_FORCE_SUBGROUP_SIZE=64/32`，另加 `GGML_VK_FORCE_NO_SUBGROUP_ARITH=1`；重跑 §5 op 扫描 | FAIL 从 `SSM_SCAN 12 / MUL_MAT 247 / MMID 8` 归零或大幅下降 → **H1 成立** | 0.5 天 |
| **H2** | **我们 fork 的着色器假设错**（与 GPU 代次无关） | 同工装同 op 集在 **第二台 Mi 10 / Adreno 650(a6xx, turnip 成熟)** 上跑 | 650 也 FAIL → fork 侧问题（继续 H2 深挖）；650 全 OK → 转 H3 | 0.5 天 |
| **H3** | **turnip a8xx 不成熟**（我们只能等/换驱动） | H2 判定为"650 OK / 830 FAIL"后：用 `third_party/mesa-kgsl` 线自编的更新版 turnip 替换 APK 内那颗，重跑 op 扫描 | 新版本 FAIL 消失 → 驱动版本轴成立，走升级+上报 | 0.5–1 天 |
| **H4** | **f32/f16 基础 matmul 也错**（247 例含 f32 76）指向比 subgroup 更基础的问题：buffer 对齐 / split_k reduce（`mul_mat_split_k_reduce.comp`）/ shared memory 大小（32768 vs 65536 差异） | 把失败用例缩到最小 shape（f32、K 对齐、无 split-k），逐 pipeline 定位；必要时 dump pipeline 名 + wg 维度 + specialization 常量 | 定位到单一 pipeline family | 1 天 |
| **H5** | 量化 dequant 路径独立损坏（`q4_0`/`iq3_s` 特征） | 用 `dequant` op 单独扫（test-backend-ops 支持 `DEQUANT`）对比 CPU | 单独 FAIL → 独立子问题 | 2 小时 |

H1 优先（判据最干净、改动最小、且 C1/C2 已经把它顶到嘴边）。H2 是最便宜的**分叉器**：一次实验就把"我们的错"与"驱动的错"劈开，**必须紧跟 H1 之后做**，否则后面所有工作都可能白做在错误的归因上。

## 3. 里程碑与 go/no-go

| 阶段 | 内容 | 产出 | 门槛 |
|---|---|---|---|
| **M0** | capability override env + op 扫描矩阵（0.5 天） | `GGML_VK_FORCE_SUBGROUP_SIZE/_NO_SUBGROUP_ARITH`；FAIL 计数表（每 env × 每 op） | 若 FAIL 归零 → 直跳 M3；若无变化 → **H1 证伪，记录后转 H2** |
| **M1** | 第二设备对照（Adreno 650，0.5 天） | 650 的 FAIL 表 | 决定走 fork 侧(M2) 还是驱动侧(M3') |
| **M2** | 最小复现 + SPIRV 级定位（1 天） | 单 op 最小 shape 复现脚本 + 嫌疑 pipeline 清单 | 能把 FAIL 收敛到 **≤2 个 pipeline family** 才继续 |
| **M3** | 修复尝试（1 天）：给 Adreno 补 `gpu_pipeline_configs` 条目 / 传 `required_subgroup_size`；或对坏 family 做设备门控回退（shmem / dequant+matmul） | 补丁（限 `ggml-vulkan/**`）+ 复验 | `SSM_SCAN/MUL_MAT/MUL_MAT_ID` FAIL=0 且端到端中文输出正确 |
| **M4** | 端到端复验 + 基准（0.5 天） | `llama-cli` 三连 + App 一轮；**正确性作为 tok/s 的前置条件**；8-04 的 Vulkan 基线作废重建 | 输出正确 + tok/s 落表（预期 ~19） |
| **M5** | 上门禁（0.5 天） | `tool/vk_gate.sh`（编工装→跑 op 扫描→FAIL==0 断言）+ `known_bad_kernels` 数据表 + JNI 设备门（A 止血产物并入） | CI 里 Vulkan 坏内核**活不过当天** |

**Stop-loss（硬，规则保留备查）**：M0+M1 一天内不能把 FAIL 收敛到单个 family；或 M2 一天内收敛不到 ≤2 个 pipeline → **停止 B，执行 A 止血**（830 上按能力表禁 Vulkan + 设备门），B 转为"跟踪 turnip/Mesa a8xx 上游"。

**执行结果（2026-10-20 当日，详账见 `wt/vk-line/docs/Vulkan专项实施记录_2026-10-20.md`）**

| 阶段 | 结果 |
|---|---|
| M0 | **命中即跳 M3**：`FORCE_SUBGROUP_SIZE=64` 毫无变化（宽度不是因），`FORCE_NO_SUBGROUP_ARITH=1` 令 `SSM_SCAN` 12/12 转 PASS -> H1'（subgroup 归约**代码路径**）成立 |
| M1 | 650 数据到手；stock 驱动两代皆不可用（830 abort / 650 `pc=0` 段错误）；a6xx turnip 暴露**第二个独立缺陷**（`MUL_MAT_ID` 433/937 FAIL，**不被本表覆盖**） |
| M2 | 收敛到 **1 个 family**（subgroup 归约），三个坏 op 同因 -> 无需再分 pipeline |
| M3 | 驱动表落地 `ggml-vulkan.cpp`（driverID + deviceName 匹配，双向诊断 env 保留）。**默认无 env**：`SSM_SCAN 12/0`、`MUL_MAT_ID 939/0`、`MUL_MAT 1132/0`；反向对照 `FORCE_SUBGROUP_ARITH=1` -> `SSM_SCAN 0/12 FAIL`（门禁确有牙） |
| M4 | 端到端三连全部正常中文、`gen 19.0-19.2 t/s`；8-04 基线已就地标注作废；新基线 `docs/backend_benchmark_2026-10-20.md`（正确性为 tok/s 前置）。**App 侧待一轮用户点击**（APK 构建中） |
| M5 | `vk_gate.sh` **GATE PASS**（默认全绿 + 反向对照复现 + stock 按表排除）；表按 `driver × device_class` 建，并引入 `known_fails` 失败预算 |

**Stop-loss 未触发**：M0+M1 当日收敛到单一 family，M2 收敛到 1 个，无需转 A 止血。
**新立目标（同级）**：OpenCL 相对 `ae8ba172`（同机 decode 14-22 t/s）的 2-3 倍回退，锚点已知、可 bisect。

**明确不做**：不为跑通而放宽 op 阈值（2e-7 不许动）；不为出数字而拿 `MUL_MAT_ID n=1` 通过冒充可用；不在 `ggml-opencl/**`、`kernels/*.cl`、`mesa_bionic/mesa_run/moe830` 上做本专项任何改动（隔离约定 §4）。

## 7. 诚实清单（未决 / 风险）

- 我不知道 turnip 那颗是不是我们自己编的、能否换版本 → **决定 H3 这条轴能不能测**。
- turnip 自报 128 到底是"turnip 谎报"还是"a8xx 真的是 128、stock 报 64"——**目前没有第三方权威值**；H1 若两侧都试（64/32）仍 FAIL，就不能再赖自报值。
- `MUL_MAT` 连 f32 都错，可能不是 subgroup 而是更基础的 shared memory / split-k 问题（H4）；若 H1 判负，H4 优先于 H3。
- op 级用合成形状，**没覆盖 KV cache 量化（JNI 硬编码 k=q4_0/v=f16，无 env）、MLA 的 rope_multi、真 MoE 形状 `n_mats=128 n_used=8 k=1536/512`**。这些只能靠 `llama-cli`/App 端到端覆盖，不能靠工装下结论。
- 本次全部证据来自 **M332BF + 内置 turnip（14.2MB 单颗）**；换设备/换驱动版本后需重跑，不得沿用本表。
- 需要用户在 App 里点数的只有 M4 的 App 侧复验一轮（Flutter UI 不可自动化）。

## 附录 A（2026-10-21 01:0x）：专项扩到第二世代，以及 e2e 卡点的定案路径

### 1. 结论变更（用户指令）

Adreno 830 停止作为测量设备，测量主设备改为 **Redmi K40 / Adreno 650**（`100.67.150.120:5555`）。
`a8xx` 已定案的 subgroup 归约缺陷与其修复保持不变；本节只增不改。

### 2. a6xx 的新缺陷与处置（已提交，见 `wt/vk-line` 分支 `spike/vulkan-line`）

`MUL_MAT`/`MUL_MAT_ID` 在 **17 个量化类型**上返回错误值（`ERR ≈ 4.15`，阈值 `5e-4`），
按类型而非形状切分；同类型用例 CPU 后端全过；a8xx 同批用例全过 —— 故判定为 turnip a6xx
独有缺陷。处置沿用同一设计原则：**数据表 + 世代位**，`supports_op` 对这些类型返回 false
（张量落 CPU：慢而对），诊断 env `GGML_VK_FORCE_MATMUL_TYPES=1` 作反向对照。
真机门禁 `GATE PASS`，且反向对照能复现 57 FAIL。

### 3. e2e 仍未通过，卡点是分配失败而非数值

`llama-cli -dev Vulkan0` 在权重加载后死于 `vk::Device::allocateMemory: ErrorOutOfDeviceMemory`，
在 `-ngl 99/24/8`、`-c 256/512/1024`、三个 host-memory env 下都一样；设备 `MemAvailable 8.5 GB`。

代码事实（`ggml-vulkan-buffers.cpp:40-179`）：分配有两个不同出口 ——
候选内存类型必须满足 `memoryHeaps[heapIndex].size >= size`（`:42`），否则**根本没问驱动**
就抛 `No suitable memory type found`；而我们拿到的是 `allocateMemory` 抛出的
`ErrorOutOfDeviceMemory`，即**驱动收到过请求并拒绝**。UMA 分支的候选已含纯 host-visible 兜底。

**下次设备一回来的定案动作（三条，不要再猜开关）**：

```sh
GGML_VK_LOG_MEMORY=1        # 堆上报多少、是否 DEVICE_LOCAL
GGML_VK_LOG_ALLOC_FAILS=1   # 被拒那次问了多大、候选 flags、落在哪个堆、堆多大（已实现并编入 .so）
GGML_VK_SUBALLOCATION_BLOCK_SIZE=67108864   # 判别单 buffer 上限是否参与本问题
```

注意：`GGML_VK_SUBALLOCATION_BLOCK_SIZE` 在本树只被 `get_max_size` 读取，**不是**申请粒度；
"子分配器一次要 1 GB 整块"的说法已撤回（同撤回"三个 host-memory env 是死旋钮"，
它们在 `ggml-vulkan-buffers.cpp:219-244` 被消费）。

### 4. JNI 设备门的正确形状（M5 待办，含为何不能在这里写机型判断）

现状：App 侧只判断"注册表里有没有 Vulkan 设备"，没有任何按量化类型的能力判断；
且日志把 825 的实测结论打印成通用结论（已改为只打印所选设备名）。

选择后端发生在 `llama_model_load` **之前**，此刻拿不到权重的量化类型，因此**能力探测必须放在模型加载之后**：

1. 从 GGUF 元数据取 `general.file_type`（`llama_model_meta_val_str` 或等价 API），映射到 `ggml_type`；
2. 用 `ggml_init` + `ggml_new_tensor` 造一对极小张量（`[k,m]` 权重类型 × `[k,n]` f32）与
   `ggml_mul_mat`（必要时加 `ggml_mul_mat_id`）；
3. `ggml_backend_dev_supports_op(vulkan_dev, op)` 为 false 即**回落 OpenCL/CPU**，
   并在推理日志里点出被拒的类型名。

这样 App 的判断**自动继承 ggml 的驱动表**，不需要、也不允许出现任何 `if(device==...)`；
新坏类型只需进 `ggml-vulkan.cpp` 的表和 `tools/known_bad_kernels.tsv` 一处。
未做原因：设备离线无法运行时验证，不把未验证代码塞进模型加载路径。
