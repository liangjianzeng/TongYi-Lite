## 1. 五层契约（从此「只加不改」）

改任何一层的**破坏性**动作，都必须走 `contractVersion` / `manifestVersion` 升版 + 双读期 + 面板告警；
**加**东西随时可以。

| 层 | 冻结了什么 | 代码在哪 | 违反之后的下场 |
|---|---|---|---|
| **L0 平台不变量** | 插件永不 `throw`（一律 `Outcome`）；`apply()` 只注册、零能力调用；每个贡献物必须挂 `ctx.effect`；每个 await 边界必须复查 `cancelToken`；disposer 逆序 + 单个失败不阻断其余 | `plugin_sdk/lib/src/{outcome,hook,ctx}.dart`、`plugin_kernel/lib/src/fiber.dart` | conformance 套件当场红（`plugin_sdk/lib/testing.dart` 六组） |
| **L1 声明层** | `plugin.json` 的字段集、类型、取值范围、未知字段只告警不拒（向前兼容）；`manifestVersion=1` | `plugin_sdk/lib/src/{manifest,validate,deprecations}.dart` | 校验报告逐条指出 path/code/hint，插件停在 `rejected` |
| **L2 能力层** | 8 个能力键 + `contractVersion` + 能力→权限的唯一映射表；`Capability{key,available,unavailableReason,warmUp,probe}` | `plugin_sdk/lib/src/capability.dart`、`plugin_kernel/lib/src/capability_registry.dart` | 缺能力 → `missingCapability` **带本机真实原因**；未声明权限 → `permissionDenied` 带「该加哪一行」 |
| **L3 呈现层** | 4 种 `SlotKind` × 3 种 `SlotScope` + 11 个宿主槽的 id/形态/容量 + 「最低 priority 胜 / 同格同优先级报错点名占用者 / chain 的 select 必须纯」 | `plugin_sdk/lib/src/{slot,slot_contract}.dart`、`plugin_kernel/test/architecture_test.dart` | 占用冲突报错点名占用者；悄悄加/改槽 → 架构测试红 |
| **L4 行为层** | flow 的 8 个 op 白名单 + 每个 op 的隐含权限 + `FlowResult` 三态（completed/cancelled/error）+ 步骤级 `abort/skipWithWarning/cancel` | `plugin_sdk/lib/src/flow.dart` | 未知 op → 校验期就拒（不是跑一半炸） |
| **L5 治理层** | 信任三级（trusted/declarative/extension）、11 个权限、启用集、方案档、预算与长度上限、诊断三件套（effect 树/槽账本/trace 日志） | `plugin_sdk/lib/src/manifest.dart`、`plugin_kernel/lib/src/{config_layers,plugin_service,trace}.dart` | 越界操作返回 `permissionDenied`；配置改崩只影响单个插件 |

## 2. 宿主槽（11 个，冻结件）

代码：`packages/plugin_sdk/lib/src/slot_contract.dart`（作者侧也可 `import 'package:plugin_sdk/slot_contract.dart';` 单文件取用）。

| 槽 id | kind | scope | 容量 | 语义（谁能填 / 怎么渲染） |
|---|---|---|---|---|
| `app.input.left` | list | sessionMaybe | — | 输入框左侧图标位（拍照/相册那排的位置） |
| `app.input.right` | list | sessionMaybe | — | 输入框右侧图标位（插件主入口，hello 示例就填这里） |
| `app.input.activity` | list | session | — | 输入区上方的活动条（「正在抽词…」这类进度） |
| `app.input.attachments` | list | session | — | 附件条上的插件附件徽章 |
| `app.composer.dock` | list | session | — | 输入框上方的停靠区（听写的词卡队列就放这） |
| `app.input.dock` | **single** | session | **4** | 互斥的整块停靠区，最多 4 个候选，**最低 priority 的那个渲染** |
| `app.input.overlay` | **single** | session | — | 输入区遮罩（接管态的确认条） |
| `app.composer.takeover` | **chain** | session | — | 发送链接管：`select` **必须是纯函数**，链上按序问「这个输入你接不接」 |
| `app.chat.node` | keyed | session | — | 气泡区的自定义节点（按 key 对位渲染） |
| `app.tool.view` | keyed | session | — | 工具卡的自定义视图 |
| `app.settings.section` | list | **root** | — | 设置页分区（不依赖具体会话） |
| `app.plugins.tab` / `app.plugins.detail.action` | list / keyed | — | — | 治理面板自己用的两个槽（`kPanelSlotContract`） |

**冻结的三条渲染语义**（有测试钉住，`plugin_sdk/test/slot_contract_test.dart`）：
1. 一个格子活着的条目里**最低 priority 的那个渲染**（与能力注册表**同一套心智：数字小者优先**）；
2. 同一格子同一优先级再来一个 → **报错并点名占用者**，绝不静默遮蔽；
3. `reportEntryError(..., abdicate)` 让崩溃的条目**主动让位**，而不是把整条输入区带崩。

> 插件也能**拥有槽**：`ctx.slots.declare(SlotDef(ownerPluginId: 自己, id: '<自己的id>.*'))`，
> 别人的插件可以来填 —— 这是「插件长插件」的落点（方案 §4.12）。越界声明会被拒。

## 3. 能力键（8 个）+ 权限映射（唯一真相）

代码：`plugin_sdk/lib/src/capability.dart` 的 `ServiceKeys` 与 `impliedPermissionFor()`
（**校验器 / 测试夹具 / 内核三处共用这一张表**，防三方漂移）。

| 能力 id | 接口 | 需要声明的权限 | P2/P4 谁来提供 |
|---|---|---|---|
| `llm.complete` | `LlmComplete` | `llm:chat` | 现有聊天Provider |
| `llm.vision` | `LlmVision` | `llm:vision` | 现有 API 视觉链路 / 本地 VLM |
| `app.speak` | `Speak`（含 `SpeakRequest/Progress/Phase`） | `tts` | **Edge-TTS 适配器**（P4，含缓存/序号/停止语义） |
| `app.capture` | `Capture` | `camera` | `home_screen._pickImage` 抽出（P2） |
| `app.store` | `Store` | `storage:plugin` | 命名空间 `plugin:<id>:` 的 KV |
| `app.interact` | `Interact` | （无） | 通用问答弹窗（「间隔几秒」就靠它） |
| `asr.transcribe` | `Transcribe` | `speechRecognition` | 现有 ASR |
| `net.search` | `Search` | `webSearch` | 现有 SearXNG |

**冻结的规则**：
- `ServiceKey(id, contractVersion)` 相等性看 **(id, version)** 两个字段；
- 同名实现 **priority 小者胜**，冲突报错点名占用者，**被遮蔽的实现不销毁、卸载后自动浮回**（离线 TTS 因此是「另一个插件」而不是 if-else）；
- 只有 `trusted` 级插件能 `ctx.capabilities.provide(...)` 贡献/替换实现；
- `available=false` 的顶层实现必须给出 `unavailableReason`，`require` 时**原样转达**（不再是一句「不可用」）。

## 6. 预算与硬限制（防「一个坏插件拖死 app」）

| 限制 | 值 | 出处 |
|---|---|---|
| `plugin.json` 大小 | ≤ **64 KB** | `kMaxManifestBytes` |
| `prompt.md` 大小 | ≤ **32 KB** | `kMaxPromptBytes` |
| 插件 id | `^[a-z][a-z0-9-]{2,63}$` | `validate.dart` |
| 能力 id / 槽 id | 至少一段点分，段内 camelCase 允许 | `validate.dart` / `isValidSlotId` |
| 参数名 / 文本参数长度 | `^[a-z][a-zA-Z0-9]{0,40}$` / ≤ 4000 字符 | `PluginParam.acceptsValue` |
| 用户可见 `message` | **≤ 120 字符**（断言强制）且不得是技术黑话 | `PluginFailure` 构造断言 |
| 六类失败**必须**带 `hint` | missingCapability / permissionDenied / configInvalid / incompatibleContract / denied / badContent | `_requiresHint` |
| 单槽条目数 | `SlotDef.maxEntries`（`app.input.dock` 冻结为 4） | `slot.dart` |
| 配置写入 | 必须带 `expectedRevision`，撞车报「被别人改过」，**绝不静默覆盖** | `ConfigStore.patchUser` |
| 来源读崩 | 该来源沿用上一次清单；全崩沿用上一次**好树**，并置 `usedLastGood` 让面板显示黄条 | `loader.dart` |

## 7. 生命周期与错误形状（L0 的机器化部分）

**fiber 六态**（逐字对齐 Cordis）：`pending → loading → active / failed → unloading → disposed`。
- **单飞（`inertia`）**：并发 `ensure()` 共享同一次迁移 —— 用户狂点开关不会把贡献物注册两遍（有测试）；
- **epoch 自动重载**：`epoch = 依赖能力的 revision 指纹 + 生效配置指纹（易变值除外）`，
  依赖实现被替换或配置真变了 → 下次 `ensure()` **先卸后装**，不需要重启 app；
- **逆序回收 + 容错**：disposer 反着跑，某个 disposer 抛异常只记进 `disposeFailures`，其余照常回收；
- **`apply` 返回 Err = fiber 停在 failed**，绝不「半激活」（贡献物注册了一半还对外可用）。

`Outcome<T>` 的失败码是**闭集**（10 个）：
`missingCapability, permissionDenied, configInvalid, runtimeError, cancelled, busy,
incompatibleContract, timeout, denied, badContent`。
新增码 = 契约变更，要走评审。

## 8. 作者纪律（写给以后所有插件，包括智能体自己写的）

1. **永不 throw**，一律 `Outcome`；内部异常用 `Outcome.guard/guardSync` 包；
2. `apply()` 里**只注册贡献物、不调能力、不做 IO**（conformance 的「生命周期」组会数给你看）；
3. 每个注册/订阅**必须** `ctx.effect(...)`，否则禁用插件后槽里会留下幽灵；
4. 每个 await 之后**复查 `ctx.cancelToken`**（用户按停止时必须真的停得下来）；
5. 取能力用 `ctx.capabilities.require(key)`，**先判 `isAvailable` 再取**，把 unavailableReason 说给用户；
6. 只在自己的 `<id>.*` 命名空间声明槽；填别人的槽可以，冒充别人不行；
7. 用户可见文案走 `message`（≤120 字、说人话），技术细节进 `cause` 走日志。

## 9. 与 v3 方案的两处偏差（已按更优解落地，请一并确认）

| 偏差 | 方案里写的 | 现在做的 | 为什么 |

**内置插件与验收实例也要过 conformance**：`flutter test test/plugins`（40 项：适配器编排 + 听写全流程 + 内置件体检）。

补充两条 P4 定下的契约（都是被测试/审计逼出来的，不是设计时想到的）：

* **平台入口防 throw**：`PluginService.run` 把插件抛出的异常收进 `Err(runtimeError)`（原文进 `cause`），
  取消信号（`isCancelSignal`）折算成 `Ok(PluginRunResult(userVisible:false))` —— 作者忘没忘 throw，UI 都不该红。
* **取消判定公开化**：取消信号类保持私有，外部只用 `isCancelSignal(e)` / `cancelReasonOf(e)`；
  插件更推荐**早退返回** `Ok(...userVisible:false)` 而不是抛（入口型插件的取消是正常终态）。

P5 又钉上四条（其中前两条是**实例 C 替平台抓出来的缺口**）：

* **隐含权限看上下文**：`llm_extract` 只在流程真的取图时（有 `capture` 步或 `useImages:true`）要求
  `llm:vision`，否则要求 `llm:chat`。引擎路由同理 —— 用户塞了图但插件没声明 `llm:vision`，
  按文本补全处理并 warn，**不替作者偷偷升权限**。
* **提示词占位符三层替换**：步骤 `params` → `ask_params` 当场问到的值 → 用户输入。
  `prompt.md` 因此可以写 `{{count}}`；跑完不许有 `{{` 漏给模型（测试机检）。
* **给人看的数字统一过 `formatCount`**：`5.0 秒`/`8.0 张` 这种尾巴是配置一律为 `double` 的副作用，
  凡进 `message`/`summary`/提示词的数都要它。
* **启用集的唯一真源是 `EnabledStore`**：`PluginService.reload()` 每次扫描前自己 `loader.setEnabledIds(enabledStore.read())`。
  宿主**不需要也不该**自己记得喂（早先靠宿主自觉，结果冷启动全员显示"未启用"）。写开关只有一条路：`setEnabled`。
* **方案档（Profile）只有一条语义通道**：`ProfileStore.compose(active, persistedEnabled, allIds)` 是纯函数，
  runtime 加载与面板预览**必须都读它**（compose == preview，对齐 DSH `composeAndRender`）。档 = `enabled` 白名单（空=不表态）
  + `disabled` 黑名单 + `config` 档位层参数 + `personaId`/`modelId`（null = 不表态，别替用户清行人格）。
  **档读不动（缺档/坏 JSON/读盘抛）一律退回"按你原来的开关走" + 一句警告，绝不因档失败而全员停用。**
  档位层参数用 `ConfigStore.replaceProfile` 整体替换（累加会让档里删掉的键阴魂不散）；用户显式改过的值恒大于档位层。
* **治理面板的状态是契约的一部分**：`active(运行中/启动中) / gated(列出缺项) / rejected(指出 JSON 路径) / disabled(说明是谁关的)`
  四态必须各有各的展示与出路，**任何一态都不许渲染成"可用"**；面板自身在任何插件出错时都不许崩（它是唯一的自诊入口）。
  作者往详情里放动作只能走冻结槽 `app.plugins.detail.action`。
* **声明式插件的实现体由 loader 的 `declarativeFactory` 注入**（app 侧给 `DeclarativePlugin(d, runner: FlowRunner())`）；
  没注入时声明式插件停在 `gated` + `gatedOn: ['flow.runner']`，`FlowHost.startAgent`/`renderExport` 未接线时
  对应原语给 `missingCapability` 并提示改 `onFailure: skipWithWarning`，**不静默糊过去**。
* **app 版本不够 = 「待功能」，不是「你 JSON 写错了」**：`engines.app` 不满足时插件停在 `gated`（描述符保留、**不进 `broken`**），
  并必须带一句可照着做的 `gatedHint`（例："需要 app >=9.9.9（升级 app 后再启用它）"）。面板 chip 与"为什么跑不起来"**优先显示 `gatedHint`**。
  判定顺序冻结：**先启用集过滤，再门控** —— 用户自己关掉的插件不许替他显示"缺能力"。
  （对比：能力缺失也是 `gated`，但那是等宿主接能力；两者都是"环境的事"，都不算作者的错。）
* **切方案档只有一条路：`HostProfiles.switchTo(service, name, sink:)`**，顺序冻结为
  记档 → `service.reload()`（插件集先就位）→ `applyProfileSettings`（人格 / 本地模型 / API 模型）→ **环境真的变了才 `resetContext()`**。
  三个 setter 的 `null` 都是"**档没表态**"，实现方**必须原样不动**；落完要**回读校验**，设置侧拒绝（如人格不存在）必须回报"本机没有"，
  不许留下半截状态也不许假装成功。`modelId`（本地默认）与 `apiModelId`（API 档）是两个独立设置项，**不许合成一个**（会串台）。
* **面板的档位预览只能走 `PluginService.previewProfile(name)`**，它与 runtime 共用 `ProfileStore.compose`；
  面板**不许**自己数插件（"预览说开三个、切完开两个"是最伤用户信任的那种 bug，已在 `test/plugins/host_profiles_test.dart` 钉死）。
* **档目录的坏文件只标坏它自己**：`HostProfiles` 读盘时单文件崩 → 内容记为非法交给内核标 `broken`（面板显示"（读不动）"，仍可点、不崩面板）；
  整个目录读不动 → 当"没有档"，由 compose 的 fail-safe 退回原开关。**任何情况下都不许因为档的问题把用户的插件全关掉。**
* **当前档名与启用集一样是持久化事实**：`ActiveProfileStore`（`FileActiveProfileStore` 写 `文档/plugin_profile.json`，原子 tmp+rename）。
  删掉正在用的档必须自动清空当前档名（不留悬空档）；`loader.knownProfiles` 每次 `reload()` 现读档目录，宿主不需要"记得刷新"。
* **第二套 `app.speak` 实现的接入方式（也是所有"可替换能力"的样板）**：宿主以 `priority: -1` 注册第二份实现，
  靠 `available` 决定它是否参与竞争 —— **不 ready 就说 false，注册表自动浮回被遮蔽的那份**，宿主里不许写 `if (离线开关) … else …`。
  三条附加纪律：① **播控只有一份实现**（`begin/isCurrent/end/stop/play` 委托在线端口），两份播放器必然两套取消语义；
  ② 逐条问 `supports(text)`，**宁可少接不许念错**（英文 VITS 模型念中文不报错、只是念不成形，听写场景比不念更糟）；
  ③ `unavailableReason` 必须给**照着做的出路**（放哪个文件、放哪个目录），原生异常一律记账返回 null **绝不外抛** ——
  平台靠"单条失败继续下一条"兜住整场。
* **`extension`（第三方 Dart 源码）级今天必须停在待功能**：没实现进程外隔离之前，跑它的代码 = 让第三方直接跑在 app 进程里。
  loader 冻结为 `gated` + `gatedOn: ['extension.broker']` + 说明"改用 declarative 或内置插件"的 `gatedHint`，
  并且**不许蹭 `flow.runner` 那句提示**（它等的不是 flow 引擎；原因说错会让人去接错东西）。
  内置来源挂 `extension` 判 `rejected`（写着"已隔离"其实没隔离，比不写更坏 —— 它骗过的是审计）。
  真要落这一级，按方案 §11 四条硬约束做：只给 façade 不给库（CI 扫 import 图）、跨界只走消息、预算与看门狗按 isolate 计、
  死亡收敛成 `failed` 且**不承诺自动恢复**。

* **`export` 的交付定义 = 用户真能打开的文件**。宿主侧（`host_export.dart`）负责两件事：
  app 私有目录 `文档/plugin_exports/<插件 id>/` 留取证副本，再导出到 `Download/TongYi-Lite/`；
  **只有后者成功才算成功**，私有副本不算交付（Android 上文件管理器看不见），此时必须返回 `runtimeError`
  让流程如实失败。作者可控的 `filename` 必须消毒（剥目录、禁字符换下划线、无扩展名补 `.txt`、限长），
  撞名自动加后缀而不覆盖。
* **失败信息三分工（有 assert 兜底，写的时候就照这个想）**：`message` 是给 UI 看的一句话（1–120 字，
  不许出现异常原文、Dart 枚举名、英文内部码）；`hint` 是出路（可以长，可以带路径/"去设置 → …"）；
  `cause` 是原始异常，只进日志与诊断树，**永不进 UI**。把路径或 `$e` 拼进 `message` 是新代码最常见的违例。

* **能力实现过同一套体检（`runCapabilityConformance`）**。"能力可替换"是平台最重要的一条承诺，
  它的风险不在插件侧而在**实现侧**：第二份 `app.speak` 一旦"不能用却不说为什么"，注册表会把它选上然后全场失败；
  一旦 `probe()` 会 throw，面板"试一下"一点就崩。所以任何一份实现 —— 宿主的、示例的、将来第三方 `trusted` 的 ——
  上岗前都过**同一套**检查，宿主那份**不特例免检**。五条硬规矩：能力 id 必须点分小写；
  `available == false` 必须给出人话原因（面板与回落都靠它指路）；`available == true` 不许乱给原因（免得面板两条口径打架）；
  `probe()` / `warmUp()` 永不 throw 且 Err 必须带 message 与出路；可用性读取稳定（不许在 getter 里藏随机或副作用）。
  套件自身**永不抛**：坏实现只能把自己变成一条红的，不能把体检搞崩。
* **出路兜底是 release 的唯一防线**。"六类失败必须带 hint"靠的是 `PluginFailure` 构造期 `assert`，
  而 **release 包里 assert 会被剥掉** —— 所以另有 `PluginFailure.ensureHint(code, hint)`：
  作者没给出路时按失败码兜一句人话（`kFallbackHints`）。两条都要：debug 照样炸（不许偷懒），release 有话可说（不出现光秃秃的"失败了"）。
  同理适用于预算类纪律：`plugin.json ≤ 64KB` / `prompt.md ≤ 32KB` 必须**按 UTF-8 字节**判（按字符算的话中文清单天然绕过），
  超了只标坏那一条文件并说清超了多少，隔壁插件照常加载。
* **能力实现的构造与可用性判断必须零副作用**。反例（已修）：`EdgeTtsPort` 构造时取 `EdgeTtsService.instance`，
  顺手建了 `AudioPlayer` 并订阅平台事件通道 —— 装配根在插件平台启动那一刻构造能力，等于开机就建播放器，
  而且让"能力体检"根本跑不起来（测试里没有 binding 就炸）。纪律：这类重资源一律 `late final` 懒建，
  `available` / `unavailableReason` / `probe` 只读不改状态。

* **`prompt.md` 的校验发生在扫描时，不是只发生在作者机器上**。CLI `validate` 是作者侧的便利，
  **拦不住用户手放进插件目录的文件**；loader 解析每条声明时必须跑 `validatePrompt`：
  超 32KB = error（判坏，说清"会挤掉模型上下文"），写法问题（如空文件）= warning（还能跑，进"声明提醒"）。
  同理适用于一切"作者写、用户改"的文件：预算与写法检查必须在**装载路径**上，写在 CLI 里不算数。

* **`agent_handoff` 的语义 = 交接进当前会话，且只等"受理"**。三个不可协商点：
  ① **不另开会话**（用户在这串对话里点的插件；隔离需求归 `app.store` 命名空间与独立能力，不归 flow 动词）；
  ② 宿主只保证**受理成功**（会话存在、该会话没在回答、智能体模式开着）就记 `agentsStarted = 1`，
  **绝不 await 智能体答完** —— flow 步骤有自己的超时，等整回合必然被误判成步骤失败；
  ③ **受理前的失败一律返回 Err 且带出路**（没打开对话 / 会话正在回答 / 智能体没开），
  回 `Ok` 假装交接了是最坏的一种假通过。材料有长度上限并在截断时注明。
* **"当前是哪一串对话"只能有一个真源**：`currentConversationIdProvider`，由 `home_screen._setCurrentConversation()`
  唯一入口写。任何宿主接缝（`agent_handoff`、将来的会话级槽位）都只读它，不许自己猜、也不许各自存一份。

* **工具的每一句判词都必须说清"是谁的问题"**。同一种"没在跑"，责任方可能完全不同，判词串了就等于把人引进死胡同：
  ① 声明式插件在 **CLI 进程**里必然待功能（flow 引擎在 app 里）→ 这是 **CLI 的边界**，不算插件毛病、不计失败退出码；
  ② 用户目录里 `trusted`/`dart` 却没代码 → 等的是"app 能从磁盘加载 Dart"这条路（`plugin.code.loader`，属 extension 级预研），
  **绝不许挂 `flow.runner`**（作者会去接 flow 引擎，接完依然跑不起来）；
  ③ 不在启用集 ≠ "已被你停用"（`EnabledStore` 只存"开着的集合"，分不出谁关的）→ 中性措辞。
  同理：**"本机有没有"要问 `hostCapabilityIds`，不能问 `validationCaps`** —— 后者是"契约全集 ∪ 本机"，
  用它判缺口会把"合法但没实现"（如 `net.search`）洗成"本机全有"，体检就白做了。
* **体检必须把被跳过的东西说出来**。列不出来的错误是最坏的错误：目录里没有 `plugin.json`（拼错、少放、多套一层）
  必须显式列成"跳过的目录"并给出路（`scaffold`），否则作者对着空列表发懵。
* **判据只能有一套装配**。`scan` 与 `doctor` 共用同一个 `_load()`；app 与 CLI 也共用 `PluginLoader` 与同一份校验。
  任何"第二条判据路径"迟早出现"面板说能跑、CLI 说不能跑"，届时没人知道信哪个。
* **不要为了可见性再造第二个真相源**（本轮撤回一次）。曾打算给 flow 引擎注册 `flow.runner` 能力，
  好让面板「本机能力」列一行 —— 撤回：引擎到位与否的唯一真源已经是装配根给的 `declarativeFactory`（loader 只看它），
  再造一个能力 = 两处要对齐 = 将来的分歧。**可见性不足就改进判词（上一条），不新增状态源。**

* **建档的格式与档名判据归内核，面板只负责问**。`profileDraftJson`（写出形状与 `PluginProfile.fromJson` 严格对齐、
  列表排序写出以便 diff）与 `profileNameProblem`（能不能当文件名 + 点开头扫不扫得到）都在内核；
  面板不许自己拼 JSON、也不许自己编一套"这个名字不行"的话术 —— 否则迟早出现"面板写出来的档内核读不懂"。
* **「新建方案档」建完不许切过去**。用户点的是"存一份"，不是"换成这个"：换档会连插件集、人格、模型一起动，
  那是另一个动作（点档卡片）的语义。同理 **同名档一律拒绝覆盖**（作者可能正用文件管理器手写那份），
  出路要指到那个文件的路径。
* **面板里的空档目录不是错误**：显示 `<档目录>/<档名>.json` 告诉用户能去哪儿放，
  但绝不因为"读不到档目录"就把插件全关掉（fail-safe 那条仍然成立）。

* **体检报告里不许有"说不清是什么"的东西**。同样是"目录里没有 plugin.json"，套了一层 / 是 Dart 包 / 真没文件
  三种病因的出路完全不同，糊成一句等于没说；一个目录同时是包又装着声明，**两件事都要说**。
* **示例即规格，规格必须自证**：`examples/` 下的每个目录都要被 `doctor`/`validate` 认出来并归类，
  门禁是 `packages/plugin_kernel/test/examples_gate_test.dart`。示例改了结构而工具不认识它，
  就是文档与工具打架且没人报警。
* **README 里写的路径必须能照抄执行**。作者照 `./plugins/zh-dictation` 去 `adb push` 会直接扑空 ——
  仓库里那个目录叫 `examples/zh_dictation`；文档里的命令与真实目录一起进门禁。
* **代码级插件不能从磁盘加载这件事要写在示例最前面**（不是藏在深处）：
  它决定作者是"推到手机就能试"还是"必须改 app 重编"，猜错一次就是半小时白干。

* **删方案档只删那份文件**：插件本身、以及每个插件各自存的参数（`plugin:<id>:<key>`）一概不许动；
  删掉**当前在用**的档必须顺手把当前档名清空（不留悬空档名），并回到"按用户自己的开关"。
* **面板上每一个破坏性动作都要有自己的确认框，且话术回答"我会不会连别的一起丢掉"**。
  删档的三句话是合同：插件与参数不动 / 在用档删完回到不用档 / 坏档也走这条路。
* **破坏性动作的目标文件可能已经被外部删掉**（手机文件管理器、adb shell）：
  这种情况要说"本来就不存在"并刷新列表，**不许谎称删掉了，也不许当故障报错**。

* **`ask_params` 只认 `params.names`**，别的键一律不读；`validate` 必须把"这一步其实一个问题都不会问"判成错误并说中后果
  （静默拿默认间隔 = 听写变连珠炮，用户只会说"念太快"）。问出来的值算"已使用"（可进 `{{count}}` 占位符）。
* **参数要么被流程真用，要么别声明**：`{{config.x}}`、`ask_params` 的 `names`、或该原语的**隐式读取**
  （`speak_sequence` 读 `voice` 与 `gapParam ?? 'gapSeconds'`；`llm_extract` 读 `readChinese`）三者之一，
  否则 `validate` 提醒 `unusedParam`。隐式读取表与 `flow_runner` 一一对应 —— **改 runner 的隐式读取必须同改此表**
  （有"写得对的插件不许被误报"那条测试钉着）。`volatile` 参数豁免，因为面板参数编辑器本来就不显示它：
  **判据必须与面板行为同源，不能两边各定一套"什么叫开关"**。
* **示例自己必须守住平台的规矩**：一层目录 = 一个插件（扫描只走一层）、零校验提醒、README 里的命令能照抄执行。
  门禁是 `packages/plugin_kernel/test/examples_gate_test.dart`（含"不许出现更里面一层 / 声明提醒"）。

* **每个原语读哪些步骤参数只有一个真源：`FlowStepOp.knownParamKeys`**。`validate` 拿它提醒 `unknownOpParam`
  （「写了等于没写」，并列出真正读的键）；`llm_extract` 是**唯一**的开放集（多余键是 `prompt.md` 的变量）。
  改 `flow_runner` 的读取必须同改此表 —— `packages/plugin_kernel/test/flow_contract_test.dart` 双向钉住，漂移当场红：
  表里有而 runner 不读 = 装饰品键；runner 读而表里没有 = 作者写对被误报（从此没人信这个工具）。
* **作者写在声明里的话必须真的到达用户**：`review` 的 `title` 不许被丢掉（它与系统的「共 N 条：…」并列显示）。
  任何「声明里有、界面上看不见」的参数都按缺陷算。
* **原语不许在什么都没做时返回成功**：`export` 空内容、`store` 空壳、`capture` 空图片都必须是 `Err`
  （三态闭集，不许「半途而废当成功」）。
* **`review` 今天的语义只有「整体放行 / 整体放弃」**。逐条点掉认错的条目需要 `Interact` 增加多选动词，
  属能力面扩档 —— 已登记方案档 §8 待拍板第 6 件；未拍板前，示例与文档**不许把 review 写成「点掉不对的」**。

* **"问得出来"只有一种定义**：`ask_params` 问得出 `number` 与 `choice`；`boolean`/`text` 由设置页负责。
  因此三种形态都是"摆个什么都不问的提问步骤"，`validate` 统一用 `askParamNotAskable` / `askParamsEmpty` 抓：
  ① 把 `boolean`/`text` 写进 `params.names`；② 给它标 `askAtStart`；③ 标了 `askAtStart` 却没有 `ask_params` 步骤。
  **问不出来的名字不算"被使用"** —— 否则 `ask_params` 与 `unusedParam` 两条判据互相打掩护。
* **引擎不信任能力实现的自觉**：`min`/`max` 是插件在 manifest 里声明的，`flow` 引擎必须复查 `app.interact` 的返回值；
  越界即失败，判词必须指名"这是宿主实现违约，不是插件写错、也不是用户填错"。
  `Interact.askNumber` 的实现侧仍须自己钳制或拒收 —— 引擎复查是兜底，不是免责。
* **"受理了但没干活"就是失败**：`agent_handoff` 的宿主 `startAgent` 返回 `<= 0` 一律 `Err`，
  不许记进 `agentsStarted`（三态闭集：不许"半途而废当成功"）。

* **交付类动作必须拿到凭据才算成功**：导出/分享/打开这类"交到用户手上"的调用，只有取得可验证的位置（content URI 或绝对路径）
  才是成功；`null` / 空串 / 空白串一律失败（`export_no_uri`）。**"成功但位置是空串"是最坏的一种返回** ——
  它让所有调用方一起假装没事（本轮 flow 的 `export` 与智能体 `export_file` 同时被蒙）。
  失败时私有取证副本照常落下，报错不许顺手删证据。
* **`prompt.md` 的占位符只有一个真源：`providedPromptPlaceholders(manifest)`**，与 `flow_runner._renderPrompt` 的三层来源一一对应 ——
  `{{userInstruction}}` ＋ **该 `llm_extract` 步骤自己的 `params`**（`promptFile`/`system` 除外）＋ **走到它之前** `ask_params` 问出来的
  **问得出来的**（`number`/`choice`）值。因此"`ask_params` 排在 `llm_extract` 之后"是缺陷（运行时静默不替换，validate 抓）。
  代码级插件豁免：它的提示词变量由 Dart 自己填，静态看不见。

* **作者的默认值只在"第一次见到"时生效**：`plugin.json` 的 `enabledByDefault` 由内核在扫描后播种，
  但"哪些 id 见过"必须由宿主持久化（内核 `FirstRunSeeder`，app 落在 `plugin_enabled.json` 的 `plugin.seen`）。
  没有这本账，用户关掉的开关会被下一次重扫悄悄翻回"开"；有这本账，**用户明确的决定永远优先于作者的默认值**。
  宿主没接账本 → 不播种（宁可不动，也不瞎开插件）。播种结果只写进 `EnabledStore` 这一个真源。
* **一份 JSON 文件只有一套状态**：`JsonMapFile` 的内存缓存与串行写队列**按解析后的路径共享**，
  且"读-改-写"的快照在队列内部才取。按对象各持一份缓存 = 两个写者同住一个文件时后者把前者的键整包洗掉
  （`plugin.enabled` / `plugin.seen` 就是这么撞的）。同步 API 的落盘是 fire-and-forget，需要确定落盘就用 `flush()`。
* **没有"注册即启用"这条路**：SDK 不再有 `PluginRegistration`。启用与否只有 `EnabledStore` 一个真源，
  唯一的自动打开就是上面那条首次播种。公开而没人读的类型/字段一律当缺陷删掉 —— 它是给作者看的假开关。

* **同一份持久化文件里，谁写的谁清，只清自己那一格**：`plugin_enabled.json` 同时住着 `plugin.enabled`（宿主开关）
  与 `plugin.seen`（首次播种账本）。任何一侧写它都必须**读-改-写**（留住别人的键），任何"reset/clear"都不许整包删/整包重写 ——
  账本被洗掉的后果是全体插件退回"第一次见到"，用户亲手关掉的开关被 `enabledByDefault` 集体翻回"开"。
* **体检报告里"未启用"必须分成三种**：默认没开 / 被用户手动关过 / 声明了 `enabledByDefault` 但 app 还没扫过它。
  第三种**不算作者的问题**（装进 app 第一次扫到会自动打开），把它报成"跑不了"会逼作者去改一份本来没问题的 `plugin.json`。

* **配置的每个写入口必须一样严**：`ConfigStore` 里判「这个键到底存不存在」的只有 `_undeclaredKey(manifest, key)` 一处，
  `patchUser` 与 `patchPath` 共用（子路径按首段判，深层结构归插件自己）。未声明的键一律拒 ——
  留下一个没查的口子，就等于给「typo 写出永远读不到的死值」留后门：面板只列声明过的参数，用户改了没反应，
  也永远看不见自己写进去的那一行。
* **四层配置必须能退回默认，而且界面点得到**：`PluginService.resetConfig(id)` **只清用户层**，
  方案档与插件声明的默认值都不许被牵连；收尾与 `setConfig` 同一条（只动易变值不重载，否则靠 epoch 自愈）；
  本来没改过时是空操作 —— 不空转 revision，也不报「已恢复」。同理，面板必须显示每个值**来自哪一层**
  （`ConfigStack.layerOf`）：「我改的到底生效没、是不是被方案档盖住了」不能靠用户猜。

* **「成功返回」不等于做成了**：`setConfig` / `retry` / `resetConfig` 这类操作把失败也包成 `Ok(PluginChangeResult)`（面板一个分支画完）。
  因此任何读结果的地方（面板、宿主、CLI）必须看 `application` 与 `failure`，**不许只看 Ok/Err**；
  `application == failed` 就播报失败原话与 hint，`restartRequired` 必须说「还没生效」。
* **「没东西可重试」要说什么干不了**：清单没过（rejected）→ 指出改 `plugin.json` 再重扫；关着的 → 「重试不会替你打开开关」；
  本机没有 → 说清去哪看。退回 `reload()` 换一句「已重试」是假回执（用户白等一轮，问题原样留着）。被拒的插件重试全程不许有副作用。
* **账本与渲染是两个视图，不许混用**：`SlotRegistry.snapshot()` 读**原始账本**（谁登记过什么 + `active`，含已让位的），
  供体检/面板自解释；`entries()` 是**该渲染谁**（single 槽滤掉让位的、做接管）。用渲染视图做体检，
  出过错被摘掉的入口会凭空消失，用户永远不知道自己的入口被摘了。面板对 `active == false` 必须显示「已让位」。
* **配置值的判据在写入口**：与「未声明的键」同级，走 `ConfigStore` 的 `patchUser` / `patchPath`（单段）共用同一条 ——
  number 越界或收到非数字、boolean 填 `"yes"`（会被判成 `false`，静默反义）、choice 不在 `options` 里，一律拒并说清范围与「你填了什么」。
  **报错而不是运行时悄悄夹逼**：夹逼是「我明明填了 99，你怎么给我 30」那种说不清的降级。
  只判 `params` 声明过的键；`manifest.config` 的自由键与深层子路径归插件自己。
* **最该看见的日志不许被「最近 N 条」挤掉**：`diagnostics()` 除 `logs`（全量）外必须给 `logFailures`（`warn`/`fail` 全量），
  面板先列它再列最近若干条。环形缓冲 + 只显最近 30 条 = 插件一刷屏就看不见真正的失败。

* **交付类动作的凭据必须包含"真名"**：`FlowHost.renderExport` 交回 `ExportReceipt{uri, fileName, renamedFrom}`，
  引擎复查 `uri` 与 `fileName` 非空 —— **空 URI、空文件名都不算交付**；流程回执必须报**真正落盘的名字**
  （撞名的 `-1`、被 sanitise 掉的都是），宿主改写过名字时 `renamedFrom` 给原名、回执里说破。
  拿作者要的文件名去报"已导出"，与"空 URI 也算成功"是同族的谎。
* **契约里承诺的钩子必须有调用者**：`CapabilityRegistry.warmUpAll`（宿主 boot 后低优先级调，内核侧入口 `PluginService.warmUpCapabilities`）
  与 `Speak.prewarm`（引擎在 `speak_sequence` 里对**除首条外**的条目后台预热）都不是可选项 ——
  没人调用等于实现写的预热永远不执行，用户等的是"下载音频的时间"却以为是插件声明的间隔。
  分工写死：`warmUp` 只做便宜的准备（不许在启动路径上加载模型），重活归 `prewarm`；两者失败与异常都只影响性能，不许惊动用户。
* **注册被拒必须留声音**：宿主注册能力只走 `registerHostCapability`（内含 `Outcome` 检查与被拒日志：哪个能力、谁没注册上、换 priority 的出路）。
  `CapabilityRegistry.register` 对同 id 同 priority 的第二次注册返回 `Err`，丢弃返回值 = "我明明注册了，怎么没生效"且零线索。
  同一条纪律对测试成立：**测试里丢弃 `Outcome` 就是测了个寂寞**（断言会打在根本没生效的对象上）。

* **配置的四层全部归 `ConfigStore` 所有**：默认 / 方案档 / 用户 / **会话**（`setSessionOverride` · `sessionOf` · `clearSessionOverrides`，
  `stackFor` 默认带上会话层）。`PluginCtx.setSessionOverride` 只许写进 store（ctx 内可留镜像），
  **不许**把临时值揣在 ctx 肚子里 —— 面板与内核读的都是 `ConfigStore.stackFor`，两边不一致时面板指着「插件默认」而实际用的是临时值。
* **每一层都得有真的写入口，界面上也得点得到**：会话层的入口是 `PluginService.trialConfig`（面板「先试试这组值」），
  **不落盘**、校验与 `setConfig` 同一条（越界/非法选项一样拒）；「恢复默认」= `resetConfig` **同时清用户层与会话层**
  （只清一层却报"已恢复默认"，用户下次看到的还是试出来的值）。
* **"改了没有"按可持久层判**：判据是 `ConfigStack.persistedOnly`（默认/方案档/用户），会话层不参与 ——
  否则会话里试过一个值之后，用户的保存会被回一句「没有变化」。试值那条入口反过来按合并值判（它看的就是合并效果）。
* **平台被丢弃时 `shutdown()` 必须被调用**：宿主侧 `ref.onDispose(() => service.shutdown())`。
  fiber 不卸载 = `ctx.effect` 的释放器（Timer / 订阅 / `provide` 出去的能力）永远挂着，重扫一次漏一份，且全程无症状；
  释放后 `diagnostics().effectTree` 必须为空（账本不许留着"已释放"的假象）。

* **贡献物（槽条目、`provide` 的能力实现）由内核自动挂进 fiber 的 effect 树**：`ctx.slots.register` / `ctx.capabilities.provide`
  成功即挂，作者忘挂 `ctx.effect(d)` 不会留幽灵；重复挂安全（注销是 `removeWhere`/`remove`，幂等）。
  卸载后 `slots.entries(...)` 必须为空、`capabilities.resolve(...)` 必须 `Err` —— 这是**验收判据**。
* **"本机有哪些能力"只有一个问法**：面板读 `CapabilityRegistry.list()`，门控与校验读宿主给的 `hostCapabilityIds`。
  **不留** `knownIds()` 这类第二份清单；**不留** `seedProfile()`（档位层写入口只有 `replaceProfile`，语义是整体替换）；
  **不留** `SlotRegistry.clearAll/clearLedgerOnly`（全量清空会抹掉别的插件的条目）。
* **每次重载一个新 traceId，而且必须有人按它筛**：`diagnostics()` 交回 `traceId` 与 `runLog`（`InMemoryTraceSink.byTrace`），
  面板分「本次运行」与「最近日志」两节 —— 混着历次实例的日志只会把人往错方向带。
* **新增/修改"泄漏类"测试必须当场验证它会红**：把修复临时关掉跑一遍，红了才算测试咬人。
  槽"同 id 视为同格"会把重载后的重复注册合并，`entries().length` 这种判据在重载场景下测不出幽灵。

* **每条用户看得见的失败文案都必须有测试引用**：机检法 = 抓 `message: '…'` → 剥插值 → 6 字滑窗到全部测试里找，找不到的逐个定性。
  "写了没人验证过"的守卫与"写了没人调用"的钩子同罪：前者是**说不出口**，后者是**做不出来**。
* **`knownProfiles`（方案档名对不上）判 `warning` 不判 `rejected`**，文案必须含「在哪个档里都不会出现」+ 出路指向「插件方案」；
  `knownProfiles` 为空时**不许**报这条（本机没有档目录这个概念，报了全是误报）。测试直接打纯函数 `parseDeclaration`。
* **"没接通"与"没干活"是两句不同的话**：宿主没有这条路 → 「这台机器还没接通 X」（`missingCapability`）；
  受理了却没产出 → 说清它受理了什么、缺了哪一步（例：`agent_handoff` 零回合）。两者不许共用一句文案。
* **空交付一律 `Err` 而且不许触碰交付副作用**：`export` 内容为空 → 失败，且宿主的 `renderExport` 回调**一次都不许被调用**
  （空文件写进用户能打开的目录，比一句报错更坏）。

* **质检套件自己必须被 mutation 测试过**：`runCapabilityConformance` / `runConformance` 的每条检查都要有一份"故意坏"的实现把它逼红，
  外加一份"合法但看起来坏"的实现证明它不误伤。只有全绿证据的门禁等于没有锁。
* **`available` 允许且只允许一个方向的翻转**：探测（`probe`）期间必须不动（`afterProbe == available`）；
  **`warmUp()` 之后由不可用转为可用是合法的**（离线 TTS/ASR 在预热里加载模型与音色表），detail 要写明"懒加载，合法"。
  反向翻转（预热后反而不可用）判坏 —— 注册表会先选它再全场回落。
* **"不可用时给人话原因 / 可用时别挂原因"两条都要判**（面板与注册表回落共用这一句），且 `probe` 失败必须带 `hint`；
  `probe` 与 `warmUp` **永不允许 throw**，异常一律折算成 `Outcome`。

* **`ValidationIssueCode` 每个枚举值都必须被某个夹具逼红过**（机检：枚举值 → 测试里找 `ValidationIssueCode.<值>`）。
  裁判的罪名没人触发过，就是死判据。
* **弃用只提醒不判坏**：登记表命中 → 只出 `ValidationIssueCode.deprecation` 的 **warning**，`validate` 的 `ok` 必须仍为真；
  文案必须含「自 <版本> 弃用（，计划 <版本> 移除）」+ hint「替代写法：…」，面板黄条与 `doctor`「声明提醒」共用这一条。
  `deprecationIssues(raw, {table})` / `validateManifest(..., {deprecations})` 的口子只为测试与迁移工具开，
  默认永远取 `kL1Deprecations` 这份唯一真相。
* **弃用登记表本身要被卫生检查把关**：`since` 三段版本号、`path` 只含 `a-zA-Z0-9.*[]`、`message` 不以句号结尾。
  `a[*].b` 这类数组路径必须实测命中 —— 写错的表现是"提醒永不响"，永远不会有人发现。
* **`doctor` 的「声明提醒 N 条」行要带条数与路径，且与「硬问题」互斥**：只该提醒的东西不许冒出"硬问题"字样。
* **`doctor` 的首要一行必须说真相**：目录里全是读不出来的声明时，第一行是「目录 X 里没有能加载的插件，但有 N 个声明读不出来：」，下面逐条列**文件名 + 第一条错误原文（最多 3 条）+ hint**，末尾才指路 `validate`；此时不许出现「没找到插件」，也不许把 `null` 念进任何用户可见句子（`没找到插件「null」` 是上一版的原文）。　`res.broken` 的 key 是**相对插件目录**的（`half/plugin.json`，不带 `plugins/` 前缀）—— 断言按这个来。
* **纪律：把一条红测试判成"产品缺陷"之前，先做最小可复现**（直跑被怀疑的那条路径、打印全部输出）。上一轮就因为它才没把"其实是我的断言写错"当成缺陷写进文档。

* **`reset` 的每一条用户可见行都要有测试**：没东西可清时说「什么都没要删（目录 X 是空的？）」并点出目录，
  不许回「完成，删了 0 个文件」（假装干完了活）；预览行要说清"清的是开关 + 同文件 `plugin.seen` 会留着"；
  确认行要说 `plugin.seen` 留着以及为什么（否则用户不知道关掉的插件会不会又自己亮起来）。
* **CLI 里不可达的防御分支不为它编夹具**：`scan()` 的两个 return 全是 `Ok`（来源读崩记成 broken + 兜底，不外抛），
  「体检做不了」这类行是契约留的防御位；守住的是**不变量**（来源读崩也不许让 `scan()` 变 Err），不是那行字。
* **扫"零覆盖文案"要按子串双向匹配**，命中不了的先**直跑打印现状**再定性：本轮 28 条里若干是扫描器的假阳性。

* **脚手架自检的四条 Dart 纪律判据，每条都要各自被逼红**：`ctx.effect(` 挂回收 / 返回 `Outcome<` / await 边界 `throwIfCancelled` /
  出现 `throw ` 即拒。模板漂移时这是唯一拦住"平台亲自教作者违反纪律"的地方。
* **自检的 hint 要一次说完，且不许误报**：多条违规必须全部列出（只报第一条 = 作者改一条跑一次）；
  某条没坏就不许出现在 hint 里（反向断言）——作者会去动没坏的地方。
* **用 `cp` 还原文件后 `find -newermt` 不再作数**（mtime 变新而内容未变）：这类收尾改判为"重打一次包比 sha256"。

### 台账复核（第 37 轮）：`testing.dart` 五个桩口的定性

上面那行「测试桩的五个口没有测试在用」**要按这条更正读**（逐个读实现之后的结论）：

* **`tickSource` / `tickForward` —— 扫描器误报，核销。** 它们是时钟链路本体：
  `FakeCapabilityHarness` 建桩时 `cap.tickSource = () => _tick`，`FakePluginCtx` 每次调用 `ctx.harness.tickForward()`。
  「同文件内自用」被启发式当成了零调用 —— 与本轮之前 `lastFailure`（`?.` 访问）、`activeProfile`（构造注入）同一类误报。
* **`lastUserText` / `lastAudioPath` / `callsSince` —— 不是死口，是「没人验证过的凭据」。**
