# 端侧超大 MoE 统一架构方案与施工计划
### —— MiniCPM-V 4.7 端侧跑通（CPU 先行 → OpenCL）与 >10B MoE 统一承载

日期：2026-10-14 ｜ 版本：v1 草案 ｜ 状态：待评审

---

## 1. 目标与范围

**一句话**：把「专家拆分 + 槽位流式 + LES 前瞻」做成 TongYi-Lite 的**统一超大 MoE 承载层**，先用 MiniCPM-V 4.7 35B-A3B 拆分版端到端跑通（CPU 先行，再 OpenCL），最终让**所有 >10B 的 MoE 模型**（MiniCPM-V 4.7、Qwen3.6-35B-A3B、Ling 系）都走同一套架构承载。

**范围内**：
- split-moe 拆分模型格式（-les 主文件 + experts/ 分片 + manifest）的装载与管理
- vendored llama.cpp（b11267）移植 omni 的 manifest loader / slot runtime / LES 调度
- 端侧 CPU 全链路 → OpenCL dense GPU → GPU MoE batched q3_K 三步递进
- Dart/JNI/Dart 模型管理侧的多文件下载、完整性校验、内存预算

**范围外（明确不做）**：
- 视觉（mmproj + clip_graph_minicpmv4_7）——纯文本先行，视觉后置独立立项
- 整包专家内联模型（20.2G Q4_K_M / 14.8G mix）端侧直载——已被官方 Apps 实锤为死路，不做
- 换引擎——保持 vendored b11267 + 自有补丁面（dspark/OpenCL batched/MTP）

## 3. 统一架构设计（四层）

```
┌─ D 层 执行层 ────────────────────────────────────────────┐
│  dense/attention → OpenCL(GPU)（白名单现成，85% 时间）        │
│  MoE 专家 → 按量化档路由：q4_0/q4_K→GPU batched；             │
│             q3_K→P3 前走 CPU 专家混合，P3 后走 GPU batched     │
├─ C 层 调度层 ────────────────────────────────────────────┤
│  LES 下一层 router 前瞻预取（零训练，命中>80%）                │
│  MATMUL_SPLIT(A2) 延后读取：attention 藏 UFS 盘读              │
│  slot 窗口缓存 + park/unpark + 静态预热 + counters             │
├─ B 层 装载层 ────────────────────────────────────────────┤
│  manifest loader（schema v1 照抄 omni，169 行）                │
│  slot runtime（窗口槽 + preadv 多线程直入 host-visible 槽位）   │
│  mmap 主文件 + preadv 专家分片（绝不做整包页故障加载）           │
├─ A 层 格式层 ────────────────────────────────────────────┤
│  split-moe：主 GGUF（专家剥离，架构 qwen35moe 等通用）          │
│  experts/layer_NNN.bin + manifest.json（per-entry 量化类型）    │
└──────────────────────────────────────────────────────────┘
```

**设计原则**：
1. **A/B 层与量化类型解耦**：manifest per-entry quant_type ⇒ 同一装载层承载 Q3_K / Q4_K / q4_0 专家包，不锁死量化档
2. **C 层与后端解耦**：slot/LES 只管「哪个专家字节块何时在内存」，不关心算子后端 ⇒ CPU/GPU 通吃
3. **D 层按量化档渐进**：CPU 专家混合是兜底永远保留；GPU batched 每档过 moe_probe 门禁才启用
4. **>10B 门槛通用化**：catalog 模型条目新增 `splitMoe` 类型；MoE 总参 >10B 且提供拆分包即走此路径，其余模型路径不变

## 5. 施工计划（六阶段，每阶段有硬门禁）

### Phase 0 — PC 装载验证（vendored 载 MiniCPM-V4.7 拆分版，CPU-only）
**做什么**：移植清单 #1/#2/#6（最小集，先不开 LES/MATMUL_SPLIT）→ PC 上用 vendored llama.cpp 装载 -les 拆分版纯文本 → 跑通生成。
- 下载：ModelScope `zerg13/MiniCPM-V-Apps-gguf`（主 1.59G + 40×330MB + manifest）
- 验证点：装载无缺张量报错；生成文本连贯（对照官方 24.11.4 CHANGELOG 文风）；专家流式读生效（观察 IO 而非一次性 14.8G 常驻）
**门禁**：生成 100 token 连贯 + 常驻内存 < 预算（slot bank ≈ n_used×bytes_per_expert×窗口）
**产出**：`llama-moe-experts.cpp` / `llama-moe-slot.cpp`（裁剪版）入库 vendored、PC 基线 t/s
**规模**：主体工作量最大的一阶段（slot 裁剪），预计 2-3 个工作日

### Phase 1 — 端侧 CPU 模式跑通
**做什么**：移植清单 #7/#8（JNI 透传 + Dart splitMoe 模型管理）→ 真机覆盖安装 → CPU 全链路 decode/prefill。
- 下载器：40 分片断点续传 + manifest SHA/字节长校验 + 批次一致性（官方 Apps 实锤批次不匹配直接拒载）
- 内存预算：slot bank 配额实测定档（P0 数据外推），预留 3-3.5G 专家热集口径
**门禁**：真机 decode t/s 记录（预期 CPU 路径个位数起步）；无 OOM 杀进程；冷专家加载不 stall 主线程
**产出**：`releases/...-v0.3.2-preview.apk`（版本 bump 0.3.2）、真机 CPU 基线表
**规模**：1-2 天

### Phase 2 — OpenCL dense GPU + CPU 专家混合
**做什么**：dense（attention/lm_head/token_embd/共享专家，Q4_K/Q6_K/F32 全白名单现成）走 GPU，专家走 CPU 流式混合（现有 batched 回退路径直接生效）。
- 这是「85% 时间在 dense」架构红利的第一次兑现：GPU dense 时间应能盖住专家 UFS 读
**门禁**：无乱码（KDBG 里程碑同款验证流程）；真机 t/s 显著高于 Phase 1；内存账本核对（GPU dense + CPU slot 双占用）
**产出**：真机 GPU dense + CPU 专家混合基线；`LLAMA_MOE_MATMUL_SPLIT` 首次真机调参
**规模**：1 天（几乎全是验证，新代码少）

### Phase 3 — GPU MoE batched q3_K（关键攻坚）
**做什么**：照 q4_K dodge 范式实现 batched q3_K 内核：
1. **新内核**：vendored OpenCL 无独立 q3_K 内核（已核验只有 ggml-opencl.cpp 引用），需新写 `gemv_noshuffle_q3_k_f32.cl` batched 版——q 平面 3-bit 解码（ql 低 2 位 + qh 高位交叉）参照 ggml-quants.c 语义改写
2. **scale dodge**：q3_K scale = get_scale_min_k3 + 4-bit mask，与 q4_K 同构 ⇒ host set_tensor 预计算 seff=d·sc / meff=dm·mn（fp16 half2 行对），内核退化为纯 half2 加载——**这是规避 Adreno E031 编译器损坏代码形状的关键**，q4_K 的 7 种形状改写均无效的教训直接沿用
3. **专家重打包**（可选支线）：PC 端把 Q3_K 专家转 q4_0/q4_K 生成自家专家包（manifest per-entry quant_type 零改动支持）——若 q3_K 内核攻坚受阻，这是 GPU 专家的绕行通道
**门禁**（与 q4_K 同款）：moe_probe 全形状 NMSE ≤1e-6（11 形状起步，补 q3_K 特有形状）；重跑位级一致；bench 对比 CPU 专家路径；tbo 抽查
**产出**：q3_K batched 上线 或 重打包绕行决策；真机 GPU 专家 t/s
**规模**：2-3 天（有 q4_K 全套基建，风险显著低于 q4_K 首攻）

### Phase 4 — LES 前瞻 + 完整调度
**做什么**：开启 `LLAMA_MOE_LOOKAHEAD_PREFETCH`（复用下一层 router × 当前 hidden，零训练）；与 MATMUL_SPLIT 联调；counters 拆账（prefill/decode、命中/miss、IO 等待 vs 计算）；PARK_WINDOW/DECODE_WINDOW 真机定参。
**门禁**：命中率 >80%（官方口径）；冷专家 miss 不 stall；对比 Phase 2/3 提速可量化
**产出**：调度参数定型、counters 日志口径入 KDBG 体系
**规模**：1-2 天

### Phase 5 — 统一架构泛化（>10B MoE 全走此路）
**做什么**：
1. catalog 模型模型类型 `splitMoe` 正式化：下载/校验/装载/内存预算全走统一层
2. 内存预算器：按 `n_moe_layers × slot_bank × bytes_per_expert + dense 常驻` 计算准入（15.5G 机型门槛自动判定）
3. Qwen3.6-35B-A3B 三步走对齐：目标模型出同款拆分包（我们自造：T42 2.25bpw 专家 → per-layer bins，量化档自选 q4_0/q4_K）→ 与 MiniCPM-V4.7 共用全部 B/C 层代码
4. 文档：统一架构白皮书段并入 README 技术架构节
**门禁**：两族模型（MiniCPM-V4.7 + Qwen3.6-35B 拆分包）同一代码路径跑通
**产出**：v0.4.0（统一超大 MoE 承载版）
**规模**：2 天

**总计约 9-13 个工作日**，里程碑：P0/P1 → **v0.3.2**（拆分版端侧 CPU 跑通）→ P2/P3 → v0.3.3（GPU dense + 专家攻坚）→ P4/P5 → **v0.4.0**（统一架构）。

## 6. 风险表与预案

| 风险 | 等级 | 预案 |
|------|------|------|
| q3_K 内核命中 Adreno E031 同类编译器损坏 | 中 | **q4_0/q4_K 的 BUG 均已修复上线（v0.3.0/v0.3.1），不是未解问题**——重打包目标选它们正因如此。但 E031 根因（在线编译器损坏特定代码形状）仍在驱动里潜伏，q3_K 新内核的 q 平面解码是新代码面；scale 侧用 dodge 预计算覆盖（最大嫌疑面），q 平面若仍损坏 → 专家重打包 q4_0/q4_K 绕行（Phase 3 支线，零 schema 改动） |
| slot 2772 行移植引入回归 | 中 | 以新增文件为主，vendored 既有文件只插调用点；每 Phase 真机回归 q4_0/q4_K 既有链路 |
| 真机 UFS 读速不足（330MB 分片冷读 stall） | 中 | Phase 1 先实测 UFS 带宽；MATMUL_SPLIT 藏读 + LES 预取双缓解；slot bank 加大 |
| 15.5G 内存不足以容纳 dense GPU + slot 热集 | 低 | dense GPU 占用远小于整包；预算器准入判定；slot bank 可调 |
| omni 基线老（arch.h 654 行 vs 我们 829 行）接入冲突 | 低 | 只移植 src 两文件 + model 钩子，不碰 arch/模板层 |
| 下载 40 分片 integrity | 低 | manifest exact_byte_length + SHA 双校验 + 官方批次一致性规则 |

## 7. 验收标准（DoD）

1. **功能**：真机（SM8750/15.5G）装载 MiniCPM-V4.7 拆分版纯文本，对话连贯，工具调用（Prompt-JSON/Ling 协议）可用
2. **性能**：三档基线齐（CPU-only / GPU dense+CPU 专家 / GPU dense+GPU 专家），LES 开关 A/B 对比数据入档
3. **正确性**：q3_K（或重打包档）moe_probe 全形状 NMSE ≤1e-6；多轮对话无乱码回归
4. **统一性**：Qwen3.6-35B 拆分包（自造）走同一代码路径装载成功
5. **工程**：slot/manifest 代码入库 vendored 补丁面文档化；KDBG+counters 证据链入 `_probe/moe_probe`；CHANGELOG/README/版本三件套随里程碑更新

## 8. 待评审决策点

1. **Phase 0 先行下载占用**：14.8G 拆分包落盘位置（PC D:\MyLLM vs 直接真机 adb push）——建议 PC 先验再推真机
2. **q3_K vs 重打包优先级**：直接攻坚 q3_K batched，还是先做 PC 重打包工具链（q4_0/q4_K 专家包）保 GPU 专家提前上线——建议并行，重打包为保底
3. **slot 参数暴露形态**：env（omni 原样）vs app 设置页 vs 固定最佳值——建议 Phase 4 前维持 env，定型后固化默认值
4. **版本策略**：v0.3.2（CPU 跑通）是否随 Phase 1 提交 push——按惯例等真机验证后点头
