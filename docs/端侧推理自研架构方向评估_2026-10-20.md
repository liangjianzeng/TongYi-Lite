# 端侧推理自研架构方向评估

日期：2026-10-20　范围：`third_party/llama.cpp` 自研 fork（重点 ggml-opencl）+ JNI/App 引擎层
起因：Ling 3.0 Tiny OpenCL 吞吐大跌（3.7 vs 8.77 tok/s）定位过程中暴露的结构性问题
配套：[Ling3.0Tiny_OpenCL性能回归定位_2026-10-20.md](./Ling3.0Tiny_OpenCL性能回归定位_2026-10-20.md)

## 1. 结构性缺失一：能力契约没有单一事实源

同一个 MoE 决策要过三处互不知情的门：

| 位置 | 作用 | 本次 Ling 的表现 |
|---|---|---|
| `supports_op`（:10216-10302，471 行里的 87 行） | 准入：这个 op 能不能上 GPU | **放行**（所以权重上了 GPU、`offloaded 25/25`） |
| `set_tensor`（:12322-12389） | 建预打包平面（`q/d/dm/s/seff/meff/se0/se1`） | 由另一套对齐守卫决定建不建（:12359 四连 `%alignment`） |
| `ggml_cl_mul_mat_id_batched`（:24681-24780） | 派发：平面在不在、形状过不过 | **静默 return false** → dense-loop |

**三处条件各自手写，漂移是数学上的必然。** 漂移的后果被随机分配成三种，三种都真实发生过：

| 漂移类型 | 案例 | 代价 |
|---|---|---|
| 崩 | q3_K 只有 batched 一条路，两道门不一致 → `GGML_ABORT`（:29267）；`OFFLOAD_MMID=1` → SIGSEGV（:15259） | 显性，反而好查 |
| 错 | E031.47 上 q4_K batched 的 codegen 损坏；厂商 `gemv_moe_q4_k` "输出=正确×错误常量"；`half` 当类型关键字致 `clBuildProgram` err=-11 | 数值错误，最危险 |
| **慢** | **本次：batched 静默回落 dense-loop，-58%，5 天无人知** | 隐性，最贵 |

**方向：一张路由表（route table）作为唯一事实源。**

```c
// 声明式，一处描述一个内核路线
{ .kernel="mul_mat_id_q4_k_f32_batched", .types={Q4_K},
  .planes_needed={ Q, D, DM, S, SEFF, MEFF },            // set_tensor 据此建平面（依赖，而非巧合）
  .gates={ Shape{K_mult:256, M_mult:128}, DeviceGen{A8X+}, Contig{}, NoView{} },
  .cost_class=COST_ONE_DISPATCH, .fallback=ROUTE_DENSE_LOOP, .owner="moe" }
```

三条硬约束：
1. `set_tensor` **因为表要求**才建平面 —— 平面与派发不可能不一致；
2. 派发只查表，**不允许**出现表外的 `if (getenv(...))`；
3. 任何 `fallback != ROUTE_NONE` 的触发**必须记账并打日志**（见缺失三）。

收益：q4_0/q4_K 缺 `es_base` 视图支持（:24773 那句硬 `return false`）这类"只补一半"的缺陷，
在表上会直接显示成 `NoView` 与 `supports_op` 不一致 —— 变成一次 host 侧单测失败，而不是两小时 adb 考古。

## 2. 结构性缺失二：只判"能不能"，从不判"值不值"

`supports_op` 返回 bool。所有"其实 CPU/GEMV 更快"的例外都是手写一行硬编码：

- A7X `lm_head` → CPU（:10168，理由 "E031.41 把 flat K-quant GEMV 编错了"）
- prefill decline `!uses_gemm && !small_weight && src1->ne[1]>=512`（:10181）
- SSM/SSM_SCAN 在 A8X 上 `return false`，靠 `GGML_OPENCL_SSM_A8X=1` 手工放行（:10077）
- dense dense-loop 准入 `K%256`（Q4_K）；dense `MUL_MAT` 故意不 offload（"probe8: 740 上 proj 慢 4.5×"）

这些理由今天只活在注释和作者记忆里，**没有数据、没有复测、换台机器就作废**。
`use_adreno_moe_kernels` 直接把 A6X/A7X/UNKNOWN 全排除 → 老 Adreno 上 MoE 只能 CPU，
这条决策的成本至今没人量过。

**方向：成本模型取代布尔，且用实测标定。**

- 每个（op × 类型 × 形状桶 × 设备指纹）→ 预测 `us/op`，来自设备首启时的微探针标定。
  **基建你已经有了**：`moe_probe9_sta3` 已经在报 `us/op / per-GEMV / GB/s`，只是它活在 `/data/local/tmp`，
  没有回灌进决策。
- 决策 = `min(预测 GPU 成本 + 提交开销×派发数, CPU 成本)`。本次这类"提交受限"（每 token ~1100 次提交、
  227ms 用户态 CPU）只有把**提交开销**建进模型才可能被自动识别；今天它只能靠人肉数线程。
- 预测 vs 实测闭环：每 N token 比对，偏差超阈值就 log 一行 `route prediction off by 3.1x` ——
  这就是自动回归探测，不需要等人来问"是不是变慢了"。

## 3. 结构性缺失三：静默降级是架构级缺陷（本次真正的教训）

一个共同模式反复出现：**系统降级了，却报告成功。**

| 降级 | 有没有日志 |
|---|---|
| batched MoE → dense-loop（七道 `return false`） | **无** |
| 哪些 op 留在 CPU（本次 46MB CPU compute buffer = KDA 孤岛） | **无** |
| Vulkan → CPU（当年 turnip 缺 `libhardware.so`，全模型静默掉 CPU） | 有，但埋在引擎日志深处，UI 只说"Vulkan 不可用" |
| mmproj 视觉塔静默落在 Vulkan（JNI 只匹配 `backend=="opencl"`） | **无** |
| OOM 守卫 `旁路=开`，只按权重预检、不为 KV/compute 预留（16K 那轮 free=13M 被系统杀） | 有一行，但没有"这很危险"的语义 |
| catalog 把拿不到 batched 的 Q4_0 标成「GPU 加速」 | 标签与代码无关，无法校验 |

这就是"脚痛医脚、头病医头"的根因：**没有反馈回路，所以你只能自己当反馈回路。**
本次从"用户说慢"到"确认 batched 没跑"花了多少轮，就是这项缺失的价格。

**方向：自报告运行时（self-reporting runtime），把降级变成一等事件。**

加载完必须打印一份结构化 report（一次，进 App 推理日志，且可被 CI diff）：

```
[engine-report] device=Adreno830 gen=A8X clcompiler=E031.47.18.49 backend=OpenCL
  route: MUL_MAT_ID q4_K -> batched@OK      planes=SEFF,MEFF built@load(38ms)
  route: SSM_SCAN         -> CPU_ISLAND      reason=GGML_OPENCL_SSM_A8X gate   ops=432/tok copy=60ms
  route: out_proj q4_K    -> GEMV            reason=ne1<512 small_weight       (predict 0.8ms)
  offload: layers 25/25 | KV q4_0/f16 | compute 322MB(GPU)+46MB(CPU) | budget w=4.49G kv=1.2G head=1.5G
  unexpected_fallback: 0        ← 不为 0 就是 bug，CI 直接红
steady-state: 1102 kernel-submissions/tok | CPU 227ms/tok | predict 8.1 tok/s actual 3.7 tok/s (2.2x off)
```

有了它：本次 2 小时定位 → 2 分钟；"内存足够时各模式都该最优"从愿望变成可验收指标。

## 4. 结构性缺失四：验收面覆盖的是"模型清单"，不是"能力类别"

基准基线是 `docs/backend_benchmark_2026-08-04.md`（8 Elite：Vulkan 8.60 / OpenCL 8.77 / CPU 4.33），
里面**没有 MoE、没有线性注意力、没有 MLA、没有 split-MoE**。
所以 10-13→10-16 那一串 MoE/SSM/slot-bank 大改，**四道门里的基准门一次都没触发**。
AGENTS.md 的四道门设计是对的（编译门抓过 `-O3` 被顶掉、内核门抓过 vendored 丢失），问题是**覆盖面漏了自研内核的主战场**。

**方向：基准矩阵按能力类别建，每类一个 pin 住的模型 + pin 住的 prompt + 每设备每后端的 tok/s 带。**

| 能力类别 | 探针模型 | 为什么必须有 |
|---|---|---|
| dense 小模型 | qwen3.5-4b | 已有 |
| **MoE top-k** | **Ling 3.0 Tiny** | 本次回归的类 |
| **MoE + 线性注意力(KDA/SSM)** | **Ling 3.0 Tiny** | CPU 孤岛税 |
| **MLA 低秩注意力** | Ling 层 3+ | 小投影走不到 Adreno GEMM |
| PTQ1_0 / PQ2_0 自定义量化 | bonsai2 / PQ2 样本 | 自研内核最多、最易崩 |
| **split-MoE（SSD 分片）** | minicpm-v4.7-35b-a3b `.experts` | GPU MoE 目前**没有可用路线** |
| 视觉塔 mmproj | MiniCPM-V | 已有静默错后端史 |
| MTP / dspark 草稿 | 现有 dspark 头 | 草稿路径独立 |

两个必须新增的一等指标（本次故障在 tok/s 上表现为"能跑，就是慢"）：
**`kernel-submissions/token`** 与 **`CPU us/token`**。30 秒就能看出提交受限，不用数线程。

**并且：显式拒绝优于静默降级。** 支持矩阵（设备类 × 量化 × 路线）必须是**显式的小集合**，
矩阵外**加载即拒绝并说明原因**，而不是"能跑但慢 3 倍"。今天 Q8_0/Q5_K/Q6_K/IQ\* 的 MoE 其实在 CPU，
UI 却显示 OpenCL —— 这是产品层的谎。

## 5. 结构性缺失五：fork 补丁面没收敛，升级即回归

`ggml-opencl.cpp` 33,516 行里 **122 个 `[dspark]` 手改标记、136 个 env、56 个按量化分支的开关**。
上次升级到 master@848bbda 是 **20 个文件 / 47 个冲突 hunk**，且同期 kleidiai v1.24→v1.31。
每次升级，策略与上游代码搅在一起重新解一遍 —— 静默回归的温床。
（Vulkan 侧 fork 一个标记都没加，只加了 4 个默认 env + turnip 直载，代价小得多。）

**方向：策略外置，上游文件接近原样。**

```
third_party/llama.cpp/
  ggml/src/ggml-opencl/
    tongyi_route_table.{h,cpp}   ← 声明式路线表 + 设备/编译器指纹 + 已知坏内核隔离名单
    tongyi_planes.cpp            ← 预打包平面的建立（依赖表，不依赖调用顺序）
    tongyi_report.cpp            ← 自报告 / 降级记账 / 稳态指标
    ggml-opencl.cpp              ← 只留 3 个 hook 调用
```

附带三个红利：
- **可 host 单测**：路线表是纯数据 + 纯函数，`(type, shape, device-fingerprint) -> route` 可在 PC 上断言。
  "q4_K 视图缺 es_base" 这类缺陷在 `gradle test` 阶段就红，不需要真机。
- 上游同步从"解 47 个 hunk"变成"改 3 个 hook"，策略文件自己 merge 自己。
- env 从 136 收敛到"每个都有 owner + 默认值 + 基准"的少数诊断开关。

## 6. 顺带必须修的三件小事（都是同类"无反馈"的产物）

1. **一个诚实的内存会计**：`weights + KV + compute(GPU+CPU) + headroom` 单一预算器，
   被 OOM 守卫、`n_ctx` 夹逼、UI 推荐 n_ctx 三方共用。现在守卫只算权重（4.49GB+256MB）且
   `旁路=开` 静默放行 → 16K 那轮 free=13M 被系统杀。**"内存刚好够时反而最慢/直接死"就是缺这个。**
2. **内核隔离名单变成数据**：`E031.47 q4_K codegen 损坏`、`E031.41 flat K-quant GEMV 编错`、
   `perm 参数触发 E031.47`、`half 关键字 err=-11`、厂商 `gemv_moe/gemm_moe` 全部数值损坏 ——
   今天每个发现变成文件里又一个 `if`；应该是一张 `known_bad_kernels` 表 + init 期全量编译验证（编译失败即该路线关闭并记录）。
3. **catalog 标签改为派生**：`「GPU 加速」「OpenCL batched MoE 通用内核」` 现在手写，与代码无关，
   已出现"推荐 Q4_K_M、加速标 Q4_0、两个都拿不到 batched"的谎。标签应由路由表算出。

## 7. 战略层面的一个取舍（最贵也最省的决定）

现在同时维护 **4 条 MoE GPU 路线** × 3 个量化 × 视图/非视图 × 设备代数：
自研 batched（q4_0/q4_K/q3_K）、自研 dense-loop、厂商单派发（830 上损坏）、slot-bank（GPU bank 未调优、
`OFFLOAD_MMID` 一开就 SIGSEGV）—— **组合爆炸，一个人维护。**

必须回答的问题：**Adreno 上的主 GPU 后端到底是哪个？**

| 选项 | 论据 |
|---|---|
| A. 自研 OpenCL 为主（现状） | 已投入最重（47k 行内核）；但 136 env / 277 个 return false 的复杂度全在你身上，且**上游没人帮你** |
| B. Vulkan(+turnip) 为主，OpenCL 退为兜底 | ggml-vulkan 有上游持续动量（fork 未改一行、只有 49 env）；你已趟通 turnip 直载 + dispatcher 化 |
| C. 收窄支持设备矩阵 | 承认"只支持 8 Elite/8s Gen4 这一档 + 少数几款"，把 per-device 手改换成指纹表；其它设备只给 CPU |

我的建议：**B 做主线、A 保留 MoE 这一条真正赚的路（batched 单派发），其余路线全部隔离或删除**。
理由：MoE 单派发是**上游没有、你独有且真赚钱**的能力（它值 8.4 vs 2.9 的量级）；
而 dense GEMV/GEMM 的 per-quant per-device 精调，是上游会持续改进、你每次同步都要重付成本的地方。
**别在上游会赢的地方跟上游赛跑。**

## 8. 立刻停止做的事

1. **停止新增 env 逃生门。** 136 个已经证明这条路不可维护。新策略必须进路由表 + 附一条基准；
   只允许保留"诊断类"env（日志/计时），且需要 owner + 默认关。
2. **停止按量化类型/机型手写 `if`。** 那 56 个按 quant 分支的 env 就是技术债的账面数字。
3. **停止把已知损坏的厂商内核留在树里**"以防有用"。它害死了那次 `test-backend-ops` abort 排查。
4. **停止只用 tok/s 验收。** 加 `submissions/token` 与 `CPU us/token`。
5. **停止"能跑就行"的静默回落。** 降级必须记账、必须打日志、CI 里 `unexpected_fallback != 0` 就红。

## 9. 落地顺序（每步都自带回报，可独立停）

| 阶段 | 工作量 | 交付 | 直接回报 |
|---|---|---|---|
| **P0** | 1 天 | 七道 `return false` 插桩 + 一份 `[engine-report]`（先只打路由与稳态指标） | **本次 Ling 回归当场定案**；此后任何"慢"问题从 2 小时降到 2 分钟 |
| **P1** | 2–3 天 | 路由表骨架，只接管 MoE（q4_0/q4_K/q3_K 三条改表驱动）；`set_tensor` 改为按表建平面；删 6–8 个 env | 派发/平面不一致从此不可能发生；q4_K 走回 batched（预期 3.7 → 8+ tok/s） |
| **P2** | 3–5 天 | 首启微探针标定（复用 `moe_probe` 基建）+ 预测/实测闭环 + 基准矩阵补 6 个能力类别 + 两个新指标 | 基准门第一次真正能拦 MoE 类回归 |
| **P3** | 1 周 | 策略外置成 `tongyi_*.{h,cpp}` + host 侧路由表单测 + 上游同步流程重跑 | 下次升级从 47 hunk 降到机械合并；缺陷左移到 PC |
| **P4** | 决策 | 第 7 节的主后端取舍 + 支持矩阵显式化（矩阵外拒绝） | 维护面砍一半，产品不再显示假 GPU |

**建议现在就批的只有 P0**（3 行日志 + 一份 report，不动任何数值路径，`third_party/llama.cpp` 只改不提交）。
它既是本次回归的定案手段，也是后面所有阶段的载体 —— 没有可观测性，路由表和成本模型都无从验收。

## 10. 怎么知道方向对了（可机检的五个数）

| 指标 | 现在 | 目标 |
|---|---|---|
| 不同 env 开关数 | 136 | < 30（每个有 owner + 默认值 + 基准） |
| `[dspark]` 手改标记（ggml-opencl.cpp） | 122 | < 20（策略搬进 `tongyi_*`） |
| 从"发现慢"到"定位到具体门" | ~2 小时（本次，含 4 次误判） | < 2 分钟（读 log） |
| 上游同步冲突 hunk | 47 | < 10 |
| 每次加载的 `unexpected_fallback` | 未知（无法测） | 恒为 0 |
| 支持矩阵外配置的处置 | 静默降级、UI 显示 GPU | 加载即拒绝 + 原因 |
