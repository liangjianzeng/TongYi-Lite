## 1. 立项理由：过去对 Vulkan 的负面判断，来源全部可追溯到 fork 自身缺陷

| 当年的"Vulkan 不行" | 定案真因 | 类别 |
|---|---|---|
| 加载任何模型都失败、回落 CPU | turnip `dlopen` 缺 `libhardware.so`（App 命名空间不能 dlopen 系统 HAL）→ `backend_ptrs.size()=1` | **打包缺陷**（已修：jniLibs stub） |
| 升级后启动 SIGSEGV | b11267 混用 11 处裸 Vulkan loader 符号，turnip device 传进系统函数 | **移植遗漏**（已修：dispatcher 化） |
| Adreno 825 空输出 | `GGML_VK_TURNIP` / `NO_SUBGROUP` / `NO_MMV` 被上游删除，fork 未回带 | **移植遗漏**（已修：三个 env 回带） |
| "Vulkan 8.60 vs OpenCL 8.77" | **基本平手**，且是稠密模型，不含 MoE/线性注意力 | 不构成"Vulkan 差"的证据 |
| "简单对话 Vulkan tok/s 失真" | **AGENTS.md 明文待办，从未实测** | 计时口径可疑 = 结论不可信 |
| bonsai2 Vulkan 掉 CPU | `supports_op` 无 PTQ1_0/PQ2_0 | 真实缺口（仅自定义量化） |

**没有任何一条是"Vulkan 在 Adreno 上慢"的实测证据。** 这不是技术判断，是记忆污染。

## 2. 清单证据：Ling 的每个零件都是 Vulkan 的主场

Ling 3.0 Tiny（`bailingmoe3`）= 混合 KDA 线性注意力 + MLA + 128 专家 MoE + swiglu + top-8 路由。
Vulkan 侧 `case GGML_OP_*` 显式覆盖（grep 全量）：

```
MUL_MAT_ID  ADD_ID  GLU  TOP_K  GET_ROWS  RMS_NORM  ROPE  SOFT_MAX  FLASH_ATTN_EXT
SSM_CONV  SSM_SCAN          ← KDA 那座 CPU 岛在 Vulkan 上有原生内核（OpenCL 侧靠 GGML_OPENCL_SSM_A8X 手工放行）
GATED_DELTA_NET  GATED_LINEAR_ATTN  RWKV_WKV6  RWKV_WKV7  LIGHTNING_INDEXER  DSV4_HC_PRE/POST
```

两条决定性事实：

1. **MoE 融合上游已实现**：`ggml_vk_can_fuse(ctx, cgraph, i, {MUL_MAT_ID, ADD_ID, MUL})` 与
   `{MUL_MAT_ID, ADD_ID}`（:14550-14556）—— 这正是自研 batched 内核手写的东西，且是图级融合。
2. **线性注意力的融合内核上游只往 Vulkan 加**（`GATED_DELTA_NET` / `GATED_LINEAR_ATTN` / `RWKV_WKV6-7` /
   `LIGHTNING_INDEXER`），**OpenCL 侧一个都没有** → 在 OpenCL 线上，这类模型按构造必然掉 CPU 岛。

量化覆盖：`Q4_0 50 / Q4_K 40 / Q3_K 28 / Q8_0 43 / Q5_K 31 / MXFP4 25` 处引用（OpenCL 侧 Q8_0/Q5_K/Q6_K/IQ\*
的 MoE 根本没有 GPU 路径）。

**结论：这不是"再试一个后端"，是把 Ling 这类模型放到唯一有上游动量的后端上。**

## 3. 诚实保留项（先声明，防止形成新的偏见）

| 未知 | 为什么可能翻车 | 怎么验 |
|---|---|---|
| `MUL_MAT_ID` 在 830 上是否走快路 | 取决于 coopmat/mmvq 是否可用；退化 = dequant+f16 matmul（带宽 ~4×）；那 38 个 `GGML_VK_DISABLE_*/FORCE_*` 就是特征差异的疤 | 看是否出现 dequant 路径日志 + `submissions/token` |
| `SSM_SCAN` 内核能否吃 KDA 形状（d_inner=2048 / n_head=16 / d_conv=4） | 上游内核按 mamba 形状写；KDA 可能需要 fork 补 kernel | 看 KDA 相关 op 是否仍落 CPU（对比 OpenCL 的 46MB CPU compute buffer） |
| turnip 在 Adreno 830 上的成熟度 | JNI 无条件默认 `GGML_VK_TURNIP=<APK 内置>`；830 很新，Mesa 侧可能不如系统驱动 | **必须跑 turnip ON / OFF 两组**（见第 5 节） |
| PTQ1_0 / PQ2_0 无 Vulkan `supports_op` | bonsai2 那类仍掉 CPU | 该线不承诺覆盖自定义量化 |
| 视觉塔 | JNI 的 mmproj 后端只匹配 `backend=="opencl"`（:1331-1338）→ Vulkan 下视觉塔静默错后端 | 立项期顺手修，属 JNI 侧 |

## 4. 隔离约定（硬边界，保证 Mesa/OpenCL 线不受干扰）

**本线拥有（可改）**
- `third_party/llama.cpp/ggml/src/ggml-vulkan/**`（含 `automatic/ggml-vulkan/**` 内核）
- `android/app/src/main/cpp/tongyilite_jni.cpp` 中 **Vulkan 相关分支**（turnip、mmproj 后端、出厂 env 块）
- `docs/` 本线文档、`tools/vkl_*` 脚本

**本线禁止触碰**
- `third_party/llama.cpp/ggml/src/ggml-opencl/**` 与 `kernels/*.cl` —— Mesa/OpenCL 线的领地（122 处手改正在演进，任何跨线改动都会污染两边的 A/B）
- 设备侧 Mesa 资产：`/data/local/tmp/{mesa_bionic,mesa_run,moe830}` 与 `830env.sh / ab_flush.sh / run_mesa_matrix.sh / run_kgsl_probe.sh`
- `vk_flags.conf` 里**非 `GGML_VK_*` 前缀**的行（现有 `GGML_OPENCL_MOE_KDBG / MOE_TIME / SSM_A8X / DUMP_FAILED_SRC` 是 OpenCL 线探针，保留不动）
- 基线文档 `docs/backend_benchmark_2026-08-04.md`（只读，做对比用）

**共享资源约定**
- `vk_flags.conf` 是本线唯一的运行期通道（**零编译**即可 A/B）；本线只增删 `GGML_VK_*` 行。
- 设备侧本线专用目录：`/data/local/tmp/vkl/`（日志、脚本、缓存），不复用 Mesa 线目录。
- 出包：`wt/vk-line/build/app/outputs/flutter-apk/`；覆盖安装同签名同 versionName，
  **绝不 `adb uninstall`**（设备上有 42GB 模型缓存）。

## 5. 第一里程碑：把数字变可信（**零编译**，只测量）

本次 Ling 定位暴露的最大成本是"没有可信测量"。所以本线第一件事不是写内核，是**建可信度**。

### 5.1 测量五规（从本次教训固化）
1. **外部独立时钟**与原生 `t_gen_ms/n_gen` **对账**（OpenCL 已验：原生 ~256ms vs 外部 252–264ms，原生诚实；
   **Vulkan 数字未经此对账前一律不得引用** —— 这就是 AGENTS.md 那个未结待办）。
2. **三个必报指标**：`tok/s`、`kernel-submissions/token`、`CPU us/token`（本次故障在 tok/s 上只是"慢"，
   在 submissions 上 30 秒现形）。
3. **单线程 vs 线程池**必须区分（`/proc/<pid>/task/*/stat`，`sed 's/.*) //'` 解析）—— 这是判定
   "GPU 提交受限" vs "CPU 算矩阵"的唯一手段。
4. **每轮必须留证据文件**（logcat + 采样），且先确认抓取进程存活再引用日志区间（本次踩过 `timeout` 静默结束）。
5. 结论分级：**实测 / 推断 / 撤回**，撤回要显式写在文档里（本次我自己撤回了 3 条）。

### 5.2 三个配置（同机同模型同 prompt，各 3 轮）
| 配置 | conf 关键行 | 后端设置 | 目的 |
|---|---|---|---|
| **A** | 默认（JNI 强开 `GGML_VK_TURNIP=<apk>`） | Vulkan | 现状：turnip 路线 |
| **B** | `GGML_VK_TURNIP=`（空值 → `turnip_path[0] != '\0'` 为假） | Vulkan | 系统 Adreno 驱动（8 Elite 原生） |
| **C** | 现状 OpenCL 探针 | OpenCL | **已测**：3.59 / 3.69 / 3.89 / 3.97（Q4_K_M）、2.78（Q4_0） |

判据（对 Ling Q4_K_M，基线 OpenCL 3.7 tok/s）：
- **≥ 6 tok/s 且 CPU/token < 80ms** → Vulkan 线成立，P1（把缺失基础设施在绿地实现 + 上游内核补齐）立刻启动；
- **3–6 tok/s 且 submissions/token 低但 CPU 忙** → 是 dequant 退化路径，值得补 mmvq/coopmat 路径；
- **≈ 3.7 tok/s 且 CPU 单线程 227ms** → 同一堵墙（说明瓶颈在 llama/ggml 调度层，不在后端），
  那么"换后端"这个假设被证伪，钱应全投路由表与自报告 —— **这同样是极具价值的结论。**

### 5.3 后续里程碑
- **P1**：在 Vulkan 线实现缺失基础设施（路由表 / `set_tensor` 依赖式建平面 / `[engine-report]`）——
  绿地、无 122 处手改，写完即成为 OpenCL 线将来必须满足的合同。
- **P2**：`SSM_SCAN`/KDA 形状适配 + `MUL_MAT_ID` 快路验证；每步都带 `[engine-report]` 验收。
- **P3**：把报告与基准接入 CI（基准矩阵补 6 个能力类别，见架构评估第 4 节）。
