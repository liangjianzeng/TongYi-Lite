## 0. 结论先行

1. **核心目标一个都没裁决掉。** 目标只有一句话：**MiniCPM-V4.7 35B-A3B 的 decode 全 GPU 跑在自研 Mesa 栈上，出真实 t/s，并回答"能不能赢 CPU bank"**。到今天为止：正确性 740 有条件成立、830 不成立；**真实 t/s 一个都没有**（24 份 830 e2e 日志 0.71–1.71 t/s 全部出自"带调试 printf 的 Mesa + 每 op clFlush"的最差配置）；赢没赢 CPU 从未被计算过。
2. **上一版结论的三块数据基石全是测量污染**（本文 §2 用同一颗二进制、同一台 830、三种测量条件现场复测，差距 3–4 倍）：
   - `830env.sh` 把 `GGML_OPENCL_OPFLUSH=1` **写死**（每 op 一次 clFlush）。所有"提交税 44.85µs/op、比 vendor 9.04µs/op 差 5 倍"的数都是这个安全阀压出来的，不是 Mesa 的本征成本。**同一二进制关掉 flush：11.42µs/op**（与 §11.2 M0 测得的 10.6–11.1µs/op 吻合）。
   - 在机的 Mesa 库是**逐次提交打 5 行 printf** 的调试版（一次 8 token 短跑打出 4.2 万行 trace），`MESA_LOG_LEVEL=0`/`FD_MESA_DEBUG=none` **压不住**（未做编译门）。同一条件只把 stderr 从 `/dev/null` 改成落文件：tiny-op **11.42 → 37.98µs/op（3.3×）**、q4_K GEMV **225 → 462µs（2.05×）**。
   - 参照系（CPU 腿）在同一批实验里自己漂了 **1.5–2.2 倍**（每 GEMV 69µs / 102µs / 153µs 三个版本互现），违反总档 §2 自家纪律「交错 A/B、90s 冷却」。
3. **真正的堵点不是性能，是两件事**：
   - **一个没修的 Mesa 提交层 bug**：深异步积压下 kernel 丢失/乱序（271390 enqueued vs 118586 submitted；正确性只在"每 ≤8 op 一次 clFlush"下成立）。这**同时**是"必须开 OPFLUSH"的原因，和"提交税看起来 5 倍于 vendor"的原因。修掉它 = 全图深异步 + 单提交成立 = M2 的整个前提。
   - **一个从没做过的干净测量**：Mesa 栈上的 GPU 纯执行时间、专家流式 IO 占比，至今是空白。§8 那张天花板推演表（150ms GPU 执行 / 110ms 合计 / 8–10 t/s）**全部来自 vendor OpenCL 的 x7 分解**，从没按 Mesa 的实测算过一遍。
4. **所以：这条线没有被证伪，它连一次有效实验都还没做过。** 允许谈止损的前提，是 §6 那三条硬判据齐备之后的数——今天的数不具备这个资格。

## 1. 核心目标与里程碑（唯一裁决口径）

**战略目标（多轮继承，不变）**：MiniCPM-les MoE 推理全部跑在自研 Mesa rusticl + freedreno(ir3) + kgsl 栈上；全 GPU 卸载面向**所有 MoE 模型**，MiniCPM-V4.7 只是攻坚载体（与 Qwen3.6-35B-A3B 同构 + 最严苛压力测试）。

**本线唯一裁决问题（总档 §1.1）**：decode 全 GPU 卸载做到极致，**能不能赢 CPU**。

三层里程碑，逐层解锁，不许跳层谈下一层：

| 层 | 里程碑 | 验收判据（可机检） | 当前状态 |
|---|---|---|---|
| L1 正确性 | 全 GPU 输出与 CPU 参照逐 token 一致 | `E2E_FORCE_SEQ` 教师强制 48 token，GPU/CPU 文本与 logits 一致；**不依赖任何 per-op clFlush/clFinish** | 740 ✅（**但依赖 OPFLUSH=1**）；830 ❌（MUL_MAT_ID 崩 + 22 FAIL） |
| L2 真实数字 | 出可信 decode t/s + 预算分解 | 同一会话交错 A/B ×3 轮，方差 ≤5%；分项（提交税/GPU 执行/专家 IO/同步）之和与总时长 ±10%；构建变体无调试 trace | ❌ **从未产出** |
| L3 裁决 | 与 CPU bank 8.07 t/s（830）对决 | L2 口径下 ≥ 8.07 为赢；6.5–8.07 为"可用但需 M3"；<6.5 才允许谈止损 | ❌ 未计算 |

> 生产基线（对照用，别记错机器）：**830 CPU bank 8.07 t/s**（主战场、裁决对手）；740 CPU bank 热稳态 3.0–3.4 t/s（调试载体，10-16 已判"GPU 路径结构性出局"，**只当回归对照，不得替 830 定罪**）。

#### 2.5.1 每 token 预算分解（同一协议下的"诊断腿"，stderr 落文件才有这两项，不参与计时）

64 token，`IO_THREADS=1`（⇒ `pread` 累计即串行墙上时间）：

| 项 | MESA_FLUSH1（正确输出） | MESA_ASYNC（乱码输出） | 口径 |
|---|---|---|---|
| decode 总时间 | ~714 ms/token | ~917 ms/token | `METRIC wall_ms/gen` |
| **专家流式 IO（pread 累计）** | **312 ms/token**（255 miss，328 MiB/token） | 825 ms/token（580 miss，747 MiB/token） | `total[decode] pread` |
| **kgsl 提交次数** | **2656 次/token**（每 op 一次 flush） | 206 次/token | `KGSLSUBMIT cmd[]` 计数 |
| BO 释放次数 | 9000 次/token（`size=32768`） | 1710 次/token | `BORERELEASE` 计数 |
| **Mesa trace 行数** | **≈15000 行/token**（SUBMIT+FDBATCH+BORERELEASE+CSDESC） | ≈2300 行/token | 同上 |
| GPU 纯执行时间 | **仍未量到**（被上面三项淹没） | 仍未量到 | 空白 §2.4-1 |

**这张表改变了优先级的排法**：

- 今天的 Mesa token 时间不是"GPU 慢"，而是**三笔可归因的开销**：专家 IO（312ms，43%）+ 每 op flush 的提交（2656 次/token，按 §2.1 的 45µs 档估 ~120ms）+ Mesa 调试版逐提交 printf（≈15000 write/token，估 150–450ms）。三者相加已覆盖整 token 时间。
- **专家 IO 从来没被当成 Mesa 线的一等公民**：35B-A3B-les 每 token 要从盘上读 **328 MiB**、miss 255 次。`IO_THREADS=1` 时这就是 312ms 的串行墙上时间，比历史 CPU bank 基线（124ms/token）还大一倍。**短腿⑤（FGSVM→UMA 直写）+ bank 命中率的优先级必须提到与 P2 同级**。
- async 腿 IO 更惨（46.7 GiB / 64 token）是**因果倒置**：输出乱码 ⇒ 路由乱跳 ⇒ 专家缓存几乎全 miss。所以 async 的 IO 数只能证明"正确性 bug 会顺带把 IO 打死"，不能当独立结论用。
- `BORERELEASE` 每 token 9000 次 × 32 KiB 与 `FDBATCH flush` 1:1 于 `KGSLSUBMIT cmd[]` ⇒ **每次提交都在建/拆一个 32KiB BO**（`use_heap=false` 老路径），这就是 P2 的头号嫌疑，也是纯 CPU 侧可测可修的点。

#### 2.5.2 P2 首轮定位扫描：kernel 丢失是"积压深度"相关（15:04 起，830 中途掉线，已复现部分入库）

|---|---|---|---|---|---|
| A_ofl0 | 0（Mesa 自定阈值） | 8753 | 67251 | 7.7 | **崩（乱码）** |
| A_ofl1 | 1 | 101554 | 340492 | 3.35 | ✅ |
| A_ofl2 | 2 | 76554 | 268488 | 3.51 | ✅ |

| A_ofl8/16/64 | — | 未取到（830 掉线，`error: closed`） | | | 待复跑 |

**已经能定性的三件事**：

1. **不是"异步"本身坏，是"积压深度"坏**：`OPFLUSH=0` 时 Mesa 自己合批（8753 次提交摊 ~2700 op/token ⇒ 每 IB 合并约 **11.6 个 op**）→ 必崩；而把未 flush 的 op 数压到 **≤4** 就正确。⇒ 病灶收窄成"Mesa 软队列/IB 复用在积压超过几个 op 之后丢 kernel"，而不是笼统的"rusticl 异步不可用"。
2. **提交税有一档免费缓解**：提交数随 OPFLUSH 线性下降（101554 → 76554 → 47002，N=1→4 少 54%），而正确性在 N≤4 全部保持 ⇒ 生产上可先用 `OPFLUSH=4` 而不是 `1`。收益必须在 **trace-off 构建**上重测才算数（本表 tok/s 是 24 token 短腿 + 调试版 Mesa，噪声压不住）。
3. **BO churn 与提交同生**：每次 flush 固定 ~3.4 次 32 KiB `BORERELEASE`，async 下反而 7.7 次/提交 ⇒ 合批更深时 BO 抖动更凶，与"IB BO 提前释放/GPU 未读完就被复用"的假设一致。

**取证中断与复跑**：830 于 15:0x 掉线，A_ofl8/16/64 与 Phase B（`FD_NODEFER`/`FD_NO_BOCACHE`/`FD_FORCE_REEMIT`/`FD_KGSL_TSSYNC`/`FD_COMPUTE_WFI`/`FD_KGSL_USLEEP_US`/`inorder`/`nogrow`）全部未取。**复跑命令**：`sh /data/local/tmp/launch_p2.sh`（脚本已入库，结果幂等）。

**新增验收尺子**：`E2E_TOKDUMP=<path>` 落 i32 token 序列 → `third_party/mesa-kgsl/scripts/token_diff.py <参照> <待测...>` 报"首个分歧 token"。跑法：`sh run_p2_accept.sh 48 cpu,flush1,async,flush2`（temp=0/seed 固定）。P2 的通过定义由此变成可机检的：**`OPFLUSH=0` 与 CPU 参照 48 token 全等**。

## 3. 与目标的差距（把账摊开算）



单 token decode ≈ **4000 次 op 提交**（40 层 ×~100 op，总档 §1.2）。CPU bank 基线 8.07 t/s = **124 ms/token**。

| 预算项 | CPU bank（对手） | Mesa 现状（OPFLUSH=1 + trace） | Mesa 干净 async（P2 修好后） | 依据 |
|---|---|---|---|---|
| host 提交税 | ~0（0.34µs/op 级） | 4000×45µs ≈ **180 ms** | 4000×11.4µs ≈ **45 ms** | 本文 §2.1 A/D 行 |
| GPU 执行（小算子为主） | — | 被 trace 淹没，未知 | **未知**（vendor 参考 150ms） | 空白 §2.4-1 |
| 专家流式 IO | 与计算重叠良好 | 疑似主导（~200ms 累计） | 待 UMA 直写治 | 空白 §2.4-2 |
| 同步/调度 | ~12 ms | 未知 | 未知 | §8 |
| **合计** | **124 ms = 8.07 t/s** | **~830 ms = 1.2 t/s** | **未知 → 必须测** | — |

> **【2026-10-20 13:00 实测校正】** 上表的 CPU 对手列是**总档 §2.1 的历史值**，今天在同机同协议下复现不出来：
> 同会话交错的 CPU bank（HEAD 自建体，`ngl=99`）只有 **3.44 t/s = 291 ms/token**，早上单轮冷启动跑过 7.00 t/s，
> 扫参其它配置 4.61–5.64 t/s。**对手数不是常数，必须与 Mesa 腿同会话交错测**，否则 8.07 会把 Mesa 打得比实际更惨。
> 同理，Mesa 列的 830ms 也是污染值；今天合法测得的 Mesa 是 **flush1 730ms/token（正确）/ async 995ms/token（乱码）**，
> 且仍含 trace 打印税（估计 2–4 倍）。**裁决输入一律以 §2.5 为准，本表只保留"预算项"这个框架。**

**差距的正确表述**：

- 现在离目标差 **7 倍**（1.2 vs 8.07 t/s），但**其中至少 4 倍是自我施加的测量/配置成本**（clFlush ×3.9 与 trace ×3.3 在 tiny-op 上可叠到两位数倍率），**不是 Mesa 栈的能力上限**。
- 提交税这一项在干净 async 下只有 **45ms/token**，与 vendor（36ms）同量级 —— **"rusticl 提交税高到结构性出局" 这个说法被今天的复测直接证伪**。
- 真正决定输赢的两个未知数是 **GPU 执行时间** 和 **专家 IO 占比**；它们在总档 §8 里分别是 150ms 和 15ms 的**借用值**。赢（124ms）要求 exec+IO+sync < 79ms，也就是**必须靠融合（M3）+ UMA 直写**，这不是"再测一次就赢"，而是"L2 数字出来后按账走 M3"。
- 结论：**目标可达性 = 未证伪 + 未验证**。当前唯一诚实的动作是先花 1 天把 L2 的数字与分解做出来，再决定 M3 的投入规模；不是现在按一个 1.2 t/s 判整线死刑。
