## 0. 结论先行

1. **核心目标一个都没裁决掉。** 目标只有一句话：**MiniCPM-V4.7 35B-A3B 的 decode 全 GPU 跑在自研 Mesa 栈上，出真实 t/s，并回答"能不能赢 CPU bank"**。到今天为止：正确性 740 有条件成立、830 不成立；**真实 t/s 一个都没有**（24 份 830 e2e 日志 0.71–1.71 t/s 全部出自"带调试 printf 的 Mesa + 每 op clFlush"的最差配置）；赢没赢 CPU 从未被计算过。
2. **上一版结论的三块数据基石全是测量污染**（本文 §2 用同一颗二进制、同一台 830、三种测量条件现场复测，差距 3–4 倍）：
   - `830env.sh` 把 `GGML_OPENCL_OPFLUSH=1` **写死**（每 op 一次 clFlush）。所有"提交税 44.85µs/op、比 vendor 9.04µs/op 差 5 倍"的数都是这个安全阀压出来的，不是 Mesa 的本征成本。**同一二进制关掉 flush：11.42µs/op**（与 §11.2 M0 测得的 10.6–11.1µs/op 吻合）。
   - 在机的 Mesa 库是**逐次提交打 5 行 printf** 的调试版（一次 8 token 短跑打出 4.2 万行 trace），`MESA_LOG_LEVEL=0`/`FD_MESA_DEBUG=none` **压不住**（未做编译门）。同一条件只把 stderr 从 `/dev/null` 改成落文件：tiny-op **11.42 → 37.98µs/op（3.3×）**、q4_K GEMV **225 → 462µs（2.05×）**。
   - 参照系（CPU 腿）在同一批实验里自己漂了 **1.5–2.2 倍**（每 GEMV 69µs / 102µs / 153µs 三个版本互现），违反总档 §2 自家纪律「交错 A/B、90s 冷却」。
3. **真正的堵点不是性能，是两件事**：
   - **一个没修的 Mesa 提交层 bug**：深异步积压下 kernel 丢失/乱序（271390 enqueued vs 118586 submitted；正确性只在"每 ≤8 op 一次 clFlush"下成立）。这**同时**是"必须开 OPFLUSH"的原因，和"提交税看起来 5 倍于 vendor"的原因。修掉它 = 全图深异步 + 单提交成立 = M2 的整个前提。
   - **一个从没做过的干净测量**：Mesa 栈上的 GPU 纯执行时间、专家流式 IO 占比，至今是空白。§8 那张天花板推演表（150ms GPU 执行 / 110ms 合计 / 8–10 t/s）**全部来自 vendor OpenCL 的 x7 分解**，从没按 Mesa 的实测算过一遍。
4. **所以：这条线没有被证伪，它连一次有效实验都还没做过。** 允许谈止损的前提，是 §6 那三条硬判据齐备之后的数——今天的数不具备这个资格。

## 1. 核心目标与里程碑（唯一裁决口径）

**战略目标（多轮继承，不变）**：MiniCPM-les MoE 推理全部跑在自研 Mesa rusticl + freedreno(ir3) + kgsl 栈上；全 GPU 卸载面向**所有 MoE 模型**，MiniCPM-V4.7 只是攻坚载体（与 Qwen3.6-35B-A3B 同构 + 最严苛压力测试）。

**本线唯一裁决问题（总档 §1.1）**：decode 全 GPU 卸载做到极致，**能不能赢 CPU**。

三层里程碑，逐层解锁，不许跳层谈下一层：

| 层 | 里程碑 | 验收判据（可机检） | 当前状态 |
|---|---|---|---|
| L1 正确性 | 全 GPU 输出与 CPU 参照逐 token 一致 | `E2E_FORCE_SEQ` 教师强制 48 token，GPU/CPU 文本与 logits 一致；**不依赖任何 per-op clFlush/clFinish** | 740 ✅（**但依赖 OPFLUSH=1**）；830 ❌（MUL_MAT_ID 崩 + 22 FAIL） |
| L2 真实数字 | 出可信 decode t/s + 预算分解 | 同一会话交错 A/B ×3 轮，方差 ≤5%；分项（提交税/GPU 执行/专家 IO/同步）之和与总时长 ±10%；构建变体无调试 trace | ❌ **从未产出** |
| L3 裁决 | 与 CPU bank 8.07 t/s（830）对决 | L2 口径下 ≥ 8.07 为赢；6.5–8.07 为"可用但需 M3"；<6.5 才允许谈止损 | ❌ 未计算 |

> 生产基线（对照用，别记错机器）：**830 CPU bank 8.07 t/s**（主战场、裁决对手）；740 CPU bank 热稳态 3.0–3.4 t/s（调试载体，10-16 已判"GPU 路径结构性出局"，**只当回归对照，不得替 830 定罪**）。

#### 2.5.1 每 token 预算分解（同一协议下的"诊断腿"，stderr 落文件才有这两项，不参与计时）

64 token，`IO_THREADS=1`（⇒ `pread` 累计即串行墙上时间）：

| 项 | MESA_FLUSH1（正确输出） | MESA_ASYNC（乱码输出） | 口径 |
|---|---|---|---|
| decode 总时间 | ~714 ms/token | ~917 ms/token | `METRIC wall_ms/gen` |
| **专家流式 IO（pread 累计）** | **312 ms/token**（255 miss，328 MiB/token） | 825 ms/token（580 miss，747 MiB/token） | `total[decode] pread` |
| **kgsl 提交次数** | **2656 次/token**（每 op 一次 flush） | 206 次/token | `KGSLSUBMIT cmd[]` 计数 |
| BO 释放次数 | 9000 次/token（`size=32768`） | 1710 次/token | `BORERELEASE` 计数 |
| **Mesa trace 行数** | **≈15000 行/token**（SUBMIT+FDBATCH+BORERELEASE+CSDESC） | ≈2300 行/token | 同上 |
| GPU 纯执行时间 | **仍未量到**（被上面三项淹没） | 仍未量到 | 空白 §2.4-1 |

**这张表改变了优先级的排法**：

- 今天的 Mesa token 时间不是"GPU 慢"，而是**三笔可归因的开销**：专家 IO（312ms，43%）+ 每 op flush 的提交（2656 次/token，按 §2.1 的 45µs 档估 ~120ms）+ Mesa 调试版逐提交 printf（≈15000 write/token，估 150–450ms）。三者相加已覆盖整 token 时间。
- **专家 IO 从来没被当成 Mesa 线的一等公民**：35B-A3B-les 每 token 要从盘上读 **328 MiB**、miss 255 次。`IO_THREADS=1` 时这就是 312ms 的串行墙上时间，比历史 CPU bank 基线（124ms/token）还大一倍。**短腿⑤（FGSVM→UMA 直写）+ bank 命中率的优先级必须提到与 P2 同级**。
- async 腿 IO 更惨（46.7 GiB / 64 token）是**因果倒置**：输出乱码 ⇒ 路由乱跳 ⇒ 专家缓存几乎全 miss。所以 async 的 IO 数只能证明"正确性 bug 会顺带把 IO 打死"，不能当独立结论用。
- `BORERELEASE` 每 token 9000 次 × 32 KiB 与 `FDBATCH flush` 1:1 于 `KGSLSUBMIT cmd[]` ⇒ **每次提交都在建/拆一个 32KiB BO**（`use_heap=false` 老路径），这就是 P2 的头号嫌疑，也是纯 CPU 侧可测可修的点。

**已经能定性的三件事**：

1. **不是"异步"本身坏，是"积压深度"坏**：`OPFLUSH=0` 时 Mesa 自己合批（8753 次提交摊 ~2700 op/token ⇒ 每 IB 合并约 **11.6 个 op**）→ 必崩；而把未 flush 的 op 数压到 **≤4** 就正确。⇒ 病灶收窄成"Mesa 软队列/IB 复用在积压超过几个 op 之后丢 kernel"，而不是笼统的"rusticl 异步不可用"。
2. **提交税有一档免费缓解**：提交数随 OPFLUSH 线性下降（101554 → 76554 → 47002，N=1→4 少 54%），而正确性在 N≤4 全部保持 ⇒ 生产上可先用 `OPFLUSH=4` 而不是 `1`。收益必须在 **trace-off 构建**上重测才算数（本表 tok/s 是 24 token 短腿 + 调试版 Mesa，噪声压不住）。
3. **BO churn 与提交同生**：每次 flush 固定 ~3.4 次 32 KiB `BORERELEASE`，async 下反而 7.7 次/提交 ⇒ 合批更深时 BO 抖动更凶，与"IB BO 提前释放/GPU 未读完就被复用"的假设一致。

**取证中断与复跑**：830 于 15:0x 掉线，A_ofl8/16/64 与 Phase B（`FD_NODEFER`/`FD_NO_BOCACHE`/`FD_FORCE_REEMIT`/`FD_KGSL_TSSYNC`/`FD_COMPUTE_WFI`/`FD_KGSL_USLEEP_US`/`inorder`/`nogrow`）全部未取。**复跑命令**：`sh /data/local/tmp/launch_p2.sh`（脚本已入库，结果幂等）。

**新增验收尺子**：`E2E_TOKDUMP=<path>` 落 i32 token 序列 → `third_party/mesa-kgsl/scripts/token_diff.py <参照> <待测...>` 报"首个分歧 token"。跑法：`sh run_p2_accept.sh 48 cpu,flush1,async,flush2`（temp=0/seed 固定）。P2 的通过定义由此变成可机检的：**`OPFLUSH=0` 与 CPU 参照 48 token 全等**。

**【17:40 P2 拿到一条上游级实锤 + K40 掉线】** 在读 fork 已安装产物（见 §5.1 勘误）时定位到提交路径的可疑核心，就是上游 `freedreno_ringbuffer_sp.c` 的**延迟提交合并**：

```c
static bool should_defer(struct fd_submit *submit) {
   if (fd_submit->nr_bos > 30) return false;
   /* On the kernel side, with 32K ringbuffer, we have an upper limit of 2k
    * cmds before we exceed the size of the ringbuffer, which results in
    * deadlock writing into the RB (ie. kernel doesn't finish writing into
    * the RB so it doesn't kick the GPU to start consuming from the RB) */
   if (submit->pipe->dev->deferred_cmds > 128) return false;
   return true; }
```
（`freedreno_ringbuffer_sp.c:309-326`，决策点 `:381` `if (!use_fence_fd && !has_shared && should_defer(submit))`）

⇒ 三点：① **上游自己就写了"超过环容量 → 内核写不完 RB → 不 kick GPU"**，而这句话的前提是 **msm 的 32K 环 / 2k cmds**；kgsl 下游内核的 drawctxt 环大小与 IB 记账完全不同 ⇒ **"enqueued 271390 > submitted 118586、ioctl 返回 0、GPU 根本没被 kick、kernel 静默消失"正是这段注释描述的事故形状**。② 那个 `assert(dev->deferred_cmds == fd_dev_count_deferred_cmds(dev))` 在 `-Db_ndebug=true` 下不存在，不变量没人守。③ 反汇编 `fd_submit_sp_flush`（436 行、36 处调用）确认它确实调 `flush_deferred_submits` + `_mesa_hash_table` + `fd_bo_add_fence` ⇒ 这条路**在跑**，不是死代码。

⇒ 不许越界的三条口子：① 这只证明**这一处**分歧无害，"每个 kernel 都对"要靠 P3 的同形状 NMSE 矩阵（ir3 vs vendor vs CPU）；② 1 次运行 / 1 条 prompt / gen6 / 带 trace 构，换 prompt 与换 gen 需复验；③ 噪声尺度 0.98 是"最坏单个值"，不是分布的上界。

## 3. 与目标的差距（把账摊开算）



单 token decode ≈ **4000 次 op 提交**（40 层 ×~100 op，总档 §1.2）。CPU bank 基线 8.07 t/s = **124 ms/token**。

| 预算项 | CPU bank（对手） | Mesa 现状（OPFLUSH=1 + trace） | Mesa 干净 async（P2 修好后） | 依据 |
|---|---|---|---|---|
| host 提交税 | ~0（0.34µs/op 级） | 4000×45µs ≈ **180 ms** | 4000×11.4µs ≈ **45 ms** | 本文 §2.1 A/D 行 |
| GPU 执行（小算子为主） | — | 被 trace 淹没，未知 | **未知**（vendor 参考 150ms） | 空白 §2.4-1 |
| 专家流式 IO | 与计算重叠良好 | 疑似主导（~200ms 累计） | 待 UMA 直写治 | 空白 §2.4-2 |
| 同步/调度 | ~12 ms | 未知 | 未知 | §8 |
| **合计** | **124 ms = 8.07 t/s** | **~830 ms = 1.2 t/s** | **未知 → 必须测** | — |

> **【2026-10-20 13:00 实测校正】** 上表的 CPU 对手列是**总档 §2.1 的历史值**，今天在同机同协议下复现不出来：
> 同会话交错的 CPU bank（HEAD 自建体，`ngl=99`）只有 **3.44 t/s = 291 ms/token**，早上单轮冷启动跑过 7.00 t/s，
> 扫参其它配置 4.61–5.64 t/s。**对手数不是常数，必须与 Mesa 腿同会话交错测**，否则 8.07 会把 Mesa 打得比实际更惨。
> 同理，Mesa 列的 830ms 也是污染值；今天合法测得的 Mesa 是 **flush1 730ms/token（正确）/ async 995ms/token（乱码）**，
> 且仍含 trace 打印税（估计 2–4 倍）。**裁决输入一律以 §2.5 为准，本表只保留"预算项"这个框架。**

**差距的正确表述**：

- 现在离目标差 **7 倍**（1.2 vs 8.07 t/s），但**其中至少 4 倍是自我施加的测量/配置成本**（clFlush ×3.9 与 trace ×3.3 在 tiny-op 上可叠到两位数倍率），**不是 Mesa 栈的能力上限**。
- 提交税这一项在干净 async 下只有 **45ms/token**，与 vendor（36ms）同量级 —— **"rusticl 提交税高到结构性出局" 这个说法被今天的复测直接证伪**。
- 真正决定输赢的两个未知数是 **GPU 执行时间** 和 **专家 IO 占比**；它们在总档 §8 里分别是 150ms 和 15ms 的**借用值**。赢（124ms）要求 exec+IO+sync < 79ms，也就是**必须靠融合（M3）+ UMA 直写**，这不是"再测一次就赢"，而是"L2 数字出来后按账走 M3"。
- 结论：**目标可达性 = 未证伪 + 未验证**。当前唯一诚实的动作是先花 1 天把 L2 的数字与分解做出来，再决定 M3 的投入规模；不是现在按一个 1.2 t/s 判整线死刑。

2. **唯一能白拿的同类实现 = libdrm 2.4.126**（与在机那颗 `libdrm_freedreno.so.1.126.0` 同版本，487 KB tarball 已下到 `/tmp/mesa_ab/drm/`）。它的 `freedreno/kgsl/kgsl_ringbuffer.c` 是 2013 年 Rob Clark 写的老后端，三条硬事实：
   - `kgsl_ringbuffer_flush()`：单 `ibdesc`，`sizedwords = ring->cur - last_start`，提交后置 `ring->last_start = ring->cur`；
   - `assert(in_fence_fd == -1); assert(out_fence_fd == NULL);` ⇒ **这份 kgsl 后端不支持 fence**；
   - `kgsl_ringbuffer_new()` 里 `assert(!flags)`、`fd_ringbuffer_grow()` 里 `assert(ring->funcs->grow); /* unsupported on kgsl */` ⇒ **环不能 grow，大小在建环时用 `IOCTL_KGSL_GPUMEM_ALLOC` 一次定死**；而我们是 `-Db_ndebug=true` 构建，**这些 assert 在机器上根本不存在**。
3. **假设（可判定，未证）**：Mesa 26 的 gallium 走 `fd_submit_new_ringbuffer()`（submit-packet 模型，上游只在 msm/virtio 上被跑过），移植过来的 kgsl 后端却是"无 fence / 不能 grow / 单 ibdesc"的 2013 模型。深队列（`OPFLUSH=0`）时一个环要装下整张图 ~3400 个 compute 的 CS，而 **gen7(a7xx) 每个 dispatch 的 CS 比 gen6 大得多**（IFPE/`CP_SET_MODE`/perfcounter 记录）⇒ gen7 更容易顶破固定环，NDEBUG 下越界不报错 ⇒ 症状恰好是"ioctl 返回 0、无错、kernel 静默消失"。
   ⇒ 这条假设**天生解释了 §2.6 的 gen6/gen7 分裂**（K40 今天四次复现失败 + 四维加压零复现，是它的正面证据），也解释了 `submitted(118586) < enqueued(271390)`。
4. **不靠源码就能判定的观测（下次 830 上线第一条腿）**：取 `FDBATCH flush: ... size=%d`（即 `sizedwords`）的**每次提交峰值**，与环容量比。预测：830 的 `async` 腿 `max(size)` 会钉在环上限（且伴随提交数骤降 / `size` 突然回落），`flush1` 腿远低于上限；K40 两腿都远低于上限。取数式已埋在脚本里：`grep -aoE 'FDBATCH flush:.*size=[0-9]+' <leg>.err | awk -Fsize= '{print $2}' | sort -n | tail -1`。

**这条假设如果成立，修法不在 rusticl 而在提交层**：kgsl 环要么按 sp 模型支持 grow/链式 IB，要么在 `flush` 里强制"环满即提交并换环"（等价于 ggml 侧 OPFLUSH 的驱动版，但按字节而非按 op 数触发，代价低得多）。这也是 P5（整图单 IB）必须与 P2 同一批人做的原因。

##### 5.1b 第二条 gen 不对称嫌疑：`UCHE_TRAP_BASE` 的硬编码回退（17:14 K40 实测）

机器上那条 `MESA: error: kgsl_pipe_get_param:105: invalid param id: 13` 不是噪音，我把 13 解出来了：
`enum fd_param_id`（`src/freedreno/drm/freedreno_drmif.h:36-51`）第 13 项 = **`FD_UCHE_TRAP_BASE`**，
唯一用户是 `freedreno_screen.c:1025-1029`：

```c
if (fd_pipe_get_param(screen->pipe, FD_UCHE_TRAP_BASE, &val)) {
   screen->uche_trap_base = screen->gen >= 6 ? 0x1fffffffff000ull : 0ull;   // 查不到 -> 猜一个
} else {
   screen->uche_trap_base = val;                                            // 查到 -> 用内核真值
}
```

也就是说：**fork 的 kgsl winsys 不实现这个 param，gallium 就拿一个硬编码猜值**；而同一颗 GPU 上
turnip 走 kgsl 是老实读 `KGSL_PROP_UCHE_TRAP_BASE(0x2F)` 的（`tu_knl_kgsl.cc:1848`）。

为把它变成可判定实验，写了 [tools/kgsl_props.c](../third_party/mesa-kgsl/tools/kgsl_props.c)
（直开 `/dev/kgsl-3d0` 做 `IOCTL_KGSL_DEVICE_GETPROPERTY`，打印真值并与那个回退常量比对，
判定语自动生成），构建并入统一的 [scripts/build_tools_android.sh](../third_party/mesa-kgsl/scripts/build_tools_android.sh)。

**K40（gen6 / Adreno650v3）17:14 实测**：

```
prop 0x03 DEVICE_POWER    ioctl_rc=-1 errno=19 (No such device)
prop 0x06 MMU_ENABLE      = 0x00000100
prop 0x13 UCHE_GMEM_VADDR = 0x0000000000000000
prop 0x2f UCHE_TRAP_BASE  ioctl_rc=-1 errno=19 (No such device)   ← 内核根本不肯回答
```

⇒ 三点结论：
1. fork 报 `invalid param id: 13` 是**诚实的**——这颗下游内核连 0x2F/0x03 都是 ENODEV，**"读 KGSL 属性"这条路在 kgsl 上根本不可靠**，winsys 只能按 gen 带表（turnip 就是这么干的）；
2. gen6 上 gallium 用的是回退常量 `0x1fffffffff000`，且这是**唯一可能值**，所以 gen6 的"不丢 kernel"与此无关，不能拿它解释 gen6 健康；
3. **真正的判定实验在 830 上**：若 830 的内核肯回答 0x2F（哪怕回 0 这种 stub 值），gen7 就走 `else` 分支拿到那个值、丢掉正确的回退常量 —— **恰好是"gen6 对、gen7 错"的方向**。830 一上线第一条腿之外的第一条命令就是 `/data/local/tmp/kgsl_props`（工具已编好，push 即跑，1 秒出结论）。

1. **`ALLOW_NO_SUBGROUP=1` 是承重的**：没有它，rusticl 报这颗 FD650 没有 `cl_khr_subgroups`，ggml 直接放弃 GPU ⇒ "关掉它就数值正常"是**测量假象**，token-18 分歧**不能**归罪给它到这种程度；
2. **`FAKE_QCOM_REQD=1` 也是承重的**：只留 `ALLOW_NO_SUBGROUP` 时 `rc=1`（内核编不过/程序起不来），与 §2.6 的源码读法一致（它注入 `-D cl_qcom_reqd_sub_group_size=1`）；
3. ⇒ **今天不能"解除降级"**，P3 的靶子因此**从 ggml 侧的开关挪到 Mesa 侧**：让 rusticl 在 Freedreno 上真正暴露 `cl_khr_subgroups`（并让 ir3 的 wave 尺寸对上），这样才谈得上"关掉两个降级开关还跑得动、且与 CPU 逐 token 一致"。⇒ 下一刀 = 读 `src/gallium/frontends/rusticl` 里 subgroup 能力位的来源 + `fd_pipe`/ir3 wave size，并把"暴露 subgroup"做成可验的构建开关；验收判据不变：**两个降级开关都不传时仍走 GPU（`KGSLSUBMIT>0`）且与 CPU 48 token 全等**。

**【19:05 P3 根因当场钉死（运行时实测，不是读码猜）】** 新量具 [tools/cl_subgroup_probe.c](../third_party/mesa-kgsl/tools/cl_subgroup_probe.c)（`dlopen("libOpenCL.so")` 自取符号，不依赖 stub，换机即跑；已 push 到 `/data/local/tmp/cl_subgroup_probe`）在 K40 现场对部署的那颗 rusticl 打出：

⇒ 三种可能里 **A 成立、B/C 当场排除**：

- **C 排除**：subgroup 相关查询全部 `rc=0`；
- **A 成立**：唯独 `cl_khr_subgroups` 这个 **1.2 式**扩展被藏，而 ggml 的准入条件正是 `cl_khr_subgroups || cl_intel_subgroups`（[ggml-opencl.cpp](../third_party/llama.cpp/ggml/src/ggml-opencl/ggml-opencl.cpp) 的探测），所以它连 3.0 式的那 10 个 subgroup 扩展看都不看，直接 `drop unsupported device 'FD650'`。
⇒ **根因与修法都是两行级**（上游 Mesa 26.2.4）：`rusticl/api/device.rs:314` 的 `CL_DEVICE_SUB_GROUP_INDEPENDENT_FORWARD_PROGRESS => false` 改报 true，加 `rusticl/core/device.rs:770` 把被注释的 `add_ext(1,0,0,"cl_khr_subgroups")` 打开（注释自己写明"requires IFP"，所以这两行是一套）。
⇒ **这条比"trace-off"更值得先编**：P0-2 的自建构因此有了真正的载荷 —— 一次构建同时产出 ① trace-off 干净构（P0-2 本职）② **IFP=true + 打开 `cl_khr_subgroups`** 的构；后者一旦上机，`ALLOW_NO_SUBGROUP=1` 就不再需要，**token-18 那条降级路（`-D cl_qcom_reqd_sub_group_size=1` + 通用 subgroup shuffle）可以整体摘掉**，P3 的验收（两开关都不传、仍在 GPU 上、与 CPU 48 token 全等）第一次变得可执行。
