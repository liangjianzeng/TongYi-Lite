# 全 GPU 卸载 · Mesa 自研栈 —— L3 裁决报告（2026-10-20）

> **裁决问题**（总档 §1.1 的核心目标）：MiniCPM-V4.7 35B-A3B `-les` MoE decode **整条跑在自研 Mesa 栈**
> （`rusticl + freedreno(ir3) + kgsl`）上，能不能**赢 CPU bank**（基准 8.07 t/s，历史单点数）。
>
> **本报告的地位**：**临时裁决（provisional）**。gen6（K40）一列已达本文档要求的裁决口径（安静态 / 交错 /
> 3 轮 / trace-off）；gen7（830）一列**未达口径**，只作方向。推翻条件写在 §4，复核命令写在 §5。

---

## 1. 结论（一句话 + 三条限定）

**当前不能：Mesa decode 是 CPU bank 的 17.5%（0.55 / 3.14 t/s，gen6 三轮中位），差 ~5–6 倍；
而且今天的数据已经把"再优化提交层就能翻盘"这条希望关掉了 —— 提交层的全部可得收益 ≤15%，
距翻盘所需的 ~13× 差两个数量级。**

三条限定，防止这个结论被过度解读或被误用：

1. **不是"内核丢了一半所以慢"**：gen6 上 async 与 flush1 的 token **逐位相同**（6 次独立复核），
   两者只差 14.5% ⇒ 慢不是丢活，是**每 op 的 dispatch→完成往返 + 内核本身执行效率**。
2. **prefill 比 decode 更落后**：CPU 11.9 s vs Mesa 54–61 s（**慢 4.5–5×**）；再加上 Mesa 多出来的
   **~15 s 固定加载成本**。⇒ 端到端体验（首 token + 总时长）比 t/s 比值更难看。
3. **这不等于"Mesa 线判死"**：还没试过的高速路径至少三条（原生 subgroup 内核、算子融合、
   xmem GEMM 在 gen7 上开起来），且 gen7 的 async 正确性还没修 —— 见 §4 的可推翻条件。

## 3. 天花板算术：为什么"再优化提交层"救不回来

**已知**：async ~330 IB/token 与 flush1 ~4,100 IB/token（**提交量 12 倍**）都跑在 ~0.6 t/s，
且**提交多 12 倍的那个反而快 14.5%**。
⇒ 单次提交的边际成本 ≪ 1% token 时间（1.6 s/token 里连 16 ms 都不到）。

| 假设全部做到的理想上限 | 量级 | 依据 |
|---|---|---|
| **P5 整图单 IB / UMA gpuobj**（提交成本归零） | **≤ +15%**，即 0.63 → ~0.72 t/s | 上限就是 async↔flush1 那 14.5%（今天实测），不是老记忆里的 26 µs/op × 4k op ≈ 88 ms/token |
| **P6 算子融合**（减 op 数 = 减 dispatch→完成往返） | **未测**，是唯一还没定价的性能杠杆 | 需 `GGML_OPENCL_MOE_TIME=1` 的分 op 计时先落地 |
| **ir3 codegen / 占用率** | 未知，但按 5–6× 缺口，**必须有数量级贡献才能翻盘** | — |
| **省掉 ~15 s 固定加载成本** | 只帮"总时长"，不改 t/s | `load_ms` 实测 |

⇒ **翻盘需要 0.63 → 8.07 t/s，即 ~13×**；提交层能给的是 1.15×。⇒ **裁决（decode 半边）：不能。**
且这个结论不依赖 gen7 的干净数 —— 因为要翻的是数量级，而两台机器的比值同带。

## 8. 【19:3x–20:0x 追加】gen7 的病灶**早有档案**，而且今天拿到了**内核粒度**的判具

写这份裁决时翻到我们自己 fork 里 2026-10-14 的注释（[ggml-opencl.cpp:24697-24715](../third_party/llama.cpp/ggml/src/ggml-opencl/ggml-opencl.cpp#L24697-L24715)）：
q4_K batched MoE 在 **Adreno 830 上被主动关掉**，理由写得很死 —— "**driver-level codegen corruption, NOT a source bug**"，
证据链在 `_probe/moe_probe`（`GGML_OPENCL_MOE_KDBG=1` / `MOE_PROBE_KREF=1`）：7 种代码改写后 **NMSE 逐位相同**
（1.267501 / 23.470122 / 2.589895）、平面与 `set_tensor` 布局 host 侧逐字节正确、**同一段内核里同一个 s-plane 地址每个 subgroup 读回不同字节**、
`regA`（q 权重 image）读回的是浮点激活的位型、**同一份内核源码重编 .so 后数值还会漂**。

⇒ 这条档案把今天 gen7 的两个现象**串成一件事**：`OPFLUSH=0` 从 token 1 全崩、`OPFLUSH=1` 与 CPU 逐 token 全等，
与"内核在深队列状态下读到不一致的内存"完全同型 —— 也就是说 **gen7 的头号嫌疑从"提交层丢内核"移到"Mesa/ir3 在深队列下的内存一致性或 codegen"**。
（仍**没有**定论；但嫌疑面从整个提交层缩到一处，且已有可复现判具。）

今天为这条线新增的两个硬事实：

1. **崩点与内核族无关**：`tbo -o MUL_MAT_ID` 在 `USE_ADRENO_KERNELS=1` 与 `=0` 两条腿**逐位相同** ——
   都是 **12 OK / 41 not supported / 0 FAIL / 53 条用例行 / 3 次 panic**，且**崩在同一条用例**
   （最后打印的是 `MUL_MAT_ID(type_a=iq3_s, n_mats=1024, m=128, k=512): not supported`）。
   ⇒ 崩溃是**形状确定性的**，与用哪套内核无关 ⇒ 别再往"我们的内核写坏了"方向查。
2. **rusticl 的 printf 收集路径有一颗无下界减法**（`core/kernel.rs:2047` `buf[0..(length-4)]`）：
   `length<4` 时无符号下溢 → 越界 panic → `event.rs:101` mutex poisoned 二次 panic → abort。
   而我们 `cl/` 全目录 **0 个 `printf(`** ⇒ 缓冲区里是**垃圾**才更合理 —— **与上面那份"in-kernel 读回不一致"是同一族症状**，
   不是我们有 printf。（2026-10-14 那份档案里恰好提到当年做过 "load-bearing printf" 的代码改写，说明这条路径在这颗 GPU 上本就不干净。）

⇒ **下一刀已经换成内核粒度的判具**（不用等 Mesa 源码）：`_probe/moe_probe` 的 `moe_probe4`（`main()` 无参数，全靠 env：
`MOE_PROBE_KREF / MOE_PROBE_SAME / MOE_PROBE_UNI / MOE_PROBE_DUMP / MOE_PROBE_ONLY`）已在 20:01 重新编出（5,974,928 B）并推上 830，
跑 **`OPFLUSH=0` vs `OPFLUSH=1` 两条腿**（`k830_probe_async.log` / `k830_probe_flush.log`）。
判据：若 async 腿复现档案里的 NMSE 签名而 flush1 腿 NMSE→0，则**病灶确定在驱动侧深队列状态**（提交层无罪，P5 继续降级，P2 变成"Mesa 侧内存一致性"专项）；
若两腿都崩，则连 kernel-granularity 的提交都不干净，Mesa 线需要重估可行性。

### 8.1 判具的第一发结果（20:0x，gen7/830，`moe_probe4` + `MOE_PROBE_KREF=1`，两份日志各 78,856 B 逐字节同大小）

```
OPFLUSH=0（async，病灶态）：worst over 1/8/32 slots: GPU NMSE=0.000000   CPU NMSE=1.2e-5 ~ 2.3e-5
OPFLUSH=1（flush1）        ：worst over 1/8/32 slots: GPU NMSE=0.000000   CPU NMSE=1.2e-5 ~ 2.3e-5
```

⇒ **MoE 内核这条路在 gen7 上是位精确的，而且 async 下也是 0**（CPU 侧 1e-5 是参考实现自己的舍入）。
⇒ **砍掉的嫌疑**：`q4_K` MoE 内核在 gen7 上被读坏 / 丢 dispatch —— 若某次 dispatch 真丢了，输出缓冲会留脏值、NMSE 不可能为 0。
⇒ **剩下的嫌疑面因此进一步收窄**：gen7 的 token-1 全崩**不是任何单个 MoE 内核**，而是
①图里**别的算子族**（注意力 / norm / rope / add / mul / cpy 等）在深队列下出问题，或
②**高 op 数下的系统性效应**（单发探针只有几个 op，测不到）。
⇒ **下一刀（已排，判据先写死）**：`tbo` 全量扫描在 `OPFLUSH=0` 与 `=1` 各跑一次，**比对两边的 FAIL 集合**；
只有"async 独有 FAIL"的算子族才是真凶；两边 FAIL 集合相同 ⇒ 单算子层无罪，转 ②（系统性效应，需要在 e2e 里按 op 段截断做二分）。

## 9. 【20:1x 追加】decode 预算的**第一块实测成分**：专家 I/O = 每 token 412 MB、**命中率 0%**

K40（安静态）、`OPFLUSH=1`、`GGML_OPENCL_MOE_TIME=1`、64 token；`[moe-ssd]` 逐 token 打点：

```
[moe-ssd] decode #64 tok=1 used=8 layers=40 unique/l=8 miss=320 hit=0 pack=40/40 nth=4
          pread_wall=399ms pread_sum=677ms bytes=412M
[moe-ssd] total[final]: miss=27520 bytes=35475.0 MiB pread=77033ms
[moe-ssd] merge-scan: experts=27520 runs=27447 avg_run=1.00 max_run=2 zerocopy=100.0% syscalls=99.7%
该腿 decode：wall_ms=103963 / 64 token = 1624 ms/token（0.62 t/s），load_ms=17820
```

⇒ **1,624 ms/token 的账，第一次能拆开**：

| 成分 | 实测/上限 | 占比 | 依据 |
|---|---|---|---|
| **专家权重 I/O** | **`pread_wall` ≈ 399 ms/token**（4 线程并行后的墙钟；`pread_sum` 677 ms） | **≈ 25%** | `bytes=412M`/token、64 token 共 **34.6 GiB**、`pread=77.0 s` |
| **提交 / flush 税** | **≤ 235 ms/token（≤14.5%）** | ≤15% | §3：12× 提交量只差 14.5%，这就是上限 |
| **专家缓存收益** | **0**：`hit=0 miss=320`（每 token 40 层 × 8 专家全 miss） | — | `avg_run=1.00 max_run=2` ⇒ 文件偏移几乎不相邻、**无法合并**；`syscalls=99.7%` |
| 其余（GPU 执行 + CPU 回落算子往返 + ggml 调度） | ≈ 1.0 s/token | ≈ 60% | 减法所得；**尚未直接测**（见 §10 为什么测不了） |

⇒ **改判**：这条线的第二瓶颈不是提交层，是**专家装载**。`hit=0` + `avg_run=1.00` 说明现在的装载模式是
"每 token 40 层 × 8 专家的随机 1 MB 粒度读"，**缓存与合并两条路都没吃到**。⇒ 新增候选项 **P8 专家装载**：
层内专家排序/去重（同层 8 专家若有重复 `unique/l=8` 已去重，跨层无复用）、按文件偏移预取合并、
把 34.6 GiB/64 token 的量压进 KV/权重共存预算内。这比继续磨提交层的性价比高得多。

## 10. 【20:2x 追加】P4 真正的靶子是**算子支持面**——"全 GPU"在算子层根本不成立

`tbo support -b GPUOpenCL` 全量普查（830 / gen7，部署 lib，`OPFLUSH` 无关）：
**115 个算子族、20,411 个用例，SUPPORTED 9,277 / NOT SUPPORTED 11,134 ⇒ 不支持率 54.5%**。
关键族（supported/总）：

| 算子族 | 支持率 | 后果 |
|---|---|---|
| **`TOP_K`** | **0/48（整族不支持）** | **MoE 每 token 的 top-k 路由必然在 CPU 上跑** |
| **`GET_ROWS`** | **21/240 = 9%** | gather 类算子基本落 CPU |
| **`SET_ROWS`** | **67/727 = 9%** | scatter 同理 |
| **`CPY`** | **138/598 = 23%** | 大量张量拷贝落 CPU ⇒ **每 token 多次 GPU↔CPU 往返** |
| `MUL_MAT_ID` | **171/945 = 18%** | 生产 MoE 形状**大多数走不到 GPU 批量路**（这正是 MoE 计时从未出数的原因，见下） |
| `FLASH_ATTN_EXT` | 2738/5308 = 52% | 注意力一半形状落 CPU/回退 |
| `MUL_MAT` | 1008/1685 = 60% | 线性层形状覆盖不全 |
| `RMS_NORM` | 31/51 = 61% | 归一化部分落 CPU |
| `CONCAT` | 112/192 = 58% | — |
| `SOFT_MAX` / `ROPE` / `ADD` / `MUL` / `NORM` | 100% | 干净 |
| 另有 **44 个族整族不支持**（含 `SUM`、`ARGMAX`、`GET_ROWS_BACK`、`SILU_BACK`、`RWKV_WKV*`、`MUL_MAT_ID_W4A4/W4A8`…） | 0% | — |

⇒ 三条硬结论：
1. **L1 的"整条图跑 GPU"目前不是"没修好"，而是"根本没实现"**：`TOP_K`/`GET_ROWS`/`SET_ROWS`/多数 `CPY`/`SUM`
   每 token 都在 CPU 上，且必然伴随 GPU↔CPU 搬运与同步 —— **§9 里那 ~1.0 s/token 的"其余"里，这部分是头号嫌疑**，
   也正是"同步"这一项预算的真实来源。
2. **P4 的靶子从"修 `MUL_MAT_ID` 生产形状"改成"补算子支持面"**，按对 decode 的影响排序：
   **`TOP_K` → `GET_ROWS`/`SET_ROWS` → `CPY` → `MUL_MAT_ID` 形状覆盖 → `FLASH_ATTN_EXT` 覆盖**。
3. **`GGML_OPENCL_MOE_TIME` 是条死路（已定位到行）**：knob 在
   [ggml-opencl.cpp:25053-25055](../third_party/llama.cpp/ggml/src/ggml-opencl/ggml-opencl.cpp#L25053-L25055)，
   只在 `is_q3_k` **且批量 q3_K 路被走到**时才打印；K40 上跑 q3_K 模型 **零输出** ⇒ 批量路没进去
   （v2 需要 host 预置 `seff/meff` 平面，缺则 `return false` 落 dense 回退）。
   ⇒ **"GPU 执行"这一项要能测，前提是让 seff/meff 平面就位** —— 这是 P4 的一个具体前置子任务，
     也解释了为什么这份裁决报告里 GPU 执行只能靠减法估。
