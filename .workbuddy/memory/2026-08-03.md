## 致命崩溃修复：聊天发消息后 native 崩溃（ggml_abort）
- **现象**：Redmi onyx / Android 16，进入聊天发消息后 APP 崩溃。native 堆栈：`llama_context::decode` → `ggml_abort` → `abort` (SIGABRT)，入口 `nativeCompletionWithMessages` → `InferenceEngine::completion`。
- **根因**：`android/app/src/main/cpp/tongyilite_jni.cpp` 的 `completion()` 原 prompt 截断逻辑（约 320 行）只保证 `n_prompt <= n_ctx-4`，**未给生成预留 KV cache 空间**。生成循环允许最多 `max_tokens=2048` 个 token，decode 位置 `decode_pos = n_prompt + n_gen - 1`。当 `n_prompt + 2048 > n_ctx(4096)`（历史+提示超 2048 token）时越界，llama.cpp 在 `kv_unified` 模式下 `ggml_abort`。即「聊几句历史变长后必崩」。
- **修复**（已改 + 编译验证通过，`flutter build apk --debug` 15s 通过）：
  1. 截断改为预留 `gen_budget = max(1, n_ctx - max_tokens - 4)`，超出则 `erase` **最旧** token、保留尾部最近上下文（最新用户轮 + assistant 前缀在尾部）。
  2. 生成循环 decode 前加 `if (decode_pos >= llama_n_ctx(context)) break;` 兜底，越界即停生成而非崩溃。
- 注：此崩溃与本机 Dart 侧 `<thinking>` 解析 bug 是两回事，勿混淆。Dart 侧 `chat_provider.dart` 的 `<thinking>` 状态机修复此前已落地（git diff 干净）。
- 设备当前未连接，未做上机实测；编译已验证。待设备在线后用标准流程 `build apk + adb install -r` 验证崩溃消失。

## Vulkan GPU 加速：编译打通（APK 已含 libggml-vulkan.so，待真机验证）
承接上节。主机工具链搭好后又踩了 6 个坑，逐个修完，`flutter build apk --debug --target-platform android-arm64` 已成功。

**坑 1 · host-toolchain 不能设 `CMAKE_SYSTEM_NAME`**
- 现象：子构建 try_compile 失败 —— `Run Build Command(s): cmTC_xxxx && 参数错误。`
- 根因：主机本就是 Windows，声明 `set(CMAKE_SYSTEM_NAME Windows)` 会让 CMake 认为在交叉编译，try_compile 从 "skipped" 变成真去构建+运行。官方模板 `ggml/src/ggml-vulkan/cmake/host-toolchain.cmake.in` **也不设**它。已删除。

**坑 2 · `CMAKE_MAKE_PROGRAM` 必须是 CACHE 变量（最隐蔽）**
- 同样报 `cmTC_xxxx && 参数错误`，但注意日志里 `Make command was:  cmTC_xxxx &&` —— make program 是**空字符串**。
- 根因：ExternalProject 只传 `-GNinja`，**不转发** `-DCMAKE_MAKE_PROGRAM`；generator 在初始化阶段只读 cache，工具链里的普通变量此时不可见。
- 修法：`set(CMAKE_MAKE_PROGRAM ".../cmake/3.22.1/bin/ninja.exe" CACHE FILEPATH "" FORCE)`。
- 调试技巧：手动 `cmake -G Ninja -DCMAKE_TOOLCHAIN_FILE=... <vulkan-shaders 目录>` 单独复现子构建，比跑整个 apk 快 100 倍。但手动测试时若在命令行传了 `-DCMAKE_MAKE_PROGRAM` 就会掩盖此 bug（我被这个骗了一轮）。

**坑 3 · NDK sysroot 没有 `vulkan/vulkan.hpp`**
- 现象：`fatal error: 'vulkan/vulkan.hpp' file not found`。
- 根因：NDK 只提供 C 头 `vulkan.h`；C++ 绑定 `vulkan.hpp` 是 LunarG SDK 的。而 Android 工具链 `CMAKE_FIND_ROOT_PATH_MODE_INCLUDE=ONLY` 让 FindVulkan 的 find_path 看不到主机 SDK。
- 修法：`set(Vulkan_INCLUDE_DIR "C:/VulkanSDK/1.4.357.0/Include" CACHE PATH "" FORCE)`。整体用 SDK 头（.h + .hpp 版本一致）比混用 NDK 的 .h 更安全。

**坑 4 · Vulkan 桩库要用 minSdk 对应的 API 级别，不能用 24**
- 现象：`ld.lld: error: undefined symbol: vkGetPhysicalDeviceFeatures2`。
- 根因：该函数是 Vulkan 1.1，Android **API 28+** 才导出。API 24 的 `libvulkan.so` 桩只有 1.0 符号。本项目 minSdk=33（clang `--target=aarch64-none-linux-android33`），API 33 桩有 233 个符号含该函数。
- 修法：路径里的 `/24/` 改成 `${ANDROID_PLATFORM_LEVEL}`（fallback 33）。
- 查符号用 `llvm-readelf --dyn-syms <stub>.so`（`llvm-nm -D` 对这些桩库无输出，别用）。

**坑 5 · `rm -rf android/app/.cxx` 会被沙箱 safe-delete 静默拦截**
- 表现：命令"成功"但目录还在，Gradle 判定 up-to-date，7 秒"编译完成"却产物没变（当时 `GGML_VULKAN:BOOL=OFF` 还留在 CMakeCache 里，差点误判）。
- 正确做法：用 **PowerShell 工具** `Remove-Item -LiteralPath 'E:\...\.cxx' -Recurse -Force`。
- 一般教训：改了 CMakeLists 的 cache 变量后**必须**清 `.cxx`。验证是否真重编看 `build/app/intermediates/cxx/Debug/*/obj/arm64-v8a/` 的时间戳和文件清单。

## 聊天会话管理「点击不生效」BUG 修复（home_screen.dart）
- 现象：用户真机测，点 AppBar 左上「会话」小图标，抽屉不弹出，无法新建/删除会话。
- 根因：`AppBar.leading` 里的 `Scaffold.of(context).openDrawer()` 用了 `build()` 的 context（HomeScreen 层，在 Scaffold **之上**）。而 `main.dart:55` 是 `home: const HomeScreen()` 且无父级 Scaffold，`Scaffold.of(buildContext)` 向上找不到 Scaffold 祖先 → `openDrawer` 无目标（debug 报错 / release 被手势异常吞掉 = 点击没反应）。
- 修复：把 `leading` 包进 `Builder`，用 `Builder` 的 `ctx`（Scaffold 之下的 context）调 `Scaffold.of(ctx).openDrawer()`。`flutter analyze` 通过；`flutter build apk --debug`（31s，Vulkan 已缓存）成功；`adb install -r` Success；启动 logcat 无本 App 崩溃/Scaffold 报错（pid 8413 RUNNING）。
- **Flutter 通用坑备忘**：在 `build()` 内（或 AppBar/leading/actions 等由 build context 创建的子部件）调用 `Scaffold.of(context)`/`Theme.of(context)`/`Navigator.of(context)` 等"向上找祖先"的 API，若要操作自身返回的 Scaffold，必须用 `Builder` 包裹拿到 Scaffold 之下的 context，否则 context 层级在 Scaffold 之上会找不到。

## AppBar leading 模型状态「竖排文本」BUG 修复（home_screen.dart）
- 现象：真机 AppBar 左侧「模型就绪」状态旁边出现一竖排文本（很奇怪）。
